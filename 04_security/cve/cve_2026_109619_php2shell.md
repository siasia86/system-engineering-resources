## 2. 취약점 상세

> 출처: [GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) / [NVD CVE-2026-109619](https://nvd.nist.gov/vuln/detail/CVE-2026-109619) / [oss-security 2026/10/21/7](https://www.openwall.com/lists/oss-security/2026/10/21/7) / [Wiz Research](https://www.wiz.io/blog/php2shell-php-rce)

PHP는 상주 워커에서 여러 요청에 걸쳐 전역 상태(error, session, object, extension 데이터)를 유지하며, 이 상태가 일시적으로 요청 메모리를 가리킵니다. 이전 요청이 OOM을 포함한 fatal error로 끝나면 전역 상태 초기화 단계를 건너뛰거나, 초기화 후 다시 채워질 수 있습니다. 요청 heap은 해제되지만 전역 변수는 여전히 해제된 메모리를 가리켜 **use-after-free**가 됩니다. 다음 요청이 초기화를 마치기 전에 이 상태를 읽거나 그 값으로 분기하면, heap 배치를 조작할 수 있는 공격자가 원격 코드를 실행할 수 있습니다.

```
요청 A (producer): fatal error / OOM 유발
        ↓
전역 상태 초기화 누락 → 해제된 요청 heap을 계속 참조
        ↓
같은 워커의 요청 B (consumer): 초기화 전에 전역 상태 사용
        ↓
use-after-free → heap 조작 → 원격 코드 실행
```

**확인된 producer·consumer 경로 (GHSA 기재):**

| 경로                                       | 상태      | 설명                                                                               |
|--------------------------------------------|-----------|------------------------------------------------------------------------------------|
| PHP 8.5 fatal error backtrace              | ❌ 확인   | shutdown에서 backtrace 상태 미정리 → 이후 진단 메시지가 사용. `mod_php` RCE 근거   |
| session upload progress                    | ❌ 확인   | 업로드 처리 중 OOM·fatal error → session·decoder 상태 잔존. `mod_php`·FPM 검증     |
| 요청 초기화 전 INI 진단                    | 🟡 가능   | 특정 INI 적용 중 warning·deprecation이 stale error 상태 사용 (표시·로그 여부 무관) |
| 기타 error·exception·object·extension 상태 | 🟡 조건부 | 애플리케이션·확장 모듈에 따라 다름                                                 |

**취약 버전:**

| 브랜치 | 취약 범위      | 패치 버전   |
|--------|----------------|-------------|
| 8.2.x  | 8.2.35 미만    | **8.2.35+** |
| 8.3.x  | 8.3.0 ~ 8.3.35 | **8.3.36+** |

## 3. 영향 범위 확인

### 익스플로잇 조건

| 조건                  | 설명                                                         |
|-----------------------|--------------------------------------------------------------|
| 취약 PHP 버전         | 위 표의 패치 버전 미만 (배포판은 백포트 버전 기준)           |
| 상주 워커             | producer·consumer 요청이 같은 워커에서 처리 (`mod_php`, FPM) |
| fatal error 유발 가능 | OOM·실행 시간 초과 등 공격자가 도달할 수 있는 fatal error    |
| consumer 경로 활성    | `fatal_error_backtraces`(8.5), `session.upload_progress` 등  |

### 탐지 명령어

```bash
# PHP 버전·패키지
php -v
dpkg -l 'php*' 2>/dev/null | grep -E '^ii\s+(php[0-9.]+-(common|cli|fpm)|libapache2-mod-php)'
rpm -q php php-common php-fpm 2>/dev/null

# 패치 적용 여부 (설치된 패키지명으로 변경)
apt-get changelog php8.3-common 2>/dev/null | grep CVE-2026-109619 | head -3
rpm -q --changelog php-common 2>/dev/null | grep CVE-2026-109619 | head -3

# 확인된 consumer 경로 설정 (1 또는 On = 활성)
php -i | grep -E '^(fatal_error_backtraces|session.upload_progress.enabled)'

# FPM 워커 재사용 횟수 (0 = 무제한 재사용)
grep -rh '^pm.max_requests' /etc/php/*/fpm/pool.d/ /etc/php-fpm.d/ 2>/dev/null
```

🟡 `php -i`는 CLI 설정을 보여줍니다. FPM·Apache에 적용되는 값은 각 SAPI의 `php.ini`·pool 설정에서 확인합니다.

## 4. 대처 방안

### 즉시 패치 (근본 대응)

> 출처: [GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) — "Updating to a release containing the complete state reset patch is the only reliable mitigation."

```bash
# Ubuntu / Debian
sudo apt update && sudo apt install --only-upgrade 'php*' -y
sudo systemctl restart 'php*-fpm' apache2 2>/dev/null

# RHEL / CentOS / Amazon Linux
sudo dnf update 'php*' -y
sudo systemctl restart php-fpm httpd 2>/dev/null
```

🟡 상주 워커에 남은 상태가 문제이므로 패키지 갱신 후 **모든 워커를 재시작**합니다.

### 임시 완화 (패치 적용 전, 불완전)

> 출처: [GHSA-6wmf-4rv5-p3rp](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) — Mitigations and workarounds 섹션. 권고문은 설정만으로 완전히 막는 방법이 없다고 밝혔습니다.

| 조치                                              | 대상         | 효과·한계                                                  |
|---------------------------------------------------|--------------|------------------------------------------------------------|
| `fatal_error_backtraces=0` + 워커 재시작          | PHP 8.5      | 확인된 RCE producer 제거, 다른 상태 문제는 남음            |
| `session.upload_progress.enabled=0` + 워커 재시작 | 전 버전      | upload progress 경로 제거, 미사용 시 패치 후에도 유지 권장 |
| `pm.max_requests=1`                               | PHP-FPM      | 워커 재사용 제한, 성능 저하 감수 필요                      |
| 도달 가능한 fatal error 제거                      | 애플리케이션 | 실행 시간 초과도 fatal error로 취급                        |
| shutdown·cleanup 중 진단 제거                     | 애플리케이션 | consumer 경로 축소                                         |
| INI 설정을 시작 설정으로 이동                     | 운영 설정    | 요청 초기화 전 INI 진단 경로 축소                          |

```bash
# 예: PHP-FPM pool 설정 (경로는 버전·배포판에 맞게 변경)
# /etc/php/8.5/fpm/pool.d/www.conf
php_admin_value[fatal_error_backtraces] = 0          ; PHP 8.5만 해당
php_admin_flag[session.upload_progress.enabled] = off
; pm.max_requests = 1                                ; 성능 영향 검토 후 적용

sudo systemctl restart php8.5-fpm
```

```bash
# 예: Apache mod_php (VirtualHost 또는 conf)
php_admin_value fatal_error_backtraces 0
php_admin_flag session.upload_progress.enabled off

sudo systemctl restart apache2
```

🟡 GHSA는 격리 환경에서 `E_ALL` 로그를 켜 warning·fatal error 발생 지점을 찾도록 권장합니다. 다만 로그가 깨끗하다고 안전이 증명되지는 않습니다.

🟡 [CVE-2026-109618](./cve_2026_109618_php2shell.md)의 완화 조치도 함께 적용합니다(GHSA 안내).

## 5. 사후 검증

```bash
# 버전 확인 (8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 이상, 또는 배포판 수정 버전)
php -v
dpkg -l 'php*-common' 2>/dev/null | grep '^ii'
rpm -q php-common 2>/dev/null

# 워커가 새 바이너리로 재시작됐는지 확인 (삭제된 바이너리 참조 = 재시작 누락)
sudo lsof -nP 2>/dev/null | grep -E 'php.*\(deleted\)' | head

# 임시 완화를 적용한 경우 실제 SAPI에서 값 확인 (웹 루트 접근 제한 후 확인하고 즉시 삭제)
echo '<?php echo ini_get("session.upload_progress.enabled"), PHP_EOL;' | sudo tee /var/www/html/_chk.php >/dev/null
curl -s http://127.0.0.1/_chk.php; sudo rm -f /var/www/html/_chk.php
```

🟡 익스플로잇 성공 시 웹 워커 권한으로 코드가 실행됩니다. 공격 징후가 있으면 웹 루트 변조, 웹 사용자 소유 신규 파일, 웹 워커의 외부 연결을 함께 점검합니다.
