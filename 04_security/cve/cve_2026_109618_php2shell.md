🔴 **애플리케이션 코드 결함과 무관하게 PHP 엔진 자체에서 발생합니다.** PHP 권고는 Apache `mod_php` 기본 설정에서 HTTP 비인증 RCE를 확인했다고 밝혔습니다.

> 동일 공개 묶음: [CVE-2026-109619](./cve_2026_109619_php2shell.md) (stale global state). 두 CVE의 수정 버전이 같으므로 함께 대응합니다.

## 2. 취약점 상세

> 출처: [GHSA-w8hw-w9fx-j79w](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) / [NVD CVE-2026-109618](https://nvd.nist.gov/vuln/detail/CVE-2026-109618) / [oss-security 2026/10/21/6](https://www.openwall.com/lists/oss-security/2026/10/21/6) / [Wiz Research](https://www.wiz.io/blog/php2shell-php-rce)

PHP는 메모리 부족(OOM) 오류가 나면 `longjmp()`로 현재 문맥을 빠져나가 요청 처리를 중단합니다. 요청 메모리가 **완전히 초기화되기 전에 다른 경로에서 접근 가능한 상태**일 때 할당이 실패하면, 조기 탈출로 그 메모리가 잘못된 값으로 남습니다. 이후 요청 종료(shutdown) 과정이 이 메모리를 읽거나 그 값으로 분기하면서 메모리 손상이 발생합니다. 실패한 할당은 잘못된 메모리와 관련이 없어도 됩니다.

```
multipart 요청 (헤더·필드 폭증)
        ↓
요청 메모리 일부만 초기화된 상태에서 할당 실패 (OOM)
        ↓
longjmp() 조기 탈출 → 초기화 미완료 메모리 잔존
        ↓
request shutdown이 잘못된 메모리를 읽고 분기
        ↓
메모리 손상 → 원격 코드 실행
```

**OOM 유도 경로 (GHSA 기재):**

| 경로                  | 설명                                                                       |
|-----------------------|----------------------------------------------------------------------------|
| content length 미선언 | 쓸 수 있는 길이 선언이 없는 multipart 요청이 `post_max_size` 1차 검사 통과 |
| part별 헤더 무제한    | part마다 헤더 수 제한이 없어 전송량보다 PHP 메모리 사용량이 훨씬 큼        |
| 빈 file control       | `max_file_uploads`에 집계되지 않지만 파일 메타데이터 배열 생성             |
| 중첩 필드명           | 위 작업량을 배수로 증가                                                    |

**SAPI별 판정 (GHSA 기준):**

| SAPI               | 판정                                             |
|--------------------|--------------------------------------------------|
| Apache `mod_php`   | ❌ 기본 설정에서 비인증 RCE 확인                 |
| PHP-FPM            | 🟡 취약 가능성 높음, 전체 익스플로잇 체인 미시연 |
| FrankenPHP / LSAPI | 🟡 취약 가능성 있음, 미검증                      |

**패치 내용:** OOM 처리에서 `longjmp()`를 제거합니다. 대신 다음 VM safe point에서 soft OOM을 발생시키고, 더 높은 임계값에서는 hard OOM으로 `_exit()`를 호출합니다.

**취약 버전:**

| 브랜치 | 취약 범위      | 패치 버전   |
|--------|----------------|-------------|
| 8.2.x  | 8.2.35 미만    | **8.2.35+** |
| 8.3.x  | 8.3.0 ~ 8.3.35 | **8.3.36+** |
| 8.4.x  | 8.4.0 ~ 8.4.26 | **8.4.27+** |
| 8.5.x  | 8.5.0 ~ 8.5.11 | **8.5.12+** |

🟡 NVD·GHSA는 지원 중인 8.2~8.5만 기재합니다. Wiz는 "지난 10년간 릴리스된 모든 PHP 버전"(PHP 5.4 이후)이 영향을 받는다고 밝혔습니다. 8.1 이하 EOL 버전은 upstream 패치가 없으므로 배포판 백포트를 확인합니다.

**배포판 수정 버전 (2026-10-22 확인):**

| 배포판               | 패키지 | 수정 버전                   | 공지               |
|----------------------|--------|-----------------------------|--------------------|
| Ubuntu 22.04 LTS     | php8.1 | 8.1.2-1ubuntu2.28           | USN-8948-1/2       |
| Ubuntu 24.04 LTS     | php8.3 | 8.3.6-0ubuntu0.24.04.13     | USN-8948-1/2       |
| Ubuntu 26.04 LTS     | php8.5 | 8.5.4-0ubuntu1.5            | USN-8948-1/2       |

| Debian 12 (bookworm) | php8.2 | 8.2.35-1~deb12u1            | DLA-4848-1         |
| Debian 13 (trixie)   | php8.4 | 8.4.27-1~deb13u1            | DSA-6574-1         |
| RHEL 계열            | php    | 미확인 (공지 페이지만 존재) | Red Hat CVE 페이지 |

🟡 Ubuntu 페이지는 USN-8948-1과 USN-8948-2 중 어느 공지가 어느 릴리스를 다루는지 밝히지 않습니다. 배포판 백포트 버전은 upstream 버전 번호보다 낮게 보이므로 upstream 버전 비교만으로 판정하지 않습니다.

## 3. 영향 범위 확인

### 익스플로잇 조건

| 조건                 | 설명                                                   |
|----------------------|--------------------------------------------------------|
| 취약 PHP 버전        | 위 표의 패치 버전 미만 (배포판은 백포트 버전 기준)     |
| HTTP로 PHP 요청 도달 | 애플리케이션 코드 결함 불필요, 요청 시작 단계에서 발생 |
| multipart 요청 처리  | OOM 유도 경로가 RFC1867 multipart 파싱에 집중됨        |
| OOM 발생 가능        | `memory_limit` 또는 `mmap()` 할당 실패                 |

### 탐지 명령어

```bash
# PHP 버전 (CLI와 웹 SAPI의 바이너리가 다를 수 있음)
php -v
php-fpm -v 2>/dev/null || ls /usr/sbin/php-fpm* 2>/dev/null

# 패키지 버전 (Ubuntu/Debian)
dpkg -l 'php*' 2>/dev/null | grep -E '^ii\s+(php[0-9.]+-(common|cli|fpm)|libapache2-mod-php)'

# 패치 적용 여부 (Ubuntu/Debian)
apt-get changelog php8.3-common 2>/dev/null | grep CVE-2026-109618 | head -3   # 설치된 버전으로 변경

# 패키지 버전 (RHEL 계열)
rpm -q php php-common php-fpm 2>/dev/null
rpm -q --changelog php-common 2>/dev/null | grep CVE-2026-109618 | head -3

# 사용 중인 SAPI (mod_php 로드 여부)
apachectl -M 2>/dev/null | grep -i php

# OOM 관련 설정
php -i | grep -E '^(memory_limit|post_max_size|max_input_vars|max_input_nesting_level|max_file_uploads|max_multipart_body_parts)'
```

🟡 `php -i`는 CLI 설정을 보여줍니다. FPM·Apache 설정은 각 SAPI의 `php.ini`·pool 설정에서 확인합니다.

### 공격 징후 (Wiz 기준)

| 징후                                                     | 확인 위치                 |
|----------------------------------------------------------|---------------------------|
| 비정상 multipart 요청 뒤 memory limit 오류·반복 HTTP 500 | 웹 서버 access/error 로그 |
| 비정상적으로 크거나 깨진 `PHPSESSID` 응답 쿠키           | 웹 서버·WAF 로그          |
| 설명되지 않는 PHP 워커 재시작                            | FPM 로그, Apache 로그     |

## 4. 대처 방안

### 즉시 패치 (근본 대응)

> 출처: [GHSA-w8hw-w9fx-j79w](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) — "Updating to a PHP release containing the patch to this vulnerability is the _only_ complete mitigation."

```bash
# Ubuntu / Debian
sudo apt update && sudo apt install --only-upgrade 'php*' -y
sudo systemctl restart 'php*-fpm' apache2 2>/dev/null

# RHEL / CentOS / Amazon Linux
sudo dnf update 'php*' -y
sudo systemctl restart php-fpm httpd 2>/dev/null
```

🟡 패키지 갱신 후 모든 PHP 워커(FPM, Apache)를 재시작해야 새 바이너리가 적용됩니다.

### 임시 완화 (패치 적용 전, 불완전)

> 출처: [GHSA-w8hw-w9fx-j79w](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) — Mitigations and workarounds 섹션

| 조치                        | 내용                                                                          | 한계                                |
|-----------------------------|-------------------------------------------------------------------------------|-------------------------------------|
| `memory_limit=-1`           | 관리자 설정으로 강제 (`php_admin_value`)                                      | `mmap()` 실패로 취약 경로 도달 가능 |
| rlimit 사용 금지            | `RLIMIT_AS`·`RLIMIT_DATA` 미사용                                              | 한도 도달 시 `mmap()` 실패 유발     |
| 입력 크기 제한              | `post_max_size` 보수적 설정 + 프런트엔드에서 디코딩 후 요청 크기 별도 제한    | 전면 차단 아님                      |
| 입력 구조 제한              | `max_input_nesting_level`·입력 변수·multipart part·part별 헤더·업로드 수 축소 | 전면 차단 아님                      |
| multipart 차단              | multipart form data를 쓰지 않으면 프런트엔드에서 차단                         | 업로드 기능 사용 시 불가            |
| cgroup·컨테이너 메모리 제한 | `memory_limit` 대안                                                           | 권고문도 부분 대안으로만 기재       |

🟡 `memory_limit=-1`은 PHP 자체 메모리 상한을 없애는 설정입니다. 한 요청이 메모리를 과다 사용할 수 있으므로 적용 전 서버 메모리 여유와 cgroup 제한을 함께 검토합니다(문서 작성자 판단).

```bash
# 예: PHP-FPM pool 설정 (경로는 버전·배포판에 맞게 변경)
# /etc/php/8.3/fpm/pool.d/www.conf
php_admin_value[memory_limit] = -1
php_admin_value[max_input_nesting_level] = 16
php_admin_value[max_input_vars] = 1000

sudo systemctl restart php8.3-fpm
```

🟡 GHSA는 [CVE-2026-109619](./cve_2026_109619_php2shell.md)의 완화 조치도 함께 적용하도록 안내합니다. 패치하지 못하는 동안에는 Cloudflare, Fastly, Google, Vercel 등 CDN·WAF 업체의 PHP2Shell 대응 규칙도 검토합니다(Wiz 기재).

## 5. 사후 검증

```bash
# 버전 확인 (8.2.35 / 8.3.36 / 8.4.27 / 8.5.12 이상, 또는 배포판 수정 버전)
php -v
dpkg -l 'php*-common' 2>/dev/null | grep '^ii'
rpm -q php-common 2>/dev/null

# 워커가 새 바이너리로 재시작됐는지 확인 (삭제된 바이너리 참조 = 재시작 누락)
sudo lsof -nP 2>/dev/null | grep -E 'php.*\(deleted\)' | head

# 서비스 상태
systemctl status 'php*-fpm' apache2 httpd 2>/dev/null | grep -E 'Loaded|Active'

# 공개 이후 의심 로그 확인 (memory 오류·500 응답)
sudo grep -h 'Allowed memory size' /var/log/php*-fpm.log /var/log/apache2/error.log 2>/dev/null | tail
```

🟡 익스플로잇 성공 시 웹 워커 권한으로 코드가 실행됩니다. 공격 징후가 있으면 웹 루트 변조, 웹 사용자 소유 신규 파일, 웹 워커의 외부 연결을 함께 점검합니다.
