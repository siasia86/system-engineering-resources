## 1. 샌드박스의 역할

샌드박스는 프로세스가 접근할 수 있는 파일, 네트워크 또는 실행 기능을 제한하는 환경입니다. 구체적인 격리 범위는 제품, 운영체제, 실행 방식과 설정에 따라 달라집니다. 단순히 작업 디렉토리를 바꾸는 것과는 다릅니다.

AI가 지침을 잘못 해석하거나 외부 문서의 악성 지시를 따르더라도, 허용하지 않은 자원에 미치는 영향을 줄이는 것이 목적입니다. 샌드박스는 판단의 정확성을 보장하거나 모든 사고를 예방하는 장치가 아닙니다.

- 쓰기 제한: 허용하지 않은 파일 변경을 차단합니다.
- 읽기 제한: 비밀정보를 입력으로 가져오지 못하게 하는 별도의 보호입니다. 읽기 전용과 읽기 금지는 다릅니다.
- 네트워크 제한: 외부 전송과 원격 서비스 접근 범위를 제어합니다.
- 자원 제한: CPU·메모리·프로세스 수 제한이 필요한 경우 별도 설정 여부를 확인합니다.

허용된 파일의 잘못된 수정, 허용된 목적지로의 정보 전송, 샌드박스 밖 도구가 수행하는 원격 변경은 별도의 통제가 필요합니다.

## 2. 다층 안전장치

각 장치는 서로 다른 질문에 답합니다. 어느 하나를 다른 장치의 대체물로 취급하지 않습니다.

1. 지침·정책: 무엇을 해도 되는지 정의합니다. Markdown 지침만으로 OS 접근을 강제 차단하지는 못합니다.
2. 실행 승인: 특정 요청을 실행해도 되는지 판단합니다. 사용자 승인과 자동 검토 승인을 구분합니다.
3. 샌드박스: 해당 실행 환경에서 접근 가능한 자원을 제한합니다.
4. OS 권한·ACL: 실제 실행 사용자와 그룹이 자원에 접근할 수 있는지 제한합니다.
5. 실행기·서버 측 통제: 허용 작업, 인자, 대상 서버와 자격증명의 범위를 검사합니다.
6. 검증·감사: 결과의 정확성과 승인 범위 준수를 확인하고 기록합니다.

예를 들어 파일 ACL에 쓰기 권한이 있어도 샌드박스에서 해당 경로가 읽기 전용이면 수정할 수 없습니다. 반대로 샌드박스가 쓰기를 허용해도 OS 권한이 부족하면 수정할 수 없습니다. 실제 허용 여부는 적용 중인 통제들을 함께 확인해야 합니다.

승인된 샌드박스 밖 실행은 곧 root 실행을 의미하지 않습니다. 샌드박스 예외 승인과 sudo를 통한 OS 권한 상승은 별개입니다. 정책 예외를 승인했다고 ACL이나 마운트 설정이 자동 변경되는 것도 아닙니다.

## 3. Codex 적용 사례

Codex에서는 샌드박스 범위, 승인 정책, 승인 검토 주체를 구분합니다. `workspace-write`는 작업공간 쓰기를 허용하는 모드이고, `on-request`는 경계를 넘는 작업에 필요한 승인 요청을 다룹니다. `approvals_reviewer`의 `user`와 `auto_review`는 각각 사용자와 검토 agent로 승인 요청을 전달하는 설정입니다. 자동 검토는 샌드박스 자체를 해제하지 않습니다. [공식 Sandbox 문서](https://learn.chatgpt.com/docs/sandboxing)

다음은 수동 승인 중심의 개념 예시이며, 이 문서 작성으로 적용되는 설정은 아닙니다.

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"
approvals_reviewer = "user"
```

기본 `workspace-write` 정책에서도 writable root의 `.git`, `.agents`, `.codex`에는 읽기 전용 보호가 적용됩니다. 따라서 문서 편집은 가능하지만 Git 메타데이터 갱신은 별도 승인이 필요한 상황이 생길 수 있습니다. `.governance`라는 이름만으로 같은 보호가 자동 적용된다고 가정해서는 안 됩니다. [공식 보호 경로 설명](https://learn.chatgpt.com/docs/agent-approvals-security#protected-paths-in-writable-roots)

2026-09-22 점검 사례에서는 다음 차이를 관찰했습니다. 다른 세션이나 서버에도 같은 상태가 적용된다는 뜻은 아닙니다.

- 일반 샌드박스에서 35 저장소의 작업 디렉토리는 `rw`, `.git`은 `ro`로 표시됐습니다.
- 샌드박스 밖의 일반 사용자 실행에서는 `engineer` 그룹과 대상 파일의 ACL 쓰기 권한이 확인됐습니다.
- 사용자 터미널의 sudo 진단에서도 호스트 마운트와 ACL이 일치했습니다.
- 이 확인은 권한과 마운트 진단이며, 실제 Git 쓰기 성공이나 전체 하위 파일 검증을 의미하지 않습니다.

설정 파일에 적힌 값과 실행 중인 세션의 적용 상태를 함께 확인합니다. 버전·관리 정책·실행 옵션에 따라 차이가 생길 수 있으므로 특정 세션의 결과를 영구적인 제품 규칙으로 기록하지 않습니다.

## 4. 저장소별 책임

다음은 여러 저장소에서 안전장치를 운영하기 위한 책임 구분입니다. 이 문서는 개념을 설명하며, 각 저장소의 최신 정책과 구현 상태를 대신하지 않습니다.

- `31_governances`: 공통 운영 기준, 저장소별 profile, 예외 승인 기준과 배포 계약을 관리하는 정책 기준점입니다.
- `35_agent-skill`: 재사용할 개인 공통 지침과 skill·agent 자산을 관리합니다. 지침 배포만으로 실행 권한이 강제되지는 않습니다.
- `30_sia-scripts`: 정책을 검사하고 설치·갱신·복구하는 실행 도구를 담당합니다. 지원 범위와 구현 여부는 해당 저장소에서 확인합니다.
- `32_system-engineering-resources`: 개념과 학습 자료를 설명합니다. 운영 정책의 또 다른 원본으로 사용하지 않습니다.
- 각 consumer 저장소: 배포받은 기준을 참조하고, 허용된 작업 영역에서 개발합니다. 중앙 관리 영역의 변경은 31의 검토·배포 경로를 따릅니다.

향후에는 샌드박스 경로, OS 계정·ACL, 승인 방식, 허용 실행기, 네트워크·원격 대상, 예외 만료 조건을 하나의 profile에서 추적할 수 있도록 설계합니다. 단, 선언한 profile과 실제 런타임 설정이 일치하는지는 별도로 검증해야 합니다.

Agent가 보호 설정 자체를 수정할 수 있다면 보호 범위를 넓힐 수 있습니다. 정책 원본, 설치된 실행기와 승인 설정의 소유권은 일반 작업 계정과 분리하는 방향으로 검토합니다.

## 5. 실행기와 원격 운영

메인 서버에서 Ansible로 여러 서버를 관리한다면, 로컬 파일 보호만으로 원격 작업을 통제할 수는 없습니다. SSH 키, API 토큰, inventory와 원격 계정 권한을 함께 제한해야 합니다.

권장하는 설계 흐름은 다음과 같습니다. 아직 배포 완료된 구조라는 뜻은 아닙니다.

```text
Agent request -> Approval -> Validating runner -> Ansible -> Scoped targets
                                  |
                              Audit record
```

실행기는 작업 식별자, 허용 인자, 대상 환경, 대상 서버, 사용할 자격증명과 변경 범위를 검증합니다. 임의 shell 문자열을 받아 실행하는 wrapper는 명령 제한 장치로 보기 어렵습니다.

"직접 명령 금지, script만 허용"을 강제하려면 agent가 동일한 운영 자격증명으로 직접 SSH나 다른 실행 경로를 사용할 수 없어야 합니다. 실행기 코드와 신뢰하는 설정도 agent가 임의 변경하지 못하게 해야 합니다. 로컬 샌드박스 밖의 MCP·외부 도구에는 그 도구의 별도 권한 경계가 필요합니다.

Hooks는 도구 호출 시 검사에, CI는 변경 결과 검증에 활용합니다. 실행 경로에 따라 적용되지 않거나 우회될 수 있으므로 운영 접근 차단의 유일한 수단으로 삼지 않습니다. 변경 후 실행되는 CI는 이미 발생한 서버 변경을 소급해서 막지 못합니다.

## 6. 환경별 권한 설계

개발·테스트 서버에는 빠른 실험을 위해 넓은 권한을 부여할 수 있습니다. 이 경우 보호 수준을 운영 환경과 동일하다고 설명하지 않습니다.

- 개발·테스트: 폐기·재생성 가능한 환경, 테스트 전용 데이터와 자격증명, 운영망과의 분리를 전제로 권한을 넓힙니다.
- 메인 관리 서버: 운영 자격증명과 실행기를 보호하고, 일반 분석·편집 작업과 서버 변경 실행을 분리합니다.
- 운영 대상 서버: 필요한 작업만 가능한 계정·권한을 부여하고, 변경 대상과 복구 절차를 검증합니다.

특히 개발 환경의 넓은 권한이 운영 자격증명, 호스트 관리 소켓 또는 공유 마운트를 통해 운영 환경으로 이어지지 않는지 확인합니다.

예외 승인에는 사유, 대상, 허용 동작, 유효 기간 또는 작업 횟수, 검증·복구 방법을 기록합니다. 파일 수정 승인, commit·push 승인, release·운영 배포 승인을 서로 대신하지 않습니다. 제한에 막혔다는 이유만으로 전체 샌드박스나 ACL을 해제하지 않습니다.

## 7. 진단과 검증 기준

권한 오류는 "검사 목적 → 관찰 결과 → 다음 조치"로 기록합니다. 먼저 실제 실행 사용자와 환경을 확인하고, 정책·샌드박스·OS·원격 권한 중 어느 계층에서 거부됐는지 좁혀갑니다.

다음은 Linux에서 특정 경로의 상태를 읽기 전용으로 확인하는 예시입니다. 변수에는 실제 검사 대상을 지정하며 비밀번호나 토큰을 출력하지 않습니다.

```bash
TARGET=/path/to/repository/.git
id
findmnt -T "$TARGET"
namei -l "$TARGET"
getfacl -pn "$TARGET"
stat -c '%A %u:%g %n' "$TARGET"
```

샌드박스 안과 승인된 외부 실행에서 동일한 대상을 비교합니다. 숫자 UID·GID가 다르게 보이거나 그룹이 누락된 경우 호스트 ACL 손상이라고 단정하지 않습니다. root로 읽은 ACL과 일반 작업 사용자의 실효 권한도 구분합니다.

운영 적용 전에는 격리된 테스트 환경에서 다음을 검증합니다.

- 허용 작업: 허용된 경로의 생성·수정과 승인된 실행이 성공하는지 확인합니다.
- 차단 작업: 보호 경로 수정, 승인되지 않은 네트워크 접근과 원격 변경이 실패하는지 확인합니다.
- 대체 경로: 심볼릭 링크, 상위 디렉토리를 통한 파일 교체, 다른 도구·자격증명 경로에서도 보호가 유지되는지 확인합니다.
- 설정 보호: agent가 정책·실행기·승인 설정을 수정해 제한을 넓힐 수 없는지 확인합니다.
- 반복 적용: 같은 정책을 다시 적용해도 불필요한 변경이 없으며, 예외 종료 후 권한이 남지 않는지 확인합니다.
- 감사·복구: 실행 목적, 대상, 승인 주체, 결과와 실패 원인을 남기고 복구 절차를 시험합니다.

보고서에는 확인된 사실, 추정, 미검증 범위를 분리합니다. 파일 접근 검사 통과를 실제 배포 성공으로, 테스트 환경 통과를 운영 적용 완료로 표현하지 않습니다.
