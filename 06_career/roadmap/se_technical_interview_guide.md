# 시스템 엔지니어 기술 면접 준비

시스템 엔지니어(SE)·SRE·인프라 직무 기술 면접에서 자주 나오는 질문 유형과 답변 구조, 준비 방법을 정리합니다. [SE 로드맵](./se_roadmap.md#면접-준비)과 [SRE 로드맵](./sre_roadmap.md#면접-준비)의 면접 준비 항목을 질문 유형별로 넓힌 문서입니다. 특정 회사의 실제 문제를 옮기지 않고, 공개 학습 자료와 일반적인 운영 원칙을 바탕으로 합니다.

## 1. 면접 구성 이해

인프라 직무 면접은 회사마다 다르지만 대체로 다음 유형을 섞습니다.

| 유형       | 확인하려는 것                               | 대표 형식                               |
|------------|---------------------------------------------|-----------------------------------------|
| 기초 지식  | OS·네트워크·스토리지 원리 이해 수준         | "TCP 3-way handshake를 설명해 주세요"   |
| 트러블슈팅 | 모르는 문제를 좁혀 가는 사고 과정           | "웹 서버가 느립니다. 어떻게 보겠습니까" |
| 설계       | 요구 조건을 구조로 바꾸는 능력, 장단점 판단 | "로그 수집 구조를 설계해 주세요"        |
| 경험(행동) | 실제로 한 일, 판단 근거, 협업 방식          | "가장 어려웠던 장애는 무엇이었나요"     |
| 실기·과제  | 손으로 다루는 능력                          | 셸 스크립트 작성, 장애 환경 복구        |

면접관은 정답 하나보다 다음을 봅니다.

- 가정을 먼저 묻고 범위를 좁히는가
- 확인한 사실과 추측을 구분해 말하는가
- 위험한 조치(재시작, 삭제) 전에 영향과 되돌리기 방법을 생각하는가
- 모르는 것을 모른다고 말하고, 어떻게 확인할지 제시하는가

## 2. 트러블슈팅 질문

### 답변 틀

Google SRE 책의 "Effective Troubleshooting" 장은 문제 보고 → 분류(triage) → 관찰(examine) → 진단(diagnose) → 검증과 조치(test and treat) → 해결(cure) 순서를 제시합니다. 면접 답변도 이 순서를 따르면 흐름이 분명해집니다.

```text
1. Clarify   : scope, since when, what changed, who is affected
2. Stabilize : reduce impact first (rollback, failover, shed load)
3. Observe   : metrics, logs, recent deploys, resource usage
4. Hypothesize and test : one variable at a time
5. Fix and verify       : confirm symptom is gone
6. Follow up            : postmortem, alert, runbook update
```

같은 장은 흔한 함정으로 관련 없는 증상에 매달리기, 지표의 의미를 잘못 읽기, 지나치게 드문 원인부터 의심하기, 우연한 상관관계를 원인으로 착각하기를 듭니다. 답변 중에 "이 지표만으로는 원인이라고 단정할 수 없으니 이것도 확인하겠다"는 말을 넣으면 함정을 알고 있다는 점이 드러납니다.

### 예시: "웹 서버 응답이 느려졌습니다"

1. 질문으로 범위 좁히기: 모든 요청인지 특정 URL인지, 언제부터인지, 최근 배포·설정 변경이 있었는지 묻습니다.
2. 영향 줄이기: 최근 배포가 있었다면 되돌리기를 우선 검토합니다.
3. 자원 확인: USE 방법(Utilization·Saturation·Errors, 자원별 사용률·포화·오류를 보는 점검법)으로 CPU·메모리·디스크·네트워크를 봅니다.

```bash
uptime                      # load average 추이
vmstat 1 5                  # r(실행 대기), si/so(스왑), wa(I/O 대기)
iostat -xz 1 3              # 디스크 사용률·대기 시간 (sysstat 패키지)
free -m                     # 메모리·스왑
ss -s                       # 소켓 상태 요약
ss -tan state time-wait | wc -l
journalctl -u nginx --since "30 min ago" | tail -n 50
```

4. 애플리케이션·의존성 확인: 응답 시간을 구간별로 나눕니다(프록시 → 앱 → DB → 외부 API).

```bash
curl -o /dev/null -s -w 'dns=%{time_namelookup} connect=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/
```

5. 가설 검증: "DB 쿼리가 느려졌다"면 느린 쿼리 로그와 연결 수를 보고, 한 가지만 바꿔 효과를 확인합니다.
6. 마무리: 재발 방지 알림 조건과 런북 수정을 언급합니다.

### 자주 나오는 트러블슈팅 질문

| 질문                                         | 답변에 들어가면 좋은 확인 지점                                   |
|----------------------------------------------|------------------------------------------------------------------|
| 디스크가 100%인데 지운 뒤에도 공간이 안 생김 | 삭제됐지만 열린 파일(`lsof +L1`), 예약 블록, inode 고갈(`df -i`) |
| SSH 접속이 안 됨                             | 네트워크 도달성, 방화벽, sshd 상태, 인증 로그, 디스크 가득 참    |
| 서버 load average가 높은데 CPU는 한가함      | I/O 대기(D 상태 프로세스), NFS 지연, 스토리지 장애               |
| 특정 도메인만 접속 안 됨                     | DNS 조회(`dig`), TTL과 캐시, 인증서 만료, 경로 문제              |
| 메모리가 부족해 프로세스가 죽음              | OOM killer 로그(`dmesg`, `journalctl -k`), cgroup 제한           |
| 배포 후 오류율 증가                          | 되돌리기 판단 기준, 카나리 비교, 설정·의존성 차이                |

🟡 주의: 면접 답변에서도 운영 서버에서 바로 `kill -9`, 서비스 재시작, 파일 삭제를 말하기 전에 영향 범위와 증거 보존(로그·코어 덤프)을 먼저 언급하는 것이 좋습니다.

## 3. 기초 지식 질문

기초 질문은 "무엇인가"보다 "왜 그렇게 동작하는가"를 묻는 경우가 많습니다. 답변은 정의 한 문장 → 동작 원리 → 운영에서 의미 순서로 구성합니다.

| 영역     | 자주 나오는 질문                                               | 운영과 연결할 점            |
|----------|----------------------------------------------------------------|-----------------------------|
| Linux    | 프로세스와 스레드 차이, 좀비 프로세스, 시그널, 부팅 과정       | 장애 시 프로세스 상태 해석  |
| Linux    | 파일 권한·소유자, 하드 링크와 심볼릭 링크, inode               | 디스크·권한 장애 진단       |
| 메모리   | 페이지 캐시, 스왑, OOM killer                                  | "free가 적다"는 오해 구분   |
| 네트워크 | TCP와 UDP, 3-way handshake, TIME_WAIT, MTU                     | 연결 수 증가·패킷 손실 진단 |
| 네트워크 | DNS 조회 순서, 재귀·권한 서버, TTL                             | 도메인 변경 반영 지연 설명  |
| 웹       | HTTP 상태 코드 계열, keep-alive, TLS 핸드셰이크, 리버스 프록시 | 502·504 구분                |
| 스토리지 | RAID 수준별 차이, LVM, 파일 시스템 저널링                      | 디스크 교체·확장 절차       |
| 보안     | 최소 권한, SSH 키 인증, 방화벽 기본 정책                       | 접근 통제 설계              |

### "브라우저에 주소를 입력하면 무슨 일이 일어나나요"

범위가 넓은 대표 질문입니다. 공개 저장소 `alex/what-happens-when`이 이 질문을 단계별로 자세히 풀어 둡니다. 면접에서는 모두 말하려 하지 말고 다음 뼈대를 말한 뒤 면접관이 관심을 보이는 단계로 깊이 들어갑니다.

```text
URL parse -> DNS lookup (cache, resolver) -> TCP connect
-> TLS handshake -> HTTP request -> load balancer / proxy
-> application -> database / cache -> HTTP response -> render
```

인프라 직무라면 DNS 캐시 계층, TLS 인증서 검증, 로드밸런서 상태 검사, 프록시 시간 제한 같은 운영 지점을 강조합니다.

## 4. 설계 질문

설계 질문은 정답보다 진행 방식이 중요합니다.

### 진행 순서

1. 요구 조건 확인: 사용자 수, 요청량, 데이터 양, 가용성 목표, 예산, 운영 인력
2. 수치 추정: 초당 요청 수, 하루 저장량, 보존 기간에 따른 총량
3. 기본 구조 제시: 단순한 구조부터 그리고 병목을 찾음
4. 장애 시나리오: 서버 한 대, 가용 영역 하나, 의존 서비스 하나가 실패하면?
5. 운영 항목: 모니터링, 백업·복구, 배포, 비용
6. 장단점 정리: 선택하지 않은 대안과 이유

### 수치 추정 예

"하루 100GB 로그를 30일 보관"이라면 다음처럼 말로 계산을 보여 줍니다.

```text
100 GB/day x 30 days = 3,000 GB (about 3 TB) raw
replica x2           = about 6 TB
compression ratio    = depends on data (measure, do not assume)
peak ingest          = 100 GB / 86,400 s = about 1.2 MB/s average
                       (plan for peak, not average)
```

압축률처럼 데이터에 따라 크게 달라지는 값은 단정하지 말고 "측정해서 정하겠다"고 말하는 편이 낫습니다. 저장소의 [100GB 로그 수집 설계](../../02_infrastructure/data_pipeline/log_aggregation_100gb.md)가 실제 예시로 참고가 됩니다.

### 자주 나오는 설계 주제

| 주제               | 다룰 요소                                             |
|--------------------|-------------------------------------------------------|
| 웹 서비스 고가용성 | 로드밸런서, 상태 검사, 세션 저장 위치, 다중 가용 영역 |
| 로그·지표 수집     | 수집기, 버퍼(큐), 저장소, 보존 정책, 조회 비용        |
| 백업·복구          | RPO·RTO, 3-2-1 원칙, 복구 훈련                        |
| 배포 파이프라인    | 빌드·테스트·승인·배포, 되돌리기, 카나리               |
| 다중 리전          | 데이터 복제 방식, 장애 전환, 비용                     |

RPO(Recovery Point Objective)는 허용 가능한 데이터 손실 시점, RTO(Recovery Time Objective)는 허용 가능한 복구 시간입니다.

## 5. 경험 질문

경험 질문은 STAR 구조(Situation·Task·Action·Result)로 정리하면 말이 길어지지 않습니다. 인프라 직무에서는 결과 뒤에 배운 점과 재발 방지(Learning)를 덧붙이면 좋습니다.

| 단계      | 담을 내용                    | 예                                   |
|-----------|------------------------------|--------------------------------------|
| Situation | 배경과 규모                  | 서비스 서버 40대, 야간 배포 중 장애  |
| Task      | 내가 맡은 역할               | 당직자로 원인 파악과 복구 담당       |
| Action    | 내가 한 판단과 행동, 그 근거 | 오류율 확인 후 직전 배포 되돌림 결정 |
| Result    | 측정 가능한 결과             | 20분 안에 복구, 영향 요청 비율 기록  |
| Learning  | 바꾼 절차·도구               | 배포 전 설정 검증 단계 추가          |

### 미리 준비할 이야기

- 가장 어려웠던 장애와 그때의 판단
- 반복 작업을 자동화한 사례와 줄어든 시간
- 동료·다른 팀과 의견이 달랐을 때 조율한 사례
- 실수한 경험과 이후 바꾼 점
- 새 기술을 짧은 기간에 익혀 적용한 사례

🟡 주의: 이전 회사의 내부 주소, 고객 이름, 보안 설정 같은 비공개 정보는 면접에서도 말하지 않습니다. 규모와 구조만 일반화해서 설명합니다.

## 6. 실기·과제 대비

실기는 화면 공유로 명령을 치거나, 고장 난 환경을 받아 복구하거나, 과제를 제출하는 형식이 많습니다.

### 손에 익혀 둘 것

| 분야        | 연습할 내용                                              |
|-------------|----------------------------------------------------------|
| 텍스트 처리 | `grep`, `awk`, `sort`, `uniq -c`, `cut`으로 로그 집계    |
| 셸 스크립트 | 인자 처리, 종료 코드, `set -euo pipefail`, 함수          |
| 서비스 관리 | `systemctl status`, `journalctl -u`, 유닛 파일 작성      |
| 네트워크    | `ss`, `ip`, `dig`, `curl -v`, `tcpdump` 기본 필터        |
| 컨테이너    | 이미지 빌드, 로그 확인, 포트·볼륨 연결                   |
| IaC         | 작은 Terraform·Ansible 코드 작성과 `plan`·`--check` 확인 |

로그 집계 예시입니다. 웹 서버 접근 로그에서 상태 코드별 건수를 셉니다(기본 combined 형식에서 9번째 필드가 상태 코드).

```bash
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head
```

과제형이라면 다음을 함께 제출하면 평가에 도움이 됩니다.

- README: 실행 방법, 가정, 선택하지 않은 대안
- 테스트 또는 검증 방법
- 시간이 더 있었다면 할 일

공개 연습 자료로는 `bregman-arie/devops-exercises`(질문·실습 모음)와 `donnemartin/system-design-primer`(설계 학습 자료)가 있습니다. devops-exercises README는 질문 대부분이 실제 면접을 나타내지 않는다고 밝히므로 학습용으로만 씁니다.

## 7. 준비 계획과 점검표

### 4주 준비 예시

| 주차 | 집중 내용                                                |
|------|----------------------------------------------------------|
| 1주  | Linux·네트워크 기초 다시 보기, 개념을 말로 설명하는 연습 |
| 2주  | 트러블슈팅 시나리오 10개를 직접 재현하고 확인 명령 정리  |
| 3주  | 설계 주제 3~4개를 그림과 수치 추정으로 정리              |
| 4주  | 경험 이야기 5개를 STAR로 정리, 모의 면접으로 시간 맞추기 |

트러블슈팅 재현은 가상 머신이나 컨테이너에서 디스크 채우기, 서비스 설정 오류, DNS 오류처럼 안전하게 만들 수 있는 장애로 합니다.

🟡 주의: 장애 재현 연습은 개인 실습 환경에서만 합니다. 회사·공용 서버에서 부하를 만들거나 서비스를 멈추지 않습니다.

### 면접 전 점검표

- [ ] 지원 직무 설명의 기술 스택을 내 경험과 연결해 정리했다
- [ ] 이력서에 적은 기술마다 "왜 썼는가, 대안은 무엇이었나"를 답할 수 있다
- [ ] 트러블슈팅 답변 틀(범위 확인 → 영향 완화 → 관찰 → 가설 → 확인 → 후속 조치)을 말로 연습했다
- [ ] 설계 질문에서 요구 조건을 먼저 묻는 습관을 들였다
- [ ] 경험 이야기 5개를 2~3분 분량으로 정리했다
- [ ] 비공개 정보를 빼고 일반화한 표현으로 바꿨다
- [ ] 면접관에게 할 질문(당직 체계, 장애 회고 문화, 자동화 수준)을 준비했다

### 면접관에게 할 만한 질문

- 당직(on-call) 주기와 호출 빈도는 어느 정도인가요
- 장애 후 회고는 어떤 방식으로 진행하나요
- 인프라 변경은 어떤 검토·승인 절차를 거치나요
- 수작업으로 남아 있는 운영 업무는 무엇인가요

관련 기준은 저장소의 [당직 설계](../../03_engineering/reliability/oncall_design.md)와 [포스트모템 프레임워크](../../03_engineering/reliability/postmortem_framework.md)에서 볼 수 있습니다.
