# Codex 공통 개념과 사용 흐름
<!-- reference: _reference/codex_cli_official_notes.md -->

Codex는 코드를 읽고 수정하며, 허용된 도구로 명령과 테스트를 실행하는 OpenAI의 코딩 에이전트입니다. 사용자는 원하는 결과를 설명하고, Codex는 그 결과에 필요한 작업을 진행합니다.

이 문서는 Codex를 처음 접하는 사람이 **무엇을 맡길 수 있는지, 어떻게 작업하는지, 결과를 어떻게 확인하는지** 배우기 위한 입문 문서입니다. Git의 저장소·변경 사항 개념과 터미널에서 명령을 실행하는 방법을 알면 예시를 이해하기 쉽습니다.

예시에서는 공백이 포함된 파일 경로를 처리하지 못하는 가상의 셸 스크립트를 고칩니다. 설치 방법과 명령어 목록은 각 사용 가이드에서 다룹니다.

## 1. 모델·에이전트·도구의 차이

Codex를 이해하려면 판단하는 **모델**, 작업을 이어가는 **에이전트**, 실제 행동을 수행하는 **도구**를 구분하면 됩니다.

| 구성 요소 | 역할                                          | 파일 경로 오류를 고칠 때의 예시              |
|-----------|-----------------------------------------------|----------------------------------------------|
| 모델      | 입력을 해석하고 원인·다음 행동을 판단         | 변수에 따옴표가 없어 경로가 나뉘었다고 추론  |
| 에이전트  | 목표에 맞춰 모델 판단과 도구 사용을 반복      | 코드 읽기 → 수정 → 테스트 → 결과 보고를 진행 |
| 도구      | 파일 읽기·수정, 명령 실행 등 실제 행동을 수행 | 스크립트를 읽고 테스트 명령을 실행           |

Codex는 모델을 사용하는 에이전트입니다. **모델 이름을 고르는 일**과 **Codex의 파일·명령 접근을 설정하는 일**은 서로 다른 선택입니다. 모델이 수정 방법을 알아도 실행 도구나 권한이 없으면 파일을 바꿀 수 없습니다.

사용자는 목표와 완료 기준을 정합니다. 예를 들어 “공백이 있는 경로도 정상적으로 검사하되 기존 출력 형식은 유지한다”라고 정하면, Codex는 그 기준에 맞춰 수정하고 검증할 수 있습니다.

## 2. 사용 화면과 실행 위치

CLI·IDE·GUI는 사용자가 Codex와 소통하는 화면입니다. 익숙한 작업 방식에 따라 시작점을 선택할 수 있습니다.

| 사용 방식                   | 어울리는 상황                            | 다음 문서                                    |
|-----------------------------|------------------------------------------|----------------------------------------------|
| CLI: 터미널의 대화형 화면   | 셸 스크립트 수정, 저장소 탐색, 명령 실행 | [CLI Linux 가이드](codex_cli_linux_guide.md) |
| IDE: 코드 편집기의 확장     | 열린 코드 설명, 선택한 코드 수정·리뷰    | [IDE 가이드](codex_ide_guide.md)             |
| GUI: 웹·데스크톱 화면       | 자료 조사, 계획과 작업 진행 상황 확인    | [GUI 가이드](codex_gui_guide.md)             |
| 자동화: 비대화형 CLI·SDK 등 | CI 검사, 반복 작업, 내부 도구 연동       | [API·자동화 가이드](codex_api_guide.md)      |

**사용 화면과 코드가 실행되는 위치는 별개입니다.** 내 노트북에서 CLI를 실행하면 노트북의 작업공간을 사용하고, SSH로 접속한 개발서버에서 CLI를 실행하면 그 서버의 작업공간을 사용합니다. 모델을 호출하는 서비스와 셸 명령이 실행되는 호스트도 구분해야 합니다.

Codex Cloud는 원격의 격리된 환경에서 저장소와 도구를 준비해 작업합니다. CLI에서 cloud 작업을 시작할 수도 있으므로, “터미널이면 항상 로컬 작업”이라고 판단하지 않습니다. 원격 환경에는 내 PC의 미커밋 변경이나 설치된 도구가 자동으로 동일하게 준비된다고 가정할 수 없습니다. ([공식 Cloud 설명](https://learn.chatgpt.com/docs/cloud))

## 3. 한 작업이 진행되는 과정

다음은 코드 수정 작업의 일반적인 흐름입니다. 모든 요청에서 수정이나 테스트가 필요한 것은 아니며, 코드 설명만 요청하면 읽기와 설명으로 끝날 수 있습니다.

```text
Request -> Read -> Edit -> Test -> Report -> Human review
                   ^        |
                   +--------+ (if tests fail)
```

1. **요청 이해**: “공백이 있는 경로에서 실패한다”는 증상과 기대 동작을 확인합니다.
2. **읽기와 원인 분석**: 관련 스크립트·저장소 규칙·테스트를 읽고 오류를 재현합니다. 재현 환경이 없으면 그 한계를 먼저 드러냅니다.
3. **수정**: 원인으로 확인된 부분을 바꾸고 기존 동작을 유지합니다.
4. **검증**: 공백이 있는 경로와 기존 정상 경로를 검사합니다. 실패하면 원인을 다시 확인하고 수정합니다.
5. **보고와 사람의 검토**: 변경 파일, 수정 이유, 실제 실행한 검사와 결과를 보고합니다. 사용자는 변경 내용을 검토해 반영 여부를 결정합니다.

예시의 원인이 인수의 따옴표 누락이었다면, 수정 전후는 다음처럼 표현할 수 있습니다. `$1`은 스크립트에 전달한 첫 번째 인수이며, `"$1"`은 공백을 포함한 경로를 하나의 인수로 유지합니다.

```diff
-[ -f $1 ]
+[ -f "$1" ]
```

여기서 `git diff`는 수정 전후의 차이입니다. Codex의 설명과 함께 diff를 읽으면 “원인만 고쳤는가”, “출력 형식도 바뀌었는가”를 확인할 수 있습니다. 테스트는 기대 동작을 확인하는 수단이고, diff 검토는 의도하지 않은 변경을 찾는 수단입니다.

## 4. 요청과 컨텍스트

**컨텍스트**는 Codex가 판단할 때 참고하는 정보입니다. 현재 요청과 대화, 읽은 코드, 오류 로그, 도구 실행 결과 등이 여기에 해당합니다. 파일이 저장소에 존재한다는 것과 Codex가 그 파일의 내용을 이미 읽었다는 것은 다릅니다. 관련 경로와 재현 방법을 알려주면 필요한 정보를 찾기 쉬워집니다.

“스크립트 고쳐줘”만으로는 어떤 동작이 잘못됐는지 알기 어렵습니다. 다음처럼 **현재 문제 → 기대 결과 → 제약 → 검증**을 적으면 수정 방향이 구체적으로 정해집니다. 경로와 파일명은 학습용 가정입니다.

> `scripts/check_file.sh`를 수정해 주세요.
>
> 현재 문제: `bash scripts/check_file.sh "fixtures/sample data.txt"`로 존재하는 파일을 검사하면 실패합니다. 공백이 없는 경로는 정상입니다.
>
> 기대 결과: 공백이 포함된 경로도 파일 존재 여부를 올바르게 검사해야 합니다.
>
> 제약: 기존 출력 메시지와 종료 코드의 의미를 유지해 주세요.
>
> 검증: 공백이 있는 경로, 없는 경로, 존재하지 않는 파일을 확인하고 실제 실행한 명령과 결과를 알려 주세요.

이 요청에서 재현 명령은 **출발점**, 기대 결과는 **완료 기준**, 제약은 **기존 동작을 지킬 범위**입니다. 오류 로그를 제공할 때는 비밀정보를 제거하고, 긴 파일은 관련 위치를 함께 짚어 줍니다. ([공식 요청 작성 설명](https://learn.chatgpt.com/docs/prompting))

큰 개발 요청에는 [AI 개발 요청 템플릿](ai_development_request_template.md)의 환경·요구사항·테스트 항목을 사용합니다. 작은 수정은 위 예시처럼 필요한 항목만 적어도 됩니다.

긴 대화에서는 앞선 내용이 요약될 수 있습니다. 이후에도 유지해야 하는 요구사항과 결정은 저장소 문서나 이슈에 기록하면 다른 세션에서도 다시 확인할 수 있습니다.

## 5. 설정과 확장 기능

### 5.1. 개인 설정과 프로젝트 설정

CLI의 설정 파일은 기본적으로 **현재 OS 사용자 계정의** `~/.codex/config.toml`입니다. `~`는 그 계정의 홈 디렉토리입니다. ChatGPT 계정별 폴더라는 뜻은 아닙니다. `CODEX_HOME`을 지정한 환경에서는 기본 저장 위치가 달라집니다.

| 설정 범위        | 위치 또는 방법                | 사용하는 이유                      |
|------------------|-------------------------------|------------------------------------|
| 사용자 기본 설정 | `~/.codex/config.toml`        | 여러 저장소에서 사용할 개인 기본값 |
| 프로젝트 설정    | 저장소의 `.codex/config.toml` | 해당 프로젝트의 실행 설정          |
| 이번 실행의 설정 | CLI 옵션·설정 재정의          | 기본값을 바꾸지 않고 한 번 적용    |

프로젝트 설정은 신뢰한 프로젝트에서 로드됩니다. 적용 값은 설정의 우선순위와 조직의 강제 정책에도 영향을 받습니다. 홈 디렉토리 경로만 보고 실제 적용 값을 단정하지 않고, 상세 규칙은 [CLI 설정 설명](codex_cli_linux_guide.md#7-설정과-agentsmd)에서 확인합니다. ChatGPT 웹이 내 PC의 설정 파일을 자동으로 읽는 것도 아닙니다.

### 5.2. AGENTS.md·Skills·MCP의 차이

세 기능은 각각 **반복 규칙**, **재사용 절차**, **외부 연결**을 담당합니다.

| 기능        | 무엇을 제공하는가                          | 사용 예시                                           |
|-------------|--------------------------------------------|-----------------------------------------------------|
| `AGENTS.md` | 사용자·저장소·하위 디렉토리의 작업 지침    | “셸 스크립트 변경 후 프로젝트 검사 명령을 실행한다” |
| Skills      | 특정 작업의 절차와 참고 자료를 묶은 패키지 | 문서 검토 순서와 확인 항목을 반복 사용              |
| MCP         | 외부 도구·자료에 접근하는 연결 규약        | OpenAI 공식 문서를 검색하고 가져오기                |

매번 요청에 적는 팀 규칙은 `AGENTS.md`에, 여러 단계의 반복 작업은 Skill에 정리할 수 있습니다. Skills는 이름·설명으로 발견하고 선택한 Skill의 본문을 읽습니다. MCP가 제공하는 기능은 서버마다 다릅니다. 공식 문서 검색 서버와 파일을 변경하는 서버는 권한과 동작이 다릅니다.

처음에는 요청과 저장소 코드만으로 작은 작업을 해 보고, 반복해서 필요한 지침이나 외부 자료가 생겼을 때 확장하면 됩니다. `AGENTS.md`에 “수정하라”고 적는 것만으로 파일 접근 권한이 생기지는 않습니다.

### 5.3. 여러 작업을 나누는 기능

**Subagent**는 주 에이전트가 나눈 작업을 맡는 별도 에이전트입니다. 예를 들어 구현과 독립적인 코드 리뷰를 분담할 수 있습니다. 별도 컨텍스트와 모델·도구 호출을 사용하므로 총 사용량은 늘 수 있습니다. 분담 요청은 지시문에 명시하며, 실제 지원 여부는 사용하는 환경에서 확인합니다.

**Git worktree**는 한 저장소에 별도의 작업 디렉토리를 만드는 Git 기능입니다. 여러 작업이 같은 파일을 동시에 덮어쓰는 문제를 줄이는 데 도움이 됩니다. 나중에 결과를 합칠 때의 충돌까지 없애 주지는 않습니다. 작은 단일 파일 수정에는 먼저 한 세션으로 작업 흐름을 익히는 편이 이해하기 쉽습니다.

## 6. 권한·로그인·비용

세 항목은 서로 다른 질문에 답합니다. **로그인 성공은 모든 파일을 수정할 수 있다는 뜻이 아닙니다.**

| 항목        | 확인할 질문                                     | 예시                                       |
|-------------|-------------------------------------------------|--------------------------------------------|
| 권한        | 어떤 파일·명령·네트워크에 접근할 수 있는가?     | 스크립트는 읽을 수 있지만 수정은 제한됨    |
| 로그인·인증 | 어떤 계정이나 자격증명으로 서비스를 사용하는가? | ChatGPT 로그인 또는 API 인증               |
| 사용량·비용 | 어떤 이용 한도나 청구 체계가 적용되는가?        | ChatGPT 플랜 사용량 또는 Platform API 과금 |

**샌드박스**는 명령이 접근할 수 있는 파일·네트워크 등의 범위를 제한합니다. **승인 정책**은 그 범위를 넘는 작업 등에 대해 승인을 요청할지 정합니다. CLI의 대표적인 샌드박스 모드는 다음과 같습니다.

| 모드                 | 이해할 핵심                                     | 어울리는 작업                       |
|----------------------|-------------------------------------------------|-------------------------------------|
| `read-only`          | 파일 쓰기를 제한하며, 읽기와 허용된 명령을 실행 | 코드 설명·조사                      |
| `workspace-write`    | 작업공간의 허용된 범위에서 파일 수정            | 코드 수정·테스트                    |
| `danger-full-access` | Codex의 명령 샌드박스 제한을 해제               | 별도 격리·통제가 준비된 환경의 작업 |

예를 들어 읽기 전용에서는 오류 원인과 수정안을 설명할 수 있어도 파일 수정은 제한됩니다. 승인 정책 `never`는 승인 요청을 하지 않는다는 뜻이며, 샌드박스 제한을 해제하지 않습니다. 실제 허용 범위에는 OS 권한과 관리 정책도 영향을 줍니다.

ChatGPT 로그인으로 사용하는 Codex와 Platform API의 과금·이용 한도를 서로 대신한다고 가정하지 않습니다. API key나 `auth.json` 같은 인증정보는 비밀번호처럼 취급하고 저장소·프롬프트·로그에 넣지 않습니다. 인증 방식별 적용 범위는 [공식 인증 설명](https://learn.chatgpt.com/docs/auth)에서 확인합니다.

[⬆ 목차로 돌아가기](#목차)

## 7. 결과 확인과 한계

Codex가 “수정했습니다”라고 보고하면, 먼저 **변경 내용이 목표에 맞는지**와 **실제로 무엇을 검증했는지** 확인합니다.

| 확인 대상          | 파일 경로 예시에서 볼 내용               | 확인하는 이유                              |
|--------------------|------------------------------------------|--------------------------------------------|
| 변경 파일과 diff   | 경로 처리에 필요한 부분이 바뀌었는가?    | 요청과 무관한 변경을 찾기 위해             |
| 실행한 검사와 결과 | 공백 포함·미포함·없는 파일을 확인했는가? | 원래 오류와 기존 동작을 함께 확인하기 위해 |
| 미실행 검사와 이유 | 필요한 도구가 없어 검사를 못 했는가?     | 아직 확인되지 않은 범위를 알기 위해        |

“테스트를 실행하세요”라는 제안과 “이 명령을 실행했고 통과했습니다”라는 결과는 다릅니다. 테스트에 성공해도 검사하지 않은 환경과 입력에서 문제가 남을 수 있습니다. 특히 개발서버와 운영서버의 셸·의존성이 다르면 해당 환경의 검증이 추가로 필요합니다.

처음 실습할 때는 `git status`로 기존 변경을 확인하고 작은 수정 하나를 요청합니다. 완료 후 diff와 실행 결과를 읽어 보고, 기존에 다른 사람이 작성한 변경이 섞여 있다면 함께 구분해 검토합니다. 커밋·PR·배포는 그 결과를 프로젝트에 반영하는 별도 단계입니다.

권한의 더 자세한 원리는 [AI 에이전트 샌드박스 개념](../../04_security/hardening/ai_agent_sandbox_concepts.md)에서 배울 수 있습니다.

## 8. 추천 학습 순서

| 단계 | 학습·실습 내용                                   | 읽을 문서                                                                                       |
|------|--------------------------------------------------|-------------------------------------------------------------------------------------------------|
| 1    | 모델·에이전트·도구, 작업 흐름을 설명해 보기      | 이 문서의 1~4절                                                                                 |
| 2    | 익숙한 화면에서 코드 설명과 작은 수정 한 번 진행 | [CLI](codex_cli_linux_guide.md) · [IDE](codex_ide_guide.md) · [GUI](codex_gui_guide.md) 중 하나 |
| 3    | 기대 결과와 검증 기준이 있는 요청 작성           | [AI 개발 요청 템플릿](ai_development_request_template.md)                                       |
| 4    | 개인·프로젝트 설정과 접근 권한 이해              | 이 문서의 5~7절과 CLI 설정 설명                                                                 |
| 5    | 반복 작업이 생기면 자동화 방식 학습              | [API·자동화 가이드](codex_api_guide.md)                                                         |

다음 질문에 답할 수 있으면 공통 개념을 이해한 것입니다.

- 읽기 전용 환경에서 수정 요청을 했을 때 파일을 바꾸지 못하는 이유는 무엇인가요?
- 개발서버에서 실행한 CLI가 사용하는 홈 디렉토리와 작업공간은 어디인가요?
- 팀의 반복 규칙을 전달할 때와 외부 문서를 검색할 때는 각각 어떤 기능이 필요한가요?

답을 확인하려면 각각 6절, 2·5절, 5절을 다시 읽습니다. 기능의 세부 동작과 제공 여부는 Codex 버전·계정·조직 정책에 따라 달라질 수 있으므로, 실제 설정 시에는 공식 문서와 사용하는 화면을 함께 확인합니다.
