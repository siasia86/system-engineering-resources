# 엔지니어를 위한 기술 문서 작성

시스템 엔지니어가 쓰는 문서(런북, 작업 계획서, 장애 보고, 설계 문서, README)를 읽는 사람이 바로 행동할 수 있게 쓰는 방법을 정리합니다. Google 기술 문서 작성 과정과 Diátaxis 문서 분류 틀을 바탕으로, 운영 문서에 맞춘 문장 규칙·구조·검토 점검표를 다룹니다.

## 1. 왜 문서 작성이 기술인가

운영 문서는 대개 급한 상황에서 읽힙니다. 새벽 장애 중에 런북을 여는 당직자, 처음 시스템을 맡은 후임자, 변경 승인을 검토하는 동료가 독자입니다. 이때 문서 품질은 복구 시간과 작업 실수에 직접 영향을 줍니다.

| 문서가 부족할 때 생기는 일  | 예                                       |
|-----------------------------|------------------------------------------|
| 같은 질문이 반복됨          | "이 서버 재시작해도 되나요"가 매번 나옴  |
| 작업자마다 절차가 다름      | 한 사람은 백업 후 작업, 다른 사람은 생략 |
| 장애 대응이 특정인에게 몰림 | 아는 사람이 휴가 중이면 복구 지연        |
| 변경 이유가 사라짐          | 1년 뒤 아무도 설정 값의 이유를 모름      |

Google은 엔지니어 대상 기술 문서 작성 과정(Technical Writing One·Two 등)을 공개하고 있으며, 이 문서의 문장 규칙은 그 과정에서 다루는 주제(능동태, 짧은 문장, 목록과 표, 독자 파악)를 운영 문서에 맞게 옮긴 것입니다.

## 2. 독자와 목적 정하기

쓰기 전에 세 가지를 한 줄씩 적습니다.

```text
Reader  : who reads this, what they already know
Goal    : what the reader can do after reading
Trigger : when they open this document
```

예를 들어 DB 장애 조치 런북이라면 다음과 같습니다.

- 독자: Linux와 기본 SQL을 아는 당직 엔지니어, 이 DB 구조는 모를 수 있음
- 목표: 기본 서버 장애 시 예비 서버로 전환하고 서비스를 확인할 수 있음
- 계기: "DB primary down" 알림을 받았을 때

독자를 정하면 생략할 것과 설명할 것이 정해집니다. 독자가 아는 내용(`ssh` 사용법)은 빼고, 모를 수 있는 내용(이 환경의 서버 이름 규칙, 전환 후 확인할 지표)은 씁니다.

### 지식의 저주 피하기

작성자는 시스템을 잘 알기 때문에 중간 단계를 건너뛰기 쉽습니다. 다음을 확인합니다.

- 약어와 사내 용어를 처음 쓸 때 풀어 썼는가
- "적절히 설정한다", "확인한다"처럼 무엇을 어떻게 하는지 빠진 문장이 없는가
- 전제 조건(권한, 접속 경로, 필요한 도구)을 맨 앞에 적었는가

## 3. 문서 유형 나누기

Diátaxis는 문서를 독자의 필요에 따라 네 가지로 나눕니다. 한 문서에 여러 목적을 섞으면 어느 독자에게도 맞지 않게 되므로, 유형을 먼저 정합니다.

| 유형         | 독자의 필요      | 운영 문서 예                     | 쓰는 방식                      |
|--------------|------------------|----------------------------------|--------------------------------|
| Tutorial     | 처음 배우기      | 신규 입사자 실습 안내            | 따라 하면 성공하는 하나의 경로 |
| How-to guide | 정해진 목표 달성 | 런북, 작업 절차서                | 목표 → 단계 → 확인             |
| Reference    | 정확한 사실 찾기 | 서버 목록, 포트 표, 설정 값 설명 | 표·목록, 설명 최소화           |
| Explanation  | 이유와 배경 이해 | 설계 문서, 아키텍처 결정 기록    | 맥락·대안·장단점               |

Diátaxis는 이 네 유형을 두 축으로 설명합니다. 행동을 돕는가(tutorial·how-to)와 이해를 돕는가(reference·explanation), 그리고 기술을 익히는 중인가(tutorial·explanation)와 쓰는 중인가(how-to·reference)입니다.

흔한 섞임과 고치는 방법입니다.

- 런북 중간에 긴 배경 설명이 있음 → 설명은 별도 문서로 옮기고 링크
- 설정 값 표에 절차가 섞임 → 표는 사실만, 절차는 how-to로 분리
- 설계 문서에 설치 명령이 길게 있음 → 설치는 how-to로 분리

설계 결정의 이유를 남기는 방법은 저장소의 [ADR 가이드](../03_engineering/delivery/adr_guide.md)를 참고합니다.

## 4. 문장 규칙

### 기본 규칙

| 규칙                  | 고치기 전                                   | 고친 후                                                     |
|-----------------------|---------------------------------------------|-------------------------------------------------------------|
| 주어와 행동을 분명히  | 백업이 확인되어야 합니다                    | 작업자는 백업 파일 크기와 생성 시각을 확인합니다            |
| 한 문장에 한 가지     | 서비스를 내리고 설정을 바꾸고 다시 올립니다 | 단계를 1, 2, 3으로 나눔                                     |
| 모호한 말 대신 기준   | 충분히 기다립니다                           | `systemctl is-active`가 `active`를 출력할 때까지 기다립니다 |
| 같은 대상은 같은 이름 | DB 서버, 디비, 데이터베이스 호스트 혼용     | 한 이름으로 통일하고 처음에 정의                            |
| 조건은 앞에           | 재시작합니다(단, 트래픽이 있으면 하지 않음) | 트래픽이 없을 때만 재시작합니다                             |

### 목록과 표

- 순서가 있는 작업은 번호 목록, 순서가 없는 항목은 글머리표를 씁니다.
- 같은 속성을 여러 대상에 비교할 때는 표를 씁니다.
- 목록 항목은 같은 문장 형태로 맞춥니다(모두 명령형이거나 모두 명사형).

### 경고 표시

위험한 단계는 그 단계 바로 앞에 경고를 둡니다. 문서 끝에 모아 두면 작업자가 이미 실행한 뒤에 읽게 됩니다.

```text
Bad : 3. Run the cleanup script.  ...  (Note at bottom: step 3 deletes data)
Good: 3. WARNING: this deletes files older than 7 days. Check the path first.
         Run the cleanup script.
```

## 5. 운영 문서 양식

### 런북

```markdown
# <서비스> <상황> 대응

- 대상 알림: <알림 이름>
- 영향: <사용자에게 보이는 증상>
- 필요한 권한: <계정·역할>
- 마지막 검증일: YYYY-MM-DD

## 1. 상황 확인
## 2. 영향 줄이기
## 3. 원인별 조치
## 4. 복구 확인
## 5. 상위 보고 기준
```

런북에서 지킬 점입니다.

- 각 단계 뒤에 "기대 결과"를 적어 작업자가 다음 단계로 넘어가도 되는지 판단하게 합니다.
- 분기 조건(이 경우 A, 아니면 B)을 명시합니다.
- 언제 다른 사람을 불러야 하는지(상위 보고 기준)를 적습니다.

### 작업 계획서(변경 계획)

| 항목        | 내용                             |
|-------------|----------------------------------|
| 목적        | 왜 바꾸는가                      |
| 대상과 범위 | 서버·서비스·시간대               |
| 사전 확인   | 백업, 현재 상태 기록, 승인       |
| 작업 단계   | 번호 목록, 단계별 기대 결과      |
| 확인 방법   | 성공 판정 기준                   |
| 되돌리기    | 실패 판단 기준과 원복 절차       |
| 연락처      | 작업자, 승인자, 영향 서비스 담당 |

변경 관리 전체 흐름은 [변경 관리](../03_engineering/delivery/change_management.md)를 참고합니다.

### 장애 보고

장애 보고는 사실과 추정을 나누고 시간순으로 씁니다. 개인을 탓하는 표현 대신 시스템과 절차의 빈틈을 적습니다. 양식은 [포스트모템 프레임워크](../03_engineering/reliability/postmortem_framework.md)를 따릅니다.

### README

저장소 README는 처음 온 사람이 5분 안에 다음을 알 수 있게 씁니다.

1. 무엇을 하는 저장소인가
2. 어떻게 실행·배포하는가
3. 어디에 무엇이 있는가
4. 누구에게 물어야 하는가

## 6. 명령과 예시 쓰기

### 복사해서 실행할 수 있게

- 프롬프트 기호(`$`, `#`)를 명령 앞에 붙이지 않습니다. 복사할 때 함께 붙여 넣어집니다.
- 바꿔야 하는 값은 `<SERVER_NAME>`처럼 눈에 띄는 자리 표시자로 쓰고, 바로 아래에 무엇을 넣는지 설명합니다.
- 명령과 출력은 다른 코드 블록으로 나눕니다.
- 실행 위치(어느 서버, 어느 사용자)를 명령 위에 적습니다.

```bash
# 실행 위치: 대상 웹 서버, sudo 권한 사용자
sudo systemctl reload nginx
systemctl is-active nginx
```

기대 출력:

```text
active
```

### 자격증명과 내부 정보

- 비밀번호·토큰·키는 문서에 쓰지 않습니다. 저장 위치(비밀 관리 도구의 경로)만 적습니다.
- 공개 문서의 예시 주소는 문서용으로 예약된 값을 씁니다. 도메인은 `example.com`([RFC 2606](https://www.rfc-editor.org/rfc/rfc2606)), IPv4는 `192.0.2.0/24`·`198.51.100.0/24`·`203.0.113.0/24`([RFC 5737](https://www.rfc-editor.org/rfc/rfc5737))입니다.

### 파괴적 명령

🟡 주의: 삭제·초기화·재시작 명령에는 실행 전 확인 단계를 함께 씁니다.

```bash
# 1. 지울 대상 먼저 확인 (삭제하지 않음)
find /var/log/app -name '*.log' -mtime +7 -print

# 2. 목록이 맞을 때만 삭제
find /var/log/app -name '*.log' -mtime +7 -delete
```

## 7. 검토와 유지 관리

### 작성자 자체 점검표

- [ ] 첫 문단만 읽어도 문서의 목적과 독자를 알 수 있다
- [ ] 문서 유형(tutorial·how-to·reference·explanation)이 하나로 정해져 있다
- [ ] 전제 조건과 필요한 권한을 앞에 적었다
- [ ] 모든 단계에 기대 결과 또는 확인 방법이 있다
- [ ] 위험한 단계 바로 앞에 경고가 있다
- [ ] 약어를 처음 쓸 때 풀어 썼다
- [ ] 명령은 복사해서 실행할 수 있고 자리 표시자가 구분된다
- [ ] 자격증명·내부 주소·개인 정보가 없다
- [ ] 링크가 동작한다

### 다른 사람에게 검토받기

가장 효과적인 검토는 문서를 처음 보는 사람이 그대로 따라 해 보는 것입니다. 검토자가 멈추거나 질문한 지점이 고칠 곳입니다. 런북이라면 장애 훈련 때 실제로 사용해 보고 고칩니다.

### 낡은 문서 관리

| 방법                      | 내용                                               |
|---------------------------|----------------------------------------------------|
| 마지막 검증일 표시        | 문서 머리에 실제로 따라 해 본 날짜를 적음          |
| 담당자 지정               | 문서마다 갱신 책임자를 둠                          |
| 변경과 함께 갱신          | 시스템 변경 작업 계획에 "관련 문서 갱신" 단계 포함 |
| 정기 점검                 | 분기마다 오래된 문서 목록을 뽑아 확인·폐기         |
| 문서 코드화(docs as code) | 문서를 저장소에 두고 코드처럼 검토·이력 관리       |

문서 저장소에 링크 검사와 Markdown 형식 검사를 자동화하면 깨진 링크를 줄일 수 있습니다.
