# 분산 시스템 기초 개념

## 1. 분산 시스템이 어려운 이유

분산 시스템(distributed system)은 메시지를 주고받는 여러 프로세스가 하나의 서비스처럼 동작하는 구조입니다. Lamport는 1978년 논문에서 "메시지 전송 지연이 한 프로세스 안의 사건 간격에 비해 무시할 수 없을 때" 시스템을 분산 시스템으로 본다고 정의했습니다.

단일 서버와 달리 다음 세 가지를 동시에 고려해야 합니다.

| 문제      | 단일 서버                 | 분산 시스템                                         |
|-----------|---------------------------|-----------------------------------------------------|
| 부분 장애 | 전체가 살아 있거나 죽음   | 일부 노드만 죽거나 느려지고, 살았는지 판별이 어려움 |
| 네트워크  | 프로세스 간 통신이 메모리 | 패킷 손실·지연·순서 바뀜·분할(partition)이 발생     |
| 시간      | 하나의 시계               | 노드마다 시계가 다르고 NTP로 맞춰도 오차가 남음     |

응답이 없는 노드가 죽었는지, 느린지, 네트워크만 끊겼는지는 밖에서 구분할 수 없습니다. 그래서 분산 시스템은 타임아웃으로 "죽었다고 간주"하고, 그 판단이 틀렸을 때도 데이터가 깨지지 않도록 설계합니다.

```text
Client --> Node A --x--> Node B      (A cannot tell)
                                     - B crashed?
                                     - B is slow (GC pause, disk stall)?
                                     - link A-B is broken (partition)?
```

## 2. 장애 모델

장애 모델(failure model)은 시스템이 어떤 종류의 고장을 견디도록 설계되었는지 정하는 전제입니다.

| 모델                    | 의미                               | 예시                            |
|-------------------------|------------------------------------|---------------------------------|
| 크래시-중단(crash-stop) | 노드가 멈추면 다시 돌아오지 않음   | 이론 모델                       |
| 크래시-복구             | 멈췄다가 디스크의 상태로 재시작    | 대부분의 DB·etcd 노드           |
| 누락(omission)          | 메시지 일부를 잃음                 | 패킷 손실, 큐 넘침              |
| 비잔틴(Byzantine)       | 임의로 잘못된 값을 보냄(버그·악의) | 블록체인, 신뢰할 수 없는 참여자 |

etcd·Raft·Kafka KRaft 같은 일반적인 인프라 합의 시스템은 크래시-복구 모델을 전제로 하며 비잔틴 장애는 견디지 않습니다. 디스크 손상이나 메모리 비트 오류처럼 "틀린 값을 그대로 보내는" 장애는 체크섬·백업으로 따로 막아야 합니다.

## 3. CAP 정리

CAP는 Eric Brewer가 2000년 PODC 기조연설에서 제시한 추측이며, 2002년 Seth Gilbert와 Nancy Lynch가 비동기 네트워크 모델에서 증명했습니다.

| 문자 | 속성                           | 뜻                                                    |
|------|--------------------------------|-------------------------------------------------------|
| C    | 일관성(Consistency)            | 모든 읽기가 가장 최근 쓰기를 봄(선형화 가능성에 해당) |
| A    | 가용성(Availability)           | 장애가 아닌 모든 노드가 모든 요청에 응답              |
| P    | 분할 내성(Partition tolerance) | 노드 사이 메시지가 사라져도 시스템이 동작             |

흔히 "셋 중 둘을 고른다"고 요약하지만, 실제 의미는 다음과 같습니다.

- 네트워크 분할은 고를 수 있는 선택지가 아니라 일어나는 사건입니다.
- 분할이 일어난 동안에만 C와 A 중 하나를 포기해야 합니다.
- 분할이 없을 때는 C와 A를 함께 제공할 수 있습니다.

```text
          partition
 [A] [B]  ||||||||  [C]

 CP choice: minority side (C) rejects writes -> consistent, not available
 AP choice: both sides accept writes        -> available, may diverge
```

🟡 CAP의 C는 ACID의 C(제약 조건 유지)와 다른 개념입니다. 문서나 제품 소개에서 "일관성"이라는 단어가 어느 쪽을 뜻하는지 먼저 확인합니다.

## 4. PACELC

Daniel Abadi는 2012년 IEEE Computer 논문에서 CAP가 "장애 때"만 다룬다는 점을 지적하고, 평상시의 지연(latency)과 일관성 사이 트레이드오프를 더한 PACELC를 제안했습니다.

```text
if Partition:  choose Availability  or Consistency   (PA / PC)
Else:          choose Latency       or Consistency   (EL / EC)
```

평상시에도 동기 복제로 모든 복제본의 확인을 기다리면 일관성은 높아지지만 응답이 느려집니다. 논문은 다음처럼 분류했습니다.

| 분류  | 논문의 예시                       | 동작                                     |
|-------|-----------------------------------|------------------------------------------|
| PA/EL | Dynamo, Cassandra, Riak 기본 설정 | 분할 때 가용성, 평상시 낮은 지연 우선    |
| PC/EC | VoltDB/H-Store, Megastore         | 분할·평상시 모두 일관성 우선             |
| PA/EC | MongoDB(논문 당시 분석)           | 평상시 일관성, 분할 때 가용성 쪽 동작    |
| PC/EL | PNUTS                             | 평상시 지연 우선, 분할 때 일관성 쪽 동작 |

분류는 2012년 논문 시점의 기본 설정 기준입니다. 현재 제품은 설정(복제 계수, 일관성 수준, write concern)에 따라 위치가 바뀌므로 운영 중인 설정으로 다시 판단합니다.

## 5. 일관성 모델

일관성 모델(consistency model)은 "동시에 여러 클라이언트가 읽고 쓸 때 어떤 결과를 허용하는가"를 정한 규칙입니다. 강한 모델일수록 프로그래밍이 쉽고, 약한 모델일수록 가용성·지연에 유리합니다.

| 모델                             | 보장 내용                                                                                  | 분할 중 가용성    |
|----------------------------------|--------------------------------------------------------------------------------------------|-------------------|
| 선형화 가능성(linearizable)      | 각 연산이 호출과 응답 사이 한 시점에 원자적으로 일어난 것처럼 보이고 실제 시간 순서를 지킴 | 전체 가용 불가    |
| 순차 일관성(sequential)          | 모든 프로세스가 같은 전체 순서를 보지만 실제 시간 순서는 무관                              | 전체 가용 불가    |
| 인과 일관성(causal)              | 원인-결과 관계가 있는 쓰기는 모두 같은 순서로 보임                                         | 세션 고정 시 가능 |
| 자기 쓰기 읽기(read-your-writes) | 자신이 쓴 값은 이후 자기 읽기에서 보임                                                     | 세션 고정 시 가능 |
| 단조 읽기(monotonic reads)       | 한 번 본 값보다 오래된 값을 다시 보지 않음                                                 | 가능              |
| 최종 일관성(eventual)            | 쓰기가 멈추면 언젠가 모든 복제본이 같은 값으로 수렴                                        | 가능              |

가용성 열은 Jepsen 분류를 따릅니다. "전체 가용 불가"는 네트워크 분할 중 일부 노드가 진행할 수 없다는 뜻이고, "세션 고정 시 가능"(sticky available)은 클라이언트가 같은 서버에 계속 붙어 있으면 분할 중에도 진행할 수 있다는 뜻입니다. Jepsen은 선형화 가능성을 "단일 객체에서 가장 강한 모델 중 하나"로 설명합니다.

실무에서 자주 만나는 증상과 원인 모델은 다음과 같습니다.

| 증상                                  | 빠진 보장          |
|---------------------------------------|--------------------|
| 글을 쓰고 새로고침하니 글이 안 보임   | read-your-writes   |
| 새로고침할 때마다 값이 앞뒤로 바뀜    | monotonic reads    |
| 댓글이 원글보다 먼저 보임             | causal             |
| 두 관리자가 동시에 같은 리소스를 획득 | linearizable(잠금) |

분산 잠금(lock)이나 리더 선출처럼 "하나만 성공해야 하는" 작업은 선형화 가능한 저장소(etcd, ZooKeeper 등)에 맡기고, 캐시·조회 수처럼 약간 늦어도 되는 데이터는 최종 일관성 저장소를 씁니다.

## 6. 복제 방식

복제(replication)는 같은 데이터를 여러 노드에 두는 것입니다. 목적은 내구성(데이터 보존), 가용성(장애 중 서비스), 읽기 확장입니다.

| 방식                       | 구조                             | 장점                  | 주의점                            |
|----------------------------|----------------------------------|-----------------------|-----------------------------------|
| 단일 리더(primary-replica) | 리더만 쓰기, 팔로워가 복제       | 쓰기 순서가 단순      | 리더 장애 시 전환(failover) 필요  |
| 다중 리더(multi-leader)    | 여러 리더가 쓰기, 서로 복제      | 지역별 낮은 쓰기 지연 | 쓰기 충돌 해결 규칙 필요          |
| 리더 없음(leaderless)      | 클라이언트가 여러 노드에 직접 씀 | 노드 장애에 강함      | 쿼럼·읽기 복구·안티 엔트로피 필요 |

동기와 비동기의 차이도 함께 봅니다.

```text
synchronous:   client -> leader -> replica ack -> leader ack -> client
               (no data loss on leader crash, higher latency)

asynchronous:  client -> leader ack -> client ; leader -> replica later
               (low latency, recent writes may be lost on failover)
```

비동기 복제에서 리더가 죽고 팔로워를 승격하면, 아직 복제되지 않은 마지막 쓰기는 사라집니다. 이 손실 허용 범위가 RPO(Recovery Point Objective, 허용 데이터 손실 시점)입니다. DB 복제의 실제 설정은 [RDBMS 복제](../../05_database/operations/rdbms_replication.md)를 함께 봅니다.

🟡 두 노드가 동시에 자신을 리더로 믿는 상태를 스플릿 브레인(split brain)이라 합니다. 쿼럼 없이 "상대가 응답하지 않으면 내가 리더"로 동작하는 2노드 구성에서 자주 생기므로 펜싱(fencing, 이전 리더의 쓰기 차단)이나 세 번째 투표자를 둡니다.

## 7. 쿼럼

쿼럼(quorum)은 결정을 내리는 데 필요한 최소 투표 수입니다. 과반수 쿼럼은 `floor(N/2) + 1`이며, 두 과반수 집합은 반드시 한 노드 이상 겹치므로 서로 모순된 결정을 막습니다.

etcd FAQ가 제시하는 클러스터 크기별 과반수와 장애 허용 수는 다음과 같습니다.

| 클러스터 크기 | 과반수 | 장애 허용 수 |
|---------------|--------|--------------|
| 1             | 1      | 0            |
| 2             | 2      | 0            |
| 3             | 2      | 1            |
| 4             | 3      | 1            |
| 5             | 3      | 2            |
| 6             | 4      | 2            |
| 7             | 4      | 3            |

짝수 크기는 같은 장애 허용 수에 노드만 하나 더 쓰므로 etcd 문서는 홀수 크기를 권장합니다. 2노드는 1노드보다 장애에 약합니다(둘 다 살아 있어야 과반수).

리더 없는 저장소에서는 복제 계수 N, 쓰기 확인 수 W, 읽기 응답 수 R을 고릅니다.

```text
N = 3 replicas
W + R > N  ->  read set and write set overlap  -> read sees latest write
W = 2, R = 2 : overlap guaranteed (quorum read/write)
W = 1, R = 1 : fast, may read stale data
```

`W + R > N`은 겹침을 보장할 뿐이며, 동시 쓰기 충돌·시계 기반 최종 쓰기 승리(last-write-wins) 같은 다른 요인 때문에 선형화 가능성까지 보장하지는 않습니다.

## 8. 합의 알고리즘 Raft

합의(consensus)는 여러 서버가 하나의 값(또는 명령 순서)에 동의하고, 한 번 결정된 값은 바뀌지 않게 하는 문제입니다. Raft는 Diego Ongaro와 John Ousterhout가 2014년 USENIX ATC에 발표한 알고리즘으로, 이해하기 쉬운 구조를 목표로 설계되었습니다. etcd와 Kafka KRaft 컨트롤러가 Raft 계열 방식을 씁니다.

### 8.1 상태와 임기

각 서버는 팔로워(follower), 후보(candidate), 리더(leader) 중 하나입니다. 시간은 임기(term)라는 번호로 나뉘며, 한 임기에는 리더가 최대 하나입니다.

```text
          timeout, start election         receives majority votes
follower ---------------------> candidate ------------------------> leader
   ^                                |                                  |
   |   discovers current leader     |                                  |
   +--------------------------------+                                  |
   +------------------- discovers higher term -------------------------+
```

### 8.2 리더 선출과 로그 복제

1. 팔로워는 리더의 하트비트(heartbeat)를 일정 시간 못 받으면 임기를 올리고 후보가 됩니다.
2. 후보는 다른 서버에 투표를 요청하고 과반수를 얻으면 리더가 됩니다.
3. 선거 타임아웃은 고정 구간에서 무작위로 고르며, 논문은 예로 150–300ms를 제시합니다. 무작위화로 동시에 여러 후보가 나와 표가 갈리는 상황을 줄입니다.
4. 리더는 클라이언트 명령을 로그에 붙이고 팔로워에 복제합니다. 과반수 서버에 저장된 항목은 커밋(commit)된 것으로 봅니다.
5. 선거 제한(election restriction): 후보의 로그가 과반수 서버의 로그만큼 최신이어야 투표를 받으므로, 커밋된 항목은 리더가 바뀌어도 사라지지 않습니다.

### 8.3 타이밍 조건

논문은 다음 관계가 성립해야 안정적으로 리더를 유지한다고 설명합니다.

```text
broadcastTime  <<  electionTimeout  <<  MTBF
(0.5ms - 20ms)     (10ms - 500ms)       (months)
```

etcd는 이를 하트비트 간격과 선거 타임아웃 설정으로 노출합니다.

| etcd 플래그            | 기본값 | 문서 권장                             |
|------------------------|--------|---------------------------------------|
| `--heartbeat-interval` | 100ms  | 멤버 간 RTT의 0.5~1.5배 정도          |
| `--election-timeout`   | 1000ms | 멤버 간 RTT의 10배 이상, 최대 50000ms |

모든 멤버가 같은 값을 써야 합니다. 디스크 fsync가 느리면 하트비트가 밀려 불필요한 리더 교체가 일어나므로, 지역 간 클러스터나 느린 스토리지에서는 이 값을 먼저 확인합니다.

## 9. 논리 시계와 순서

노드마다 물리 시계가 다르므로 "어느 사건이 먼저인가"를 타임스탬프만으로 판단하면 틀릴 수 있습니다. Lamport는 1978년 논문(Communications of the ACM 21권 7호)에서 "먼저 일어남(happened-before)" 관계와 논리 시계를 정의했습니다.

- 같은 프로세스 안에서 a가 b보다 앞서면 a → b입니다.
- a가 메시지 송신이고 b가 그 메시지 수신이면 a → b입니다.
- 둘 다 아니면 두 사건은 동시(concurrent)입니다.

논리 시계 구현 규칙은 두 가지입니다.

```text
IR1: each process increments its counter between any two successive events
IR2: send     -> attach own counter T to the message
     receive  -> counter = max(own counter, T) + 1
```

이 규칙을 지키면 "a → b이면 C(a) < C(b)"가 성립합니다. 반대 방향(C(a) < C(b)이면 a → b)은 보장하지 않으므로, 동시 쓰기를 판별해야 하는 저장소는 노드별 카운터 배열인 벡터 시계(vector clock)를 씁니다.

운영 관점의 결론은 다음과 같습니다.

- 로그를 여러 서버에서 모아 시간순으로 정렬해도 실제 인과 순서와 다를 수 있습니다. 요청 ID·트레이스 ID로 묶어 봅니다.
- 시계 기반 "최종 쓰기 승리"는 시계가 앞선 노드의 쓰기가 나중 쓰기를 덮어쓸 수 있습니다. NTP 상태를 감시합니다.

## 10. 운영에서 보는 지표와 명령

etcd 클러스터를 예로 들면, 아래 명령으로 멤버 상태와 리더를 확인합니다(`etcdctl` v3 API 기준, 인증서 옵션은 환경에 맞게 추가).

```bash
# 각 멤버의 리더 여부, Raft 임기(term), 인덱스, DB 크기를 표로 확인
etcdctl --endpoints=https://192.0.2.11:2379,https://192.0.2.12:2379,https://192.0.2.13:2379 \
  endpoint status -w table

# 각 엔드포인트가 요청에 응답하는지 확인
etcdctl --endpoints=https://192.0.2.11:2379,https://192.0.2.12:2379,https://192.0.2.13:2379 \
  endpoint health

# 멤버 목록
etcdctl --endpoints=https://192.0.2.11:2379 member list -w table
```

| 관찰 항목                | 정상 기준           | 이상 신호의 의미                            |
|--------------------------|---------------------|---------------------------------------------|
| 리더 수                  | 정확히 1            | 0이면 과반수 상실, 쓰기 불가                |
| Raft 임기 증가 속도      | 장애·작업 때만 증가 | 자주 오르면 리더 교체 반복(디스크·네트워크) |
| 멤버 간 Raft 인덱스 차이 | 작고 곧 따라잡음    | 계속 벌어지면 느린 팔로워                   |
| 디스크 fsync 지연        | 낮고 안정적         | 하트비트 지연, 선거 유발                    |

🟡 과반수를 잃은 클러스터에서 멤버를 강제로 제거하거나 스냅숏에서 새 클러스터를 만드는 작업은 데이터 손실 위험이 있습니다. 공식 재해 복구 절차와 최신 백업을 확인한 뒤 수행합니다.
