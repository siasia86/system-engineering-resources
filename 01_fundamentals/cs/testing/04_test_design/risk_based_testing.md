# 위험 기반 테스트 (Risk-Based Testing)
<!-- reference: _reference/software_testing_official_notes.md -->

위험 기반 테스트(Risk-Based Testing)는 실패했을 때의 영향과 실패 가능성을 기준으로 테스트 범위·우선순위·깊이를 결정하는 접근 방식입니다. 모든 기능을 같은 강도로 검증하기보다 제한된 시간과 자원을 위험이 큰 영역에 먼저 배분합니다.

## 1. 개요

테스트 위험은 결함이 발생하거나 발견되지 않아 기대한 결과를 얻지 못할 가능성과 그 영향으로 구성합니다.

| 구분        | 질문                                                     |
|-------------|----------------------------------------------------------|
| 발생 가능성 | 해당 영역에서 결함이 발생할 가능성이 어느 정도인가?      |
| 영향도      | 결함이 발생하면 사용자·데이터·운영에 어떤 영향이 있는가? |
| 발견 난이도 | 다른 테스트나 운영 모니터링으로 발견하기 어려운가?       |
| 변경 위험   | 최근 변경량·복잡도·의존성이 큰 영역인가?                 |

위험 기반 테스트는 테스트를 생략하기 위한 근거가 아니라, **검증 순서와 검증 깊이를 결정하기 위한 근거**입니다.

## 2. 위험 식별

### 위험의 출처

| 출처      | 위험 예시                                |
|-----------|------------------------------------------|
| 요구사항  | 모호한 규칙, 누락된 예외, 상충하는 조건  |
| 변경      | 신규 기능, 리팩터링, 데이터 마이그레이션 |
| 복잡도    | 조건 조합, 상태 전이, 동시성             |
| 의존성    | 외부 API, DB, 파일 시스템, 메시지 큐     |
| 데이터    | 개인정보, 금전·재화, 대량·오래된 데이터  |
| 운영 환경 | 권한, 네트워크, 용량, 배포·복구          |
| 과거 결함 | 재발 결함, 반복 장애, 미해결 위험        |

### 위험 문장 작성

위험은 “기능이 중요합니다”처럼 작성하지 않고, 원인과 결과가 드러나는 문장으로 구체화합니다.

```text
[원인] 인증 토큰 갱신과 요청 처리의 순서가 어긋남
[결함] 만료된 토큰이 정상 요청으로 처리되거나 정상 세션이 종료됨
[영향] 사용자 접근 실패와 세션 데이터 불일치 발생
```

## 3. 위험 평가

### 평가 항목

| 항목        | 낮음                          | 중간                      | 높음                                |
|-------------|-------------------------------|---------------------------|-------------------------------------|
| 영향도      | 일부 기능 불편                | 특정 사용자·업무 영향     | 데이터·보안·금전·핵심 서비스 영향   |
| 발생 가능성 | 변경 없음·단순 로직           | 일반적인 변경·의존성 존재 | 복잡한 변경·반복 결함·불안정 의존성 |
| 발견 난이도 | 즉시 오류나 모니터링으로 발견 | 통합·회귀 테스트에서 발견 | 운영 후 특정 조건에서만 발견        |

팀에서 사용하는 위험 등급의 정의는 프로젝트 기준으로 고정하고, 평가자가 달라도 같은 의미로 해석되도록 합니다.

### 위험 목록 예시

| 위험 ID | 대상          | 원인                         | 영향도 | 가능성 | 우선순위 |
|---------|---------------|------------------------------|--------|--------|----------|
| RSK-001 | 인증 상태     | 갱신 경로의 순서 경쟁        | 높음   | 중간   | P1       |
| RSK-002 | 검색 결과     | 특수 입력과 인코딩 처리 누락 | 중간   | 중간   | P2       |
| RSK-003 | 관리자 보고서 | 대량 데이터 처리 시간 증가   | 중간   | 낮음   | P3       |

위험 등급을 계산하는 단일 공식보다, 영향도·가능성·발견 난이도와 판단 근거를 함께 기록하는 것이 중요합니다.

## 4. 테스트 우선순위

### 위험에서 테스트로 변환

```text
위험 식별
   │
   v
위험 평가와 우선순위 지정
   │
   v
필수 테스트 케이스 선정
   │
   v
추가 테스트·탐색 테스트·회귀 범위 결정
   │
   v
잔여 위험 기록
```

| 위험 수준 | 우선 테스트 범위                                 |
|-----------|--------------------------------------------------|
| 높음      | 정상·오류·경계·권한·복구·회귀·통합 테스트        |
| 중간      | 핵심 정상·오류·경계·변경 영향 범위               |
| 낮음      | 대표 정상 흐름·기본 회귀·자동화 가능한 최소 범위 |

우선순위가 낮은 영역도 완전히 배제하지 않습니다. 테스트하지 않은 영역과 그 근거를 잔여 위험으로 기록합니다.

### 테스트 자원 배분 시 고려 사항

- 결함의 영향이 큰 영역을 먼저 실행합니다.
- 변경된 코드와 의존성이 많은 경로를 우선 확인합니다.
- 자동화 테스트로 빠르게 확인할 수 있는 핵심 조건을 먼저 실행합니다.
- 발견 난이도가 높은 위험은 운영 전용 검증이나 탐색 테스트를 추가합니다.
- 테스트 종료 시점에 남은 위험과 수용 주체를 기록합니다.

## 5. 실행과 재평가

위험 평가는 테스트 시작 전에 한 번만 수행하지 않습니다.

| 시점          | 재평가 내용                              |
|---------------|------------------------------------------|
| 요구사항 변경 | 새 위험·조건·추적 항목 추가              |
| 코드 변경     | 변경 영향과 회귀 범위 재산정             |
| 테스트 실패   | 결함 영향도·재현성·재발 가능성 갱신      |
| 환경 변경     | 의존성·권한·데이터·성능 위험 재검토      |
| 릴리스 직전   | 미검증·미해결·수용된 잔여 위험 최종 확인 |

위험 목록과 테스트 결과가 서로 다른 상태를 가리키지 않도록 위험 ID를 테스트 케이스·결함·결정 기록에 함께 사용합니다.

## 6. 체크리스트

- [ ] 위험이 요구사항·변경·과거 결함·운영 환경에서 도출되었습니다.
- [ ] 각 위험에 원인·결함·영향이 기록되었습니다.
- [ ] 영향도·가능성·발견 난이도의 판단 근거가 있습니다.
- [ ] 위험 등급별 테스트 범위가 정의되었습니다.
- [ ] 높은 위험에 정상·오류·경계·복구 케이스가 포함되었습니다.
- [ ] 테스트 케이스와 위험 ID가 연결됩니다.
- [ ] 테스트하지 않은 영역과 그 사유가 잔여 위험으로 기록됩니다.
- [ ] 테스트 실패와 환경 변경 후 위험 평가가 갱신됩니다.
- [ ] 잔여 위험의 수용 주체와 결정 근거가 있습니다.
