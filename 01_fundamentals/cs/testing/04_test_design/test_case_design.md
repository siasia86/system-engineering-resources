# 테스트 케이스 설계 (Test Case Design)
<!-- reference: _reference/software_testing_official_notes.md -->

테스트 케이스(Test Case)는 특정 조건에서 시스템을 실행하고 결과를 판정하기 위한 검증 단위입니다. 테스트 케이스 설계는 요구사항과 위험을 실행 가능한 검증 절차로 변환하는 작업입니다.

## 1. 개요

테스트 케이스는 테스트 시나리오보다 구체적이며, 테스트 실행자가 동일한 조건에서 반복 실행할 수 있어야 합니다.

| 구분            | 의미                                          |
|-----------------|-----------------------------------------------|
| 테스트 시나리오 | 검증할 기능·업무 흐름을 상위 수준으로 표현    |
| 테스트 케이스   | 조건·절차·기대 결과를 포함한 실행 가능한 단위 |
| 테스트 스위트   | 목적이나 기능이 같은 테스트 케이스의 묶음     |
| 테스트 결과     | 실행 후 실제 결과와 판정 상태                 |

좋은 테스트 케이스는 구현 내부가 아니라 검증할 **관찰 가능한 동작**을 중심으로 작성합니다.

## 2. 구성 요소

| 요소          | 작성 내용                                         |
|---------------|---------------------------------------------------|
| ID            | 고유 식별자와 추적 가능한 명명 규칙               |
| 제목          | 검증 대상과 조건을 짧게 표현                      |
| 목적          | 이 케이스가 확인하는 요구사항·위험                |
| 우선순위      | 영향도·발생 가능성·변경 위험에 따른 실행 순서     |
| 사전 조건     | 실행 전에 만족해야 하는 환경·데이터·권한          |
| 입력 데이터   | 값·파일·요청·이벤트 등 실행에 사용하는 입력       |
| 실행 절차     | 실행자가 재현할 수 있는 순서와 동작               |
| 기대 결과     | 성공·실패·상태 변화·부수 효과의 판정 기준         |
| 사후 조건     | 실행 후 보장되어야 하는 데이터·상태               |
| 테스트 데이터 | 재사용 여부·격리·초기화 방법                      |
| 증적          | 로그·응답·스크린샷·리포트 등 결과를 입증하는 자료 |

기대 결과는 “정상 동작”처럼 모호하게 쓰지 않고, 상태·값·메시지·부수 효과를 관찰 가능한 표현으로 작성합니다.

## 3. 작성 절차

### 요구사항에서 테스트 케이스로 변환

```text
요구사항
   │
   v
검증 대상과 위험 식별
   │
   v
입력·상태·환경 조건 분류
   │
   v
테스트 시나리오 작성
   │
   v
구체적인 테스트 케이스와 기대 결과 작성
   │
   v
동료 검토와 추적성 확인
```

### 권장 순서

1. 요구사항에서 검증 가능한 문장과 제약 조건을 추출합니다.
2. 정상·오류·경계·예외 조건을 동등 분할합니다.
3. 상태 전이와 조건 조합이 있으면 별도 행으로 분리합니다.
4. 각 조건에 대해 입력·절차·기대 결과를 작성합니다.
5. 데이터 격리와 반복 실행 가능성을 확인합니다.
6. 요구사항 또는 위험 항목과 테스트 케이스 ID를 연결합니다.
7. 다른 사람이 문서만 보고 실행할 수 있는지 검토합니다.

경계값·동등 분할·결정 테이블·상태 전이 기법은 대상에 맞게 조합합니다.

## 4. 테스트 케이스 유형

| 유형             | 검증 관점                   | 예시                         |
|------------------|-----------------------------|------------------------------|
| 정상 케이스      | 유효한 입력의 기대 동작     | 유효한 자격증명으로 로그인   |
| 오류 케이스      | 잘못된 입력과 실패 처리     | 필수 필드 누락 시 오류 반환  |
| 경계 케이스      | 허용 범위 안팎의 값         | 최소값·최대값·범위 밖 값     |
| 예외 케이스      | 외부 장애·권한·리소스 제한  | 의존 서비스 응답 지연        |
| 상태 전이 케이스 | 상태와 이벤트 순서          | 초안 → 승인 → 취소           |
| 조합 케이스      | 여러 조건의 조합            | 권한·지역·계정 상태의 조합   |
| 회귀 케이스      | 변경으로 영향받은 기존 동작 | 수정된 결제 로직의 기존 흐름 |
| 비기능 케이스    | 성능·보안·호환성·접근성 등  | 응답 시간 목표와 오류율 검증 |

하나의 케이스에 너무 많은 목적을 넣지 않습니다. 서로 다른 판정 기준이나 실패 원인을 가지면 케이스를 분리합니다.

## 5. 품질 검토

### 체크리스트

- [ ] 테스트 케이스 ID가 중복되지 않습니다.
- [ ] 요구사항 또는 위험 항목과 연결됩니다.
- [ ] 사전 조건과 테스트 데이터가 재현 가능합니다.
- [ ] 실행 절차가 모호한 표현 없이 순서대로 작성됩니다.
- [ ] 기대 결과가 관찰 가능하고 판정 가능합니다.
- [ ] 정상·오류·경계 조건이 포함됩니다.
- [ ] 외부 의존성과 장애 조건이 필요한 범위에서 분리됩니다.
- [ ] 실행 후 데이터와 환경을 정리할 수 있습니다.
- [ ] 다른 케이스의 실행 결과에 의존하지 않습니다.
- [ ] 구현 세부사항에 과도하게 결합되지 않습니다.

### 자주 발생하는 문제

| 문제                        | 결과                           | 개선 방향                  |
|-----------------------------|--------------------------------|----------------------------|
| 기대 결과가 모호함          | 실행자마다 다른 판정           | 값·상태·메시지로 구체화    |
| 사전 조건 누락              | 재현 불가 또는 불필요한 실패   | 데이터·권한·환경 명시      |
| 정상 케이스만 존재          | 오류와 경계 결함을 놓침        | 오류·경계·복구 케이스 추가 |
| 케이스 간 상태 공유         | 실행 순서에 따라 결과가 달라짐 | 초기화·격리·정리 절차 추가 |
| 하나의 케이스가 과도하게 큼 | 원인 분석과 유지보수 어려움    | 검증 목적별로 분리         |
