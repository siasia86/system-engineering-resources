# 게임 테스트 케이스 설계 (Game Test Case Design)
<!-- reference: _reference/game_testing_official_notes.md -->

게임 테스트 케이스 설계는 게임 규칙·상태·플레이 흐름을 실행 가능한 검증 단위로 변환하는 작업입니다. 특정 엔진의 구현보다 게임 결과와 상태 정합성을 관찰하는 데 초점을 둡니다.

## 1. 개요

게임 테스트 케이스는 기능 결과뿐 아니라 게임 상태·규칙·플레이어 진행·저장 데이터의 변화를 검증합니다.

| 구분     | 검증 예시                               |
|----------|-----------------------------------------|
| 규칙     | 입력·조건·판정 결과의 일치              |
| 상태     | 게임방·캐릭터·퀘스트·세션 상태 전이     |
| 흐름     | 시작·진행·완료·실패·취소·복구           |
| 데이터   | 저장·불러오기·보상·재화·인벤토리 정합성 |
| 상호작용 | 입력·UI·네트워크·다른 플레이어 이벤트   |
| 비기능   | 로딩·응답·프레임·메모리·연결 안정성     |

게임 테스트 케이스는 클라이언트·서버·데이터의 관찰 위치를 사전 조건과 증적에 포함합니다.

[⬆ 목차로 돌아가기](#목차)

## 2. 구성 요소

| 요소        | 게임 테스트에서의 작성 내용              |
|-------------|------------------------------------------|
| 목표        | 규칙·상태·흐름 중 검증할 대상            |
| 초기 상태   | 계정·캐릭터·방·아이템·세션의 시작 상태   |
| 입력·이벤트 | 사용자 입력·시간·네트워크·서버 이벤트    |
| 실행 절차   | 재현 가능한 플레이·API·상태 조작 순서    |
| 기대 결과   | 화면·응답·상태·데이터·이벤트의 판정 기준 |
| 중단 조건   | 앱 종료·연결 끊김·세션 만료·외부 오류    |
| 복구 결과   | 재접속·재개·취소·롤백·중복 방지 결과     |
| 증적        | 로그·상태 덤프·요청 ID·리플레이·스크린샷 |

기대 결과는 “플레이가 정상입니다”가 아니라 검증할 상태와 관찰 위치를 구체적으로 적습니다.

[⬆ 목차로 돌아가기](#목차)

## 3. 설계 절차

1. 게임 규칙과 사용자 목표를 읽고 검증 대상을 정합니다.
2. 시작·중간·종료 상태와 허용 이벤트를 정의합니다.
3. 정상·대안·오류·중단·복구 흐름을 분리합니다.
4. 입력·권한·시간·네트워크·데이터 조건을 조합합니다.
5. 각 흐름을 실행 절차와 기대 결과가 있는 케이스로 변환합니다.
6. 동일 보상·재화·상태의 중복 처리와 순서 역전을 확인합니다.
7. 테스트 데이터·초기화·정리 방법을 정의합니다.
8. 규칙·상태·데이터·결함과 케이스 ID를 연결합니다.

### 케이스 예시

| ID      | 상황                    | 기대 결과                              |
|---------|-------------------------|----------------------------------------|
| GTC-001 | 정상 입력으로 규칙 실행 | 규칙 판정·상태·보상 결과 일치          |
| GTC-002 | 허용되지 않은 입력      | 입력 거부·오류 표시·상태 불변          |
| GTC-003 | 처리 중 연결 종료       | 재접속 후 중복·유실 없이 상태 복구     |
| GTC-004 | 동일 보상 요청 재전송   | 보상 중복 지급 없음·최종 상태 일관     |
| GTC-005 | 저장 중 앱 종료         | 재실행 후 저장 상태가 정책에 맞게 복구 |

## 4. 게임 특화 관점

### 상태와 오라클

게임의 화면만으로 상태를 판정하기 어려운 경우 다음 관찰 대상을 조합합니다.

- 클라이언트 표시와 서버 판정
- 세션·방·매치 상태
- 재화·보상·인벤토리 저장 결과
- 이벤트·로그·리플레이·리퀘스트 ID
- 재접속·재시작 후의 최종 상태

### 엔진 독립성

Unity Test Framework나 Firebase Game Loop 같은 도구는 특정 실행 환경의 검증 수단입니다. 게임 테스트 케이스의 규칙·오라클·정합성 원칙을 모든 엔진의 동일한 구현 방식으로 일반화하지 않습니다.

게임 서버 부하·프로토콜·실제 모바일 기기 테스트는 각각 부하·API·디바이스 테스트 문서와 함께 참조합니다.

## 5. 체크리스트

- [ ] 게임 규칙·초기 상태·종료 상태가 명확합니다.
- [ ] 정상·대안·오류·중단·복구 흐름이 포함됩니다.
- [ ] 상태 전이와 이벤트 순서가 검증됩니다.
- [ ] 재화·보상·인벤토리·저장 데이터의 정합성을 확인합니다.
- [ ] 중복 요청·재전송·재접속 조건을 포함합니다.
- [ ] 클라이언트 표시와 서버·데이터 판정을 구분합니다.
- [ ] 테스트 데이터와 초기화·정리 방법이 있습니다.
- [ ] 실패 재현에 필요한 로그·ID·상태 증적을 수집합니다.
- [ ] 특정 엔진 기능을 범용 게임 규칙으로 과장하지 않습니다.
