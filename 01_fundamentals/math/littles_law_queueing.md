# Little 법칙과 대기열 기초 — 용량 계획의 수학

동시 처리 수, 처리량, 응답 시간 사이의 관계를 나타내는 Little 법칙(L = λW)과 단순 대기열 모델을 정리합니다. 서버 스레드 수·커넥션 풀 크기를 정하거나 "사용률이 80%를 넘으면 왜 갑자기 느려지는가"를 설명할 때 쓰는 기초입니다.

## 1. 기호와 용어

| 기호 | 이름                      | 단위 예 | 운영 지표로 보면                           |
|------|---------------------------|---------|--------------------------------------------|
| λ    | 도착률(arrival rate)      | 요청/초 | 초당 요청 수(RPS), 초당 트랜잭션 수(TPS)   |
| X    | 처리량(throughput)        | 요청/초 | 안정 상태에서는 λ와 같음                   |
| W    | 시스템 체류 시간          | 초      | 응답 시간(대기 + 처리)                     |
| S    | 서비스 시간(service time) | 초      | 대기 없이 순수하게 처리에 걸리는 시간      |
| Wq   | 대기 시간                 | 초      | 큐에서 차례를 기다린 시간. W = Wq + S      |
| L    | 시스템 안 평균 개수       | 개      | 동시 처리 중 + 대기 중인 요청 수           |
| Lq   | 큐 안 평균 개수           | 개      | 대기 중인 요청 수                          |
| μ    | 서비스율                  | 요청/초 | 서버 하나가 초당 처리하는 수. μ = 1/S      |
| c    | 서버 수                   | 개      | 워커 스레드, 프로세스, CPU 코어, DB 커넥션 |
| ρ    | 사용률(utilization)       | 0~1     | 서버가 바쁜 시간 비율. ρ = λ / (c·μ)       |

**안정 상태(steady state)**: 일정 기간 동안 들어오는 양과 나가는 양이 평균적으로 같아 큐가 한없이 늘지 않는 상태입니다. 이 문서의 공식은 모두 안정 상태를 전제로 합니다. λ ≥ c·μ이면 안정 상태가 없고 큐는 계속 늘어납니다.

## 2. Little 법칙

```text
L = λ × W

L : average number of items in the system
λ : average arrival rate
W : average time an item spends in the system
```

John D. C. Little이 1961년 Operations Research에 증명을 발표했습니다. 이 법칙이 실무에서 유용한 이유는 조건이 적기 때문입니다.

| 성질                 | 의미                                                       |
|----------------------|------------------------------------------------------------|
| 분포에 무관          | 도착 간격이나 처리 시간이 어떤 분포든 장기 평균끼리는 성립 |
| 처리 순서에 무관     | FIFO, 우선순위, 라운드로빈 등 스케줄링 방식과 상관없음     |
| 경계를 마음대로 정함 | "시스템"을 큐만, 서버만, 전체 서비스로 잡아도 각각 성립    |
| 평균에 대한 법칙     | 백분위(p99 등)나 순간값에는 그대로 적용되지 않음           |

경계를 어디로 잡느냐에 따라 세 가지 형태로 씁니다.

| 경계        | 식          | 해석                                  |
|-------------|-------------|---------------------------------------|
| 시스템 전체 | L = λ · W   | 동시 요청 수 = RPS × 평균 응답 시간   |
| 큐만        | Lq = λ · Wq | 대기 중인 수 = RPS × 평균 대기 시간   |
| 서버만      | Ls = λ · S  | 처리 중인 수 = RPS × 평균 서비스 시간 |

서버만 경계로 잡은 식을 서버 수 c로 나누면 사용률이 됩니다: ρ = λ·S / c. 이것을 Utilization Law라고도 부릅니다.

## 3. 적용 예제

### 3.1 필요한 워커 수 추정

API 서버가 초당 400개의 요청을 받고, 요청 하나를 처리하는 평균 시간이 50ms입니다.

```text
Ls = λ × S = 400 req/s × 0.05 s = 20
```

평균적으로 20개의 요청이 동시에 처리 중입니다. 워커가 20개뿐이면 사용률이 100%가 되어 대기열이 계속 늘어납니다. 4절의 사용률 기준(예: 70% 이하)을 적용하면 20 / 0.7 ≈ 29개 이상이 필요합니다.

### 3.2 DB 커넥션 풀 크기

애플리케이션이 초당 1,200개의 쿼리를 보내고 평균 쿼리 시간이 4ms입니다.

```text
L = 1200 × 0.004 = 4.8 connections busy on average
```

평균 5개 정도의 커넥션이 쓰입니다. 풀을 수백 개로 잡아도 처리량은 늘지 않고, DB 쪽 경합만 늘 수 있습니다. 반대로 피크 λ가 3배가 되면 평균만으로도 14.4개가 필요하므로 피크 기준으로 계산해야 합니다.

### 3.3 측정값 교차 검증

모니터링에서 다음 값을 보았습니다.

| 지표              | 값    |
|-------------------|-------|
| 평균 RPS          | 250   |
| 평균 응답 시간    | 120ms |
| 평균 활성 연결 수 | 85    |

Little 법칙으로 기대하는 활성 수는 250 × 0.12 = 30입니다. 측정값 85와 크게 다르면 다음을 의심합니다.

- 응답 시간 지표가 서버 내부 처리만 재고, 클라이언트 연결 유지 시간(keep-alive, 느린 클라이언트 업로드)은 빠져 있음
- 활성 연결 수에 유휴 keep-alive 연결이 섞여 있음
- 측정 구간이 달라서 평균이 맞지 않음

이처럼 세 값 중 둘로 나머지 하나를 계산해 대시보드 지표의 정의가 서로 맞는지 점검할 수 있습니다.

## 4. 사용률과 대기 시간

Little 법칙은 세 값의 관계만 알려 주고, 사용률이 높아질 때 대기 시간이 얼마나 늘어나는지는 알려 주지 않습니다. 이를 보려면 대기열 모델이 필요합니다.

### 4.1 M/M/1 모델

Kendall 표기법 `A/B/c`에서 A는 도착 분포, B는 서비스 시간 분포, c는 서버 수입니다. M(Markovian)은 도착 간격·서비스 시간이 지수 분포임을 뜻합니다. M/M/1은 도착이 무작위(포아송 과정)이고 서버가 하나인 가장 단순한 모델입니다.

| 값        | 식                            |
|-----------|-------------------------------|
| 사용률    | ρ = λ / μ                     |
| 평균 개수 | L = ρ / (1 − ρ)               |
| 응답 시간 | W = 1 / (μ − λ) = S / (1 − ρ) |
| 대기 시간 | Wq = ρ · S / (1 − ρ)          |

L = λW를 넣어 보면 L = λ / (μ − λ) = ρ / (1 − ρ)로 서로 맞습니다.

### 4.2 사용률에 따른 응답 시간 배수

서비스 시간 S = 10ms인 M/M/1 서버에서 W = S / (1 − ρ)를 계산한 표입니다.

| 사용률 ρ | W / S | 응답 시간 W |
|----------|-------|-------------|
| 0.50     | 2     | 20ms        |
| 0.70     | 3.3   | 33ms        |
| 0.80     | 5     | 50ms        |
| 0.90     | 10    | 100ms       |
| 0.95     | 20    | 200ms       |
| 0.99     | 100   | 1,000ms     |

핵심은 곡선이 1에 가까워질수록 급격히 치솟는다는 점입니다. 사용률 80%에서 90%로 10%p만 올라가도 평균 응답 시간은 두 배가 됩니다. 그래서 운영에서는 평균 사용률에 여유(headroom)를 두고, 순간 피크에서도 ρ가 1에 닿지 않도록 계획합니다.

실제 시스템은 지수 분포를 정확히 따르지 않으므로 표의 숫자는 모양을 이해하는 용도로만 씁니다. 서비스 시간의 편차가 클수록(일부 요청만 매우 느림) 같은 사용률에서 대기 시간이 더 길어집니다.

## 5. 서버가 여러 개일 때

서버가 c개(M/M/c)이면 같은 사용률에서도 하나의 큐를 여러 서버가 나누어 처리하므로 대기 시간이 M/M/1보다 짧습니다.

| 구성                            | 특징                                                          |
|---------------------------------|---------------------------------------------------------------|
| 공유 큐 하나 + 서버 c개 (M/M/c) | 빈 서버가 바로 다음 요청을 가져감. 대기 시간이 가장 짧음      |
| 서버별 큐 c개 (M/M/1이 c개)     | 한 서버 큐가 밀려도 다른 서버가 놀 수 있음. 대기 시간이 더 김 |

운영 예:

- 로드밸런서의 round-robin은 서버별 큐에 가깝고, least-connections는 공유 큐에 조금 더 가까운 효과를 냅니다.
- 워커 풀이 하나의 작업 큐를 공유하면 서버별 큐보다 꼬리 지연이 줄어듭니다.

M/M/c의 대기 확률은 Erlang C 공식으로 계산합니다. 식이 길어 이 문서에서는 다루지 않으며, 필요하면 참고 자료의 대기열 이론 교재를 봅니다.

## 6. 측정값을 쓸 때 주의

| 주의점               | 설명                                                                        |
|----------------------|-----------------------------------------------------------------------------|
| 단위 맞추기          | λ가 초당이면 W도 초. ms를 그대로 곱하면 1,000배 틀림                        |
| 같은 경계, 같은 구간 | λ, W, L을 같은 시스템 경계와 같은 시간 구간에서 재야 함                     |
| 평균과 백분위        | Little 법칙은 평균에만 성립. p99 응답 시간을 넣어 L을 구하면 과대 추정      |
| 안정 상태 확인       | 장애 중처럼 큐가 계속 늘어나는 구간에서는 λ와 X가 다르므로 공식이 맞지 않음 |
| 실패한 요청          | 빠르게 실패한 요청(에러 응답)이 섞이면 평균 W가 낮아 보임                   |
| 측정 간격            | 1분 평균은 수 초짜리 버스트를 숨김. 피크 계획에는 짧은 간격 데이터가 필요   |

## 7. 용량 계획 절차

| 단계 | 할 일                                                         | 산출물                  |
|------|---------------------------------------------------------------|-------------------------|
| 1    | 피크 도착률 λ_peak 측정 또는 예측(이벤트, 계절성 포함)        | 피크 RPS                |
| 2    | 부하가 낮을 때의 평균 서비스 시간 S 측정                      | S (대기 없는 처리 시간) |
| 3    | 필요한 동시 처리 수 Ls = λ_peak × S                           | 평균 바쁜 서버 수       |
| 4    | 목표 사용률 ρ_target 선택(응답 시간 목표와 변동성에 따라)     | 예: 0.6~0.7             |
| 5    | 서버 수 c = Ls / ρ_target 올림                                | 워커·인스턴스 수        |
| 6    | 부하 시험으로 실제 W와 사용률 곡선 확인                       | 검증된 c                |
| 7    | 운영 중 λ, W, L을 함께 모니터링하고 L = λW로 지표 정합성 점검 | 대시보드                |

목표 사용률을 몇 %로 둘지는 정답이 없습니다. 응답 시간 목표가 엄격할수록, 서비스 시간 편차가 클수록, 장애 시 다른 서버 몫까지 받아야 할수록(N+1 구성) 낮게 잡습니다. 부하 시험 방법은 [performance_testing.md](../cs/testing/03_test_levels/performance_testing.md)를 봅니다.

## 8. 자주 하는 실수

| 실수                                  | 바른 이해                                                           |
|---------------------------------------|---------------------------------------------------------------------|
| 스레드를 늘리면 처리량이 계속 오른다  | 병목 자원(CPU, DB, 락)의 μ가 한계. 그 이상은 L과 W만 커짐           |
| 평균 사용률 50%면 여유가 충분하다     | 1분 평균 50% 안에 수 초간 100% 구간이 있을 수 있음                  |
| 응답 시간이 늘면 서버가 느려진 것이다 | 서비스 시간 S는 그대로이고 대기 Wq만 늘었을 수 있음. 둘을 나눠 측정 |
| L = λW를 p99에 적용한다               | 평균끼리만 성립                                                     |
| 타임아웃·재시도는 부하와 무관하다     | 재시도는 λ를 늘려 ρ를 더 올림. 혼잡할 때 재시도 폭주가 생길 수 있음 |
