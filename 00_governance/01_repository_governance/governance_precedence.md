# Repository Governance Precedence

저장소별 규칙과 전역 규칙이 충돌할 때 적용 순서를 정의합니다. 저장소마다 성격이
다르므로 전역 규칙만으로는 모든 저장소를 다룰 수 없고, 저장소별 규칙을 전역 실행
환경에 계속 추가하면 무관한 저장소 작업에서도 해당 규칙이 로드됩니다. 이 문서는
저장소별 규칙을 해당 저장소 안에 두고, 전역 규칙과의 적용 순서를 규정합니다.

## 1. 목적

저장소별 규칙이 저장소 밖에 흩어지는 문제를 해결합니다.

이 정책 도입 이전에는 같은 성격의 요구가 서로 다른 형태로 구현되었습니다.
Ansible 학습·자동화 저장소의 문서 예외는 이 저장소의 중앙 profile 문서로 관리되었고,
Zircon 저장소의 푸터 예외는 전역 skill로 관리되었습니다. 두 경우 모두 규칙이 적용될
저장소 안에는 규칙이 없었습니다.

이 구조는 다음 문제를 만듭니다.

- 저장소를 clone한 사람이 해당 저장소의 규칙을 알 수 없습니다.
- 저장소별 규칙이 전역 skill로 누적되면 무관한 세션에서도 컨텍스트를 소모합니다.
- 같은 종류의 규칙이 문서와 skill로 이원화되어 조회 위치가 일정하지 않습니다.

문서의 역할과 생명주기는 [Documentation Policy](documentation_policy.md)가 정의합니다.
이 문서는 규칙 출처가 충돌할 때의 적용 순서와 `.governance/`의 범위를 정의합니다.
따라서 문서 생성·갱신 방법은 `documentation_policy.md`를 따르고, 충돌하는 규칙의
선택은 이 문서의 우선순위 체계를 따릅니다.

## 2. 우선순위 체계

| 순위 | 출처                      | 적용 범위        | 지속성            |
|------|---------------------------|------------------|-------------------|
| 1    | 사용자의 명시적 지시      | 해당 세션        | 세션 종료 시 소멸 |
| 2    | repo-local `.governance/` | 해당 저장소      | 저장소에 영속     |
| 3    | 전역 skill                | 모든 저장소      | 실행 환경에 영속  |
| 4    | 기본 동작                 | 규칙이 없는 판단 | 해당 없음         |

```
사용자의 명시적 지시
       │  세션 한정, 근거 필요
       v
repo-local .governance/
       │  해당 저장소 범위
       v
전역 skill
       │  조직 공통 기본값
       v
기본 동작
```

### 적용 규칙

- 상위 순위가 하위 순위를 덮어씁니다.
- 사용자의 명시적 지시가 하위 규칙과 충돌하면 지시를 따르되, 어떤 규칙과 충돌하는지
  함께 알립니다.
- 사용자 지시는 해당 세션에만 적용합니다. 영속적인 변경이 필요하면 `.governance/`
  또는 전역 skill을 수정합니다.
- 하위 순위에만 규칙이 있으면 그 규칙을 그대로 적용합니다.
- 어느 순위에도 규칙이 없으면 기본 동작으로 처리하고, 반복되면 규칙으로 승격을 검토합니다.

### 사용자 지시를 최상위에 두는 이유

규칙은 통상적인 상황을 전제로 작성되며, 예외 상황을 모두 담지 못합니다. 규칙이
사용자 지시보다 우선하면 정당한 예외 작업이 차단되고, 규칙을 우회하려면 규칙 파일을
수정해야 합니다. 이는 일회성 예외를 영속 규칙으로 만드는 부작용을 낳습니다.

사용자 지시를 최상위에 두되 세션 한정으로 제한하면, 예외를 허용하면서도 규칙 자체는
보존됩니다.

## 3. 안전 예외

다음 항목은 우선순위와 무관하게 항상 확인 절차를 거칩니다. 사용자 지시나
`.governance/` 설정으로도 이 절차를 생략할 수 없습니다.

| 항목           | 확인 대상                                           |
|----------------|-----------------------------------------------------|
| 비가역 작업    | 데이터 삭제, 이력 재작성, force push, 프로덕션 반영 |
| 자격증명 취급  | 키·토큰·인증서의 조회·출력·전송·삭제                |
| 권한 변경      | 인증·인가·접근제어 정책 수정                        |
| 영향 범위 확대 | 재귀 삭제, 대량 수정, 공유 시스템 변경              |

확인 절차는 작업 내용, 예상 영향, 되돌리기 가능 여부를 제시하고 진행 여부를 확인하는
과정입니다. 사용자가 이미 승인한 작업을 다시 확인하지는 않으며, 승인 범위를 넘는
작업으로 확장될 때 다시 확인합니다.

🟡 안전 예외를 우선순위 밖에 두는 이유는 이 항목들의 실패 비용이 비대칭이기 때문입니다.
확인 절차를 한 번 더 거치는 비용은 작지만, 비가역 작업을 잘못 실행한 비용은 복구가
불가능합니다.

## 4. `.governance/` 구조

저장소 최상위에 `.governance/` 디렉토리를 둡니다.

```
<repository-root>/
├── .governance/
│   ├── GOVERNANCE.md      신규 저장소 필수 — 저장소 성격과 예외 요약
│   ├── ISSUE.md           신규 저장소 필수 — 이슈 기록
│   ├── TODO.md            신규 저장소 필수 — 미완료 작업
│   ├── PLAN.md            신규 저장소 필수 — 진행 중인 복합 작업
│   ├── exceptions.md      선택 — 예외 상세
│   └── verification.md    선택 — 저장소 전용 검증 명령
├── README.md
└── ...
```

| 파일              | 역할                              | 신규 저장소 | 기존 저장소 |
|-------------------|-----------------------------------|-------------|-------------|
| `GOVERNANCE.md`   | 저장소 성격, 적용 규칙, 예외 요약 | 필수        | 조건부      |
| `ISSUE.md`        | 이슈 기록                         | 필수        | 권장        |
| `TODO.md`         | 미완료 작업                       | 필수        | 권장        |
| `PLAN.md`         | 진행 중인 복합 작업               | 필수        | 권장        |
| `exceptions.md`   | 전역 규칙 대비 예외 상세          | 선택        | 선택        |
| `verification.md` | 저장소 전용 검증 명령             | 선택        | 선택        |

신규 저장소는 `GOVERNANCE.md`, `ISSUE.md`, `TODO.md`, `PLAN.md`를 기본으로 둡니다. 활성 항목이 없더라도 문서를 삭제하지 않고 상태를 명시합니다. 규칙과 검증 절차가 늘어나면 `exceptions.md`와 `verification.md`를 선택적으로 추가합니다.

기존 저장소는 루트 문서를 즉시 이동하지 않습니다. 해당 저장소의 다음 구조 변경이나 규칙 이관 시 `.governance/`로 이동하고, 기존 루트 문서는 legacy 호환 기간 후 제거합니다.

### 도구 중립 규칙과 도구 종속 자료

현재 디렉토리 구조를 다음 기준으로 분리합니다.

| 구분      | 판단 기준                                                  | 저장 위치                             |
|-----------|------------------------------------------------------------|---------------------------------------|
| 도구 중립 | 저장소 운영·문서 생명주기·검증처럼 실행 도구와 무관한 규칙 | `01_repository_governance/`           |
| 도구 종속 | 특정 에이전트의 Skill·Agent·Hook·설정·manifest             | 해당 도구 영역(`02_kiro/` 등)         |
| 혼합 내용 | 공통 원칙과 도구별 구현이 함께 필요한 내용                 | 원칙은 `01_`, 구현은 도구 영역에 분리 |

도구 중립 규칙을 도구 영역에 복사하지 않습니다. 도구 종속 자료가 공통 규칙을
설명해야 할 때는 원칙을 재정의하지 않고 공통 정책을 참조합니다. 반대로 특정 저장소의
도구 사용 예외는 해당 저장소의 `.governance/`에 기록하며, 도구 미러 영역에 저장소
규칙을 추가하지 않습니다.

각 파일은 템플릿을 사용해 작성합니다.

- `GOVERNANCE.md`: [GOVERNANCE 템플릿](templates/governance_template.md)
- `ISSUE.md`: [ISSUE 템플릿](templates/issue_template.md)
- `TODO.md`: [TODO 템플릿](templates/todo_template.md)
- `PLAN.md`: [PLAN 템플릿](templates/plan_template.md)
- `verification.md`: [VERIFICATION 템플릿](templates/verification_template.md)

### 디렉토리명을 `.governance/`로 정한 이유

- 특정 AI 도구 이름을 포함하지 않아 도구가 바뀌어도 유지됩니다.
- 저장소 최상위의 가시 파일 수를 늘리지 않습니다.
- 규칙이 늘어날 때 파일 분리로 대응할 수 있습니다.

숨김 디렉토리라 탐색 시 눈에 띄지 않으므로, 저장소 `README.md`에서 `.governance/`를
링크하여 발견성을 확보합니다.

### 전역 인식 방법

`.governance/`를 두어도 AI 실행 환경이 자동으로 읽지는 않습니다. 전역 skill에
탐색 지시를 등록하여 모든 세션이 동일하게 인식하도록 합니다.

```
전역 skill (저장소 1개당 추가 없음)
    │
    ├── 작업 대상 저장소 최상위에서 .governance/ 탐색
    ├── 존재하면 GOVERNANCE.md 를 먼저 읽음
    └── 전역 규칙보다 우선 적용 (사용자 지시보다는 하위)
```

이 방식은 저장소가 늘어도 전역 skill을 추가하지 않습니다. 저장소별 skill을 계속
등록하는 기존 방식과 달리 전역 컨텍스트 크기가 저장소 수에 비례하지 않습니다.

## 5. 예외 기술 범위

`.governance/`에는 전역 규칙 대비 **차이만** 기술합니다. 전역 규칙을 다시 쓰거나
전체를 재정의하지 않습니다.

| 기술 가능                         | 기술 불가                       |
|-----------------------------------|---------------------------------|
| 전역 규칙 중 특정 항목의 비활성화 | 전역 규칙 전체의 재정의         |
| 전역 규칙 값의 저장소별 조정      | 안전 예외 항목의 무력화         |
| 저장소 전용 검증 절차 추가        | 사용자 지시보다 우선한다는 선언 |
| 문서 역할·생명주기 예외           | 다른 저장소에 대한 규칙         |

### 기술 형식

전역 규칙 중 무엇을 어떻게 예외 처리하는지 명시합니다.

```markdown
## 적용 범위

이 정책은 다음 저장소 하위에만 적용합니다.

<repository-root>/**

## 유지하는 전역 규칙

- work-rules
- STYLE.md 표 정렬 규칙
- Git 커밋 규칙

## 저장소 전용 예외

전역 `readme-template` 규칙 중 푸터·통계 항목만 적용하지 않습니다.

- 통계 섹션
- 작성일, 마지막 업데이트
- 저작권 푸터

그 외 `readme-template` 규칙은 그대로 적용합니다.
```

유지하는 규칙을 명시적으로 나열하면, 예외가 의도한 범위를 넘는지 검토할 수 있습니다.
예외 항목만 적으면 나머지 규칙의 적용 여부가 불명확해집니다.

## 6. 적용 절차

### 새 저장소에 적용

1. 저장소 최상위에 `.governance/`를 생성합니다.
2. `GOVERNANCE.md`, `ISSUE.md`, `TODO.md`, `PLAN.md`를 템플릿으로 생성합니다.
3. 저장소 성격, 적용 범위와 저장소 전용 예외를 `GOVERNANCE.md`에 기술합니다.
4. 이슈·작업·계획이 없으면 각 문서에 해당 상태를 명시합니다.
5. 저장소 `README.md`에서 `.governance/`를 링크합니다.
6. 검증 명령을 실행하고 결과를 확인합니다.

### 기존 저장소 호환

기존 저장소의 루트 `ISSUE.md`, `TODO.md`, `PLAN.md`는 즉시 이동하지 않고 legacy 위치로 인식합니다. 새로 생성하는 문서는 `.governance/` 아래에 둡니다. 이관 시에는 링크·자동화·CI 탐색 경로를 함께 수정하고, 검증 후 기존 루트 문서를 제거합니다.

### 기존 저장소별 규칙 이관

| 이전 규칙 출처                    | 대상 저장소                | 현재 규칙 위치                          |
|-----------------------------------|----------------------------|-----------------------------------------|
| 중앙 profile (이관 완료)          | Ansible 학습·자동화 저장소 | 해당 저장소 `.governance/GOVERNANCE.md` |
| 전역 skill `zircon-readme-policy` | Zircon 저장소              | 해당 저장소 `.governance/GOVERNANCE.md` |

Ansible 학습·자동화 저장소는 2026-08-27에 이관과 병행 검증을 완료하고 중앙 profile을 제거했습니다. 이관 절차입니다.

1. 대상 저장소에 `.governance/GOVERNANCE.md`를 생성하고 기존 내용을 옮깁니다.
2. 옮긴 내용이 5장의 기술 범위를 벗어나지 않는지 확인합니다.
3. 두 위치를 병행 유지하며 새 위치가 정상 인식되는지 확인합니다.
4. 기존 위치를 제거합니다.
5. 이 저장소의 `README.md`와 `CHANGELOG.md`를 갱신합니다.

🟡 3단계 병행 기간을 두는 이유는 새 위치가 인식되지 않을 때 규칙이 공백 상태가 되는
것을 막기 위함입니다. 기존 위치를 먼저 제거하지 않습니다.

## 7. 금지 범위

`.governance/`에는 다음 정보를 기록하지 않습니다.

- 내부 IP, 호스트명, 사용자명, 개인 경로.
- API key, token, password, SSH key와 같은 자격증명.
- 실제 인프라 구성값과 접속 정보.
- 운영 환경의 상태·장애·접속 기록.
- 다른 저장소에 적용되는 규칙.

`.governance/`는 저장소와 함께 배포되므로 공개 범위를 저장소 공개 범위와 동일하게
취급합니다. 환경 종속 정보가 필요하면 접근이 제한된 별도 운영 문서에서 관리합니다.

## 8. 검증

`.governance/` 추가 또는 수정 후 다음을 실행합니다.

```bash
sudo python3 md-link-check.py .
sudo python3 md-heading-check.py .
sudo python3 md-style-check.py .
sudo gitleaks detect --source . --no-banner
git diff --check
```
