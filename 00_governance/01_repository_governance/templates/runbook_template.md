# RUNBOOK Template

운영 중인 서비스·자동화의 점검과 장애 대응 절차를 기록할 때 사용합니다. 계획 문서는 `plan_template.md`, 원인 분석은 `issue_template.md`를 사용합니다.

Runbook은 장애 상황에서 읽는 문서입니다. 배경 설명보다 실행할 명령과 판단 기준을 앞에 둡니다.

🟡 이 템플릿 파일 하단의 푸터는 템플릿 자체에 적용된 것입니다. 복사한 문서의 푸터는 대상 저장소의 규칙을 따릅니다. 푸터를 금지하는 저장소에서는 푸터를 제거하고, 날짜는 복사한 날짜로 갱신합니다.

## 1. 대상

- 대상 시스템 또는 자동화의 이름을 작성합니다.
- 담당 역할을 작성합니다. 개인 이름 대신 역할로 기록합니다.
- 실행 주기를 작성합니다. 정기 실행이면 주기, 이벤트 기반이면 트리거를 명시합니다.
- 의존 대상을 작성합니다. 이 대상이 실패하면 함께 영향받는 범위를 기록합니다.

## 2. 정상 상태

장애 판단의 기준선입니다. 무엇이 정상인지 모르면 이상 여부를 판정할 수 없습니다.

| 확인 항목      | 명령                    | 정상 기준               |
|----------------|-------------------------|-------------------------|
| 서비스 상태    | 확인 명령을 작성합니다. | 기대 출력을 작성합니다. |
| 로그 이상 여부 | 확인 명령을 작성합니다. | 기대 출력을 작성합니다. |
| 리소스 사용량  | 확인 명령을 작성합니다. | 임계값을 작성합니다.    |

```bash
# 정상 여부를 한 번에 확인하는 명령을 작성합니다.
```

## 3. 정기 점검

- [ ] 점검 항목을 작성합니다. (주기: 일 / 주 / 월)
- [ ] 점검 항목을 작성합니다.

점검 결과를 기록할 위치를 작성합니다. 기록하지 않으면 추세를 판단할 수 없습니다.

## 4. 장애 대응

### 증상별 분기

| 증상               | 우선 확인               | 대응 절차 |
|--------------------|-------------------------|-----------|
| 증상을 작성합니다. | 확인 항목을 작성합니다. | 4.1 참고  |

### 4.1 대응 절차 예시

```bash
# 1. 현재 상태 확인
# 2. 로그 확인
# 3. 조치 실행
# 4. 결과 확인
```

- 각 단계의 기대 결과를 작성합니다.
- 기대와 다르면 어디로 분기하는지 작성합니다.
- 조치가 실패하면 6장 에스컬레이션으로 넘어갑니다.

🟡 원인이 확인되지 않은 상태에서 재시작·삭제를 반복하지 않습니다. 증거가 사라져 이후 원인 분석이 불가능해집니다. 조치 전에 로그와 상태를 먼저 확보합니다.

## 5. 복구 절차

- 정상 상태로 되돌리는 절차를 작성합니다.
- 데이터 복원이 필요하면 복원 원본의 위치와 최신성 확인 방법을 작성합니다.
- 복구 후 2장 정상 상태 확인을 다시 실행합니다.

```bash
# 복구 명령을 작성합니다.
```

### 복구 검증

- [ ] 2장 정상 상태 기준 충족.
- [ ] 장애 기간 중 누락된 처리 확인.
- [ ] 재발 여부 관찰 기간 설정.

## 6. 에스컬레이션

| 조건               | 대상                    | 전달 정보                    |
|--------------------|-------------------------|------------------------------|
| N분 내 복구 실패   | 담당 역할을 작성합니다. | 증상, 확인 결과, 시도한 조치 |
| 데이터 손실 가능성 | 담당 역할을 작성합니다. | 영향 범위, 최종 정상 시점    |
| 비가역 작업 필요   | 승인 권한자             | 작업 내용, 영향, 대안        |

전달할 때 포함할 정보입니다.

- 발생 시각과 인지 시각.
- 확인한 증상과 그 근거(명령 출력, 로그).
- 시도한 조치와 결과.
- 현재 영향 범위.
- 판단이 필요한 사항.

## 7. 비가역 작업

이 Runbook에 포함된 되돌릴 수 없는 작업입니다. 실행 직전에 승인을 받습니다.

| 작업                    | 비가역 사유                       | 승인 필요 |
|-------------------------|-----------------------------------|-----------|
| 작업 내용을 작성합니다. | 되돌릴 수 없는 이유를 작성합니다. | ✅        |

비가역 작업이 없으면 `해당 없음`으로 기록합니다. 확인하지 않은 상태로 비워두지 않습니다.

판단 기준입니다.

- 데이터 삭제, 이력 재작성, force push
- 자격증명 삭제 (비활성화는 되돌릴 수 있으므로 삭제와 구분합니다)
- 설정 후 완화할 수 없는 보호 기능 활성화
- 프로덕션 반영, 공유 시스템 변경

## 8. 변경 이력

| 날짜         | 변경                    | 사유                    |
|--------------|-------------------------|-------------------------|
| `YYYY-MM-DD` | 변경 내용을 작성합니다. | 변경 사유를 작성합니다. |

절차를 변경할 때마다 한 행을 남깁니다. 장애 대응 중 절차가 맞지 않아 즉석에서 다르게 처리했다면, 그 내용을 반영해 절차를 갱신합니다.
