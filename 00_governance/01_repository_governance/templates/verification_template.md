# VERIFICATION Template

저장소별 검증 절차를 `.governance/verification.md`에 정의할 때 사용합니다. 적용 순서와 기술 범위는 [저장소 규칙 우선순위 정책](../governance_precedence.md)에서 정의합니다.

`.governance/GOVERNANCE.md`의 검증 섹션만으로 충분하면 이 파일을 만들지 않습니다. 변경 유형이 여러 가지이고 각각 다른 검증이 필요한 저장소에서 분리합니다.

🟡 이 템플릿 파일 하단의 푸터는 템플릿 자체에 적용된 것입니다. 복사한 문서의 푸터는 대상 저장소의 규칙을 따릅니다. 푸터를 금지하는 저장소에서는 푸터를 제거하고, 날짜는 복사한 날짜로 갱신합니다.

## 1. 사용 방법

```bash
REPO=$(git -C <path> rev-parse --show-toplevel)
mkdir -p "${REPO}/.governance"
cp templates/verification_template.md "${REPO}/.governance/verification.md"
```

복사 후 이 `사용 방법` 섹션을 제거하고, 2·3장을 대상 저장소에서 실제로 실행 가능한 명령으로 교체합니다.

실행할 수 없는 명령을 적어두면 검증을 건너뛰는 원인이 됩니다. 도구가 설치되지 않았으면 5장에 그 사실을 기록합니다.

검증 명령에 내부 IP, 호스트명, 사용자명, 개인 경로, 자격증명을 직접 넣지 않습니다. 환경 종속 값은 환경변수나 placeholder로 두고, 실제 값은 접근이 제한된 별도 문서에서 관리합니다.

## 2. 공통 검증

변경 유형과 무관하게 매번 실행합니다.

```bash
# 문서 검사
# 비밀정보 검사
# 공백·줄바꿈 검사
git diff --check
```

- [ ] 문서 링크·스타일 검사 통과.
- [ ] 비밀정보 검사 통과.
- [ ] 의도하지 않은 파일이 변경 목록에 없음.
- [ ] 변경 범위가 작업 목표와 일치.

## 3. 변경 유형별 검증

| 변경 유형        | 검증 명령                        | 통과 기준               |
|------------------|----------------------------------|-------------------------|
| Markdown 문서    | 링크·스타일 검사                 | 이슈 0건                |
| Python 스크립트  | 구문 검사 및 테스트              | 오류 0건                |
| Bash 스크립트    | `bash -n` 또는 `shellcheck`      | 오류 0건                |
| Ansible          | syntax check, lint, Molecule     | 실패 0건                |
| Terraform        | `fmt -check`, `validate`, `plan` | 변경 내역이 의도와 일치 |
| Docker Compose   | `config` 렌더링                  | 렌더링 성공             |
| Packer / Vagrant | 구문 검사 또는 dry-run           | 오류 0건                |
| Kubernetes       | `--dry-run=client` 검증          | 오류 0건                |
| 보안 관련 변경   | 비밀정보 검사, 로그 출력 확인    | 탐지 0건                |

- 위 표는 예시입니다. 대상 저장소에 없는 유형은 행을 제거합니다.
- 각 유형의 실제 명령을 아래에 작성합니다.

### 유형별 명령

```bash
# Markdown 문서
# Python 스크립트
# Ansible
# Terraform
```

🟡 Terraform `plan` 결과는 실행 전 반드시 사람이 검토합니다. `apply`를 검증 단계에 포함하지 않습니다.

## 4. 실행 순서

```
1. 공통 검증 (2장)
       |
       v
2. 변경 유형 식별
       |
       v
3. 해당 유형 검증 (3장)
       |
       v
4. 실패 시 5장 처리
       |
       v
5. 전체 통과 후 commit
```

빠른 검사를 앞에 둡니다. 구문 검사가 실패하면 뒤의 무거운 검사를 실행할 필요가 없습니다.

## 5. 실패 처리

| 상황        | 처리                                              |
|-------------|---------------------------------------------------|
| 검사 실패   | 원인을 수정합니다. 예외 설정으로 숨기지 않습니다. |
| 도구 미설치 | 그 사실을 명시하고 대체 검증 방법을 기록합니다.   |
| 오탐 확인   | 6장에 대상과 사유를 기록한 뒤 예외로 등록합니다.  |
| 검증 불가   | 무엇을 확인하지 못했는지 작업 문서에 남깁니다.    |

검증 실패를 예외 설정으로 숨기지 않습니다. 예외가 필요하면 6장에 사유를 기록합니다.

### 검증 불가 항목 기록

도구 부재, 환경 제약, 권한 부족으로 검증할 수 없으면 무엇을 확인하지 못했는지 작업 문서에 남깁니다. 통과로 처리하지 않습니다.

## 6. 검사 예외

| 대상           | 제외 검사 | 사유      | 재검토 시점            |
|----------------|-----------|-----------|------------------------|
| 파일 또는 경로 | 검사 항목 | 제외 사유 | `YYYY-MM-DD` 또는 조건 |

- 예외마다 사유와 재검토 시점을 기록합니다.
- 검사기 설정 파일에도 동일한 사유를 주석으로 남깁니다.
- 재검토 시점이 지나면 예외가 여전히 필요한지 확인합니다.

예외는 한 번 만들면 유지되기 쉽습니다. 재검토 시점을 남기지 않으면 원래 사유가 해소된 뒤에도 예외가 남아 검사 공백이 됩니다.
