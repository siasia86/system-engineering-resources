# 에이전트 평가 설계

AX 환경에서 에이전트가 일을 제대로 하는지, 설정을 바꾼 뒤에도 같은 수준을 지키는지를 재는 평가(eval) 설계 방법입니다. 특정 도구의 평가 기능이 아니라 과제·채점기·지표·운영 순서를 도구와 무관하게 정리합니다.

## 1. 평가가 필요한 이유와 용어

에이전트는 여러 턴에 걸쳐 도구를 부르고 파일·시스템 상태를 바꿉니다. 한 단계의 작은 실수가 뒤로 갈수록 커지고, 같은 요청에도 실행마다 결과가 달라집니다. 평가 없이 운영하면 사용자가 문제를 먼저 발견하고, 한 문제를 고치면 다른 문제가 생기는 순환에 빠지기 쉽습니다. 자동 평가는 이런 변화를 배포 전에 드러내는 장치입니다.

용어는 Anthropic의 "Demystifying evals for AI agents"(2026-01-09) 정의를 따릅니다.

| 용어                           | 뜻                                                                    |
|--------------------------------|-----------------------------------------------------------------------|
| 과제(task)                     | 입력과 성공 기준이 정해진 시험 하나                                   |
| 시행(trial)                    | 과제를 한 번 시도한 것. 결과가 매번 달라 여러 번 돌림                 |
| 채점기(grader)                 | 결과의 한 측면을 점수로 바꾸는 논리. 과제 하나에 여러 개를 둘 수 있음 |
| 기록(transcript, trace)        | 한 시행의 출력·도구 호출·중간 결과 전체                               |
| 결과 상태(outcome)             | 시행이 끝난 뒤 환경의 최종 상태                                       |
| 평가 실행기(eval harness)      | 과제 실행·기록·채점·집계를 처음부터 끝까지 돌리는 기반                |
| 에이전트 실행기(agent harness) | 모델이 에이전트로 움직이게 하는 틀. 평가 대상은 모델과 이 틀의 조합   |
| 평가 세트(eval suite)          | 같은 능력·행동을 재는 과제 묶음                                       |

결과 상태와 기록을 구분하는 것이 중요합니다. 예를 들어 "설정 파일을 고쳤다"는 보고는 기록에 있는 주장이고, 실제 파일 내용과 서비스 상태가 결과 상태입니다. 채점은 가능한 한 결과 상태를 봅니다.

## 2. 채점기 종류

| 종류      | 방법 예                                                       | 장점                                 | 약점                                       |
|-----------|---------------------------------------------------------------|--------------------------------------|--------------------------------------------|
| 코드 채점 | 문자열 비교, 테스트 실행, 정적 분석, 결과 상태·도구 호출 확인 | 빠름, 싸고 재현됨, 원인 추적이 쉬움  | 맞는 답의 다른 표현을 틀렸다고 볼 수 있음  |
| 모델 채점 | 기준표(rubric) 채점, 자연어 단언, 두 결과 비교, 정답 대조     | 열린 답과 미묘한 품질을 다룰 수 있음 | 실행마다 다름, 비용, 사람 판정과 맞춰야 함 |
| 사람 채점 | 전문가 검토, 표본 검사, A/B 시험, 검토자 간 일치도 측정       | 품질 기준점이 됨, 모델 채점기 보정용 | 느리고 비쌈, 규모를 키우기 어려움          |

과제 점수는 세 방식으로 합칩니다.

- 가중 합: 채점기 점수를 가중치로 더해 기준값 이상이면 통과
- 전부 통과: 모든 채점기가 통과해야 통과
- 혼합: 필수 항목은 전부 통과, 나머지는 가중 합

선택 원칙은 "결정론적 채점을 먼저, 필요한 곳만 모델 채점, 사람은 검증용"입니다. 파일 존재·문법·링크·빌드처럼 기계가 판정할 수 있는 항목에 모델 채점을 쓰면 비용과 흔들림만 늘어납니다.

## 3. 능력 평가와 회귀 평가

| 구분                  | 묻는 것                       | 기대 통과율   | 쓰임                        |
|-----------------------|-------------------------------|---------------|-----------------------------|
| 능력 평가(capability) | 이 에이전트가 무엇을 잘하는가 | 처음에는 낮음 | 개선 방향 찾기, 설정 비교   |
| 회귀 평가(regression) | 예전에 되던 일이 아직 되는가  | 100%에 가까움 | 모델·지침·도구 변경 전 관문 |

능력 평가에서 통과율이 높아져 안정된 과제는 회귀 평가로 옮깁니다(원문 표현 "graduate"). 회귀 평가는 지침 파일·skill·모델·도구 버전을 바꿀 때마다 돌립니다.

평가 세트가 거의 100%에 도달하면 포화(saturation) 상태입니다. 포화된 세트는 퇴보는 잡지만 개선은 보여 주지 못하므로, 더 어려운 과제를 능력 평가에 추가합니다.

## 4. 반복 시행과 지표

같은 과제도 실행마다 결과가 다르므로 과제당 여러 번(k번) 시행합니다. 이때 두 지표의 뜻이 반대입니다.

| 지표   | 뜻                            | k가 커지면 | 맞는 상황                                   |
|--------|-------------------------------|------------|---------------------------------------------|
| pass@k | k번 중 한 번 이상 성공할 확률 | 올라감     | 사람이 결과를 골라 쓰는 경우(후보 생성)     |
| pass^k | k번 모두 성공할 확률          | 내려감     | 매번 맞아야 하는 경우(자동 실행, 운영 작업) |

pass^k는 τ-bench 논문(arXiv:2406.12045, 2024-06)이 에이전트 신뢰성 지표로 제안했습니다. 시행이 서로 독립이고 한 번 성공률이 p라면 다음과 같이 계산합니다.

```python
p, k = 0.75, 3
pass_at_k = 1 - (1 - p) ** k   # 0.984...
pass_pow_k = p ** k            # 0.421...
print(f"pass@{k}={pass_at_k:.3f}  pass^{k}={pass_pow_k:.3f}")
```

한 번 성공률 75%인 에이전트는 세 번 중 한 번은 거의 성공하지만(약 98%), 세 번 모두 성공할 확률은 약 42%입니다. 운영 작업을 자동으로 맡길지 판단할 때는 pass^k를 봅니다. k=1이면 두 값은 같습니다.

🟡 실제 시행은 같은 환경·캐시를 공유하면 독립이 아니어서 위 공식과 어긋납니다. 시행마다 깨끗한 환경을 쓰는 이유이기도 합니다(5절 5단계).

## 5. 첫 평가 세트 만들기

Anthropic 글의 순서를 AX 환경 용어로 옮겼습니다.

1. 일찍 시작합니다. 실제 실패에서 뽑은 20~50개의 단순한 과제로 충분히 출발할 수 있습니다.
2. 이미 하는 수동 확인에서 시작합니다. 배포 전 확인 항목, 장애 기록, 반복된 지적을 과제로 바꾸고 영향이 큰 것부터 넣습니다.
3. 모호하지 않게 쓰고 참고 해답을 둡니다. 두 전문가가 같은 통과·실패 판정을 내릴 정도로 기준을 적고, 참고 해답으로 풀 수 있는 과제임을 보입니다. 여러 시행에서 0%가 나오면 에이전트보다 과제가 잘못됐을 가능성이 큽니다.
4. 양쪽을 모두 시험합니다. 어떤 행동을 해야 할 때와 하지 말아야 할 때를 함께 넣어 한쪽으로만 최적화되지 않게 합니다(예: "삭제해야 하는 경우"와 "삭제하면 안 되는 경우").
5. 안정된 실행 환경을 만듭니다. 시행마다 깨끗한 상태에서 시작하고 공유 상태를 없앱니다. 공유 상태가 있으면 이전 시행의 Git 이력을 읽어 답을 베끼는 일도 생깁니다.
6. 채점기를 신중히 설계합니다. 정해진 단계 순서가 아니라 결과를 채점하고, 부분 점수를 두고, 채점기를 속이는 방법이 없는지 봅니다.
7. 기록을 읽습니다. 실패가 정당한 실패인지, 채점기가 맞는 해답을 거부한 것인지는 기록을 봐야 압니다. 원문은 "Read the transcripts!"라고 강조합니다.
8. 포화를 지켜봅니다(3절).
9. 담당을 정합니다. 평가 기반은 한 담당이 관리하고, 과제는 각 업무 담당이 보탭니다. 기능을 만들기 전에 그 기능의 평가 과제를 먼저 쓰는 방식(eval-driven development)을 권합니다.

OpenAI의 평가 지침도 같은 방향입니다. 자료는 운영 기록·전문가 작성 예·과거 로그를 섞고, 일반·경계·적대적 사례를 함께 넣으며, 변경마다 평가를 돌리라고 권합니다. "느낌으로 하는 평가(vibe-based evals)"와 배포 뒤로 평가를 미루는 것을 피해야 할 습관으로 듭니다.

## 6. 모델 채점기 운영

모델이 채점하는 방식(LLM-as-judge)은 편하지만 그대로 믿으면 안 됩니다.

| 위험               | 내용                                 | 대응                                                   |
|--------------------|--------------------------------------|--------------------------------------------------------|
| 위치 편향          | 비교할 때 먼저 나온 답을 선호        | 순서를 바꿔 두 번 채점하고 결과가 다르면 무승부·재검토 |
| 길이 편향          | 긴 답을 더 좋게 봄                   | 기준표에 길이와 무관한 항목만 두고, 길이 차이를 기록   |
| 사람 판정과 어긋남 | 채점 기준이 사람 기대와 다름         | 사람이 채점한 표본과 일치도를 확인한 뒤 규모를 키움    |
| 억지 판정          | 판단 근거가 없는데도 점수를 냄       | "판단 불가(Unknown)" 선택지를 둠                       |
| 항목 간 간섭       | 한 항목 인상이 다른 항목 점수에 번짐 | 평가 항목마다 별도 채점 호출로 분리                    |

추가 원칙입니다.

- 열린 점수(1~10점)보다 두 결과 비교나 통과·실패 판정이 안정적입니다(OpenAI 지침).
- 채점 모델이 점수 전에 근거를 먼저 쓰게 합니다.
- 채점 모델과 채점 지시문도 버전을 고정하고, 바꾸면 이전 판정과 비교합니다.

## 7. AX 환경 적용 예

시스템 엔지니어링 저장소에서 에이전트에게 자주 맡기는 일을 과제로 바꾼 예입니다. 채점은 가능한 한 이미 쓰는 검사 도구로 합니다.

| 맡기는 일               | 결과 상태 채점(코드)                                     | 모델·사람 채점이 필요한 부분    |
|-------------------------|----------------------------------------------------------|---------------------------------|
| 셸 스크립트 작성·수정   | `bash -n`, `shellcheck`, 시험 입력으로 실행한 종료 코드  | 로그 문구의 명확성              |
| Ansible 역할 수정       | `ansible-playbook --syntax-check`, `--check --diff` 결과 | 변경 범위가 요청과 맞는지       |
| Markdown 문서 작성      | 링크·앵커 검사, 금지어 검사, 필수 절 존재                | 설명의 정확성, 출처와 본문 일치 |
| 장애 기록에서 원인 요약 | 필수 항목(시각·영향·원인·조치) 존재                      | 원인 판단이 기록 근거와 맞는지  |
| 금지 행동 지키기        | 기록에서 금지 명령(`git push --force` 등) 호출 여부 검사 | 없음                            |

과제 하나를 파일로 적어 두면 사람과 실행기가 같은 기준을 봅니다. 아래 형식은 이 문서가 예로 만든 것이며 표준 형식이 아닙니다.

```yaml
id: shell-log-rotate-001
kind: regression            # capability | regression
prompt: |
  scripts/rotate.sh adds a --dry-run option that prints targets without deleting.
setup:
  - git checkout --quiet fixtures/rotate-base
graders:
  - type: code
    run: bash -n scripts/rotate.sh && shellcheck scripts/rotate.sh
  - type: code
    run: ./scripts/rotate.sh --dry-run /tmp/eval-logs | grep -q 'would delete'
  - type: code
    run: test "$(ls /tmp/eval-logs | wc -l)" -eq 5   # nothing deleted
  - type: model
    rubric: "Help text explains --dry-run in one line. Answer PASS, FAIL or UNKNOWN."
scoring: all_required
trials: 3
metric: pass_pow_k
```

운영 순서는 다음과 같습니다.

1. 장애·검토 지적이 생길 때마다 과제 하나를 추가합니다.
2. 지침 파일·skill·모델·도구 버전을 바꾸는 변경에는 회귀 세트를 돌린 결과를 함께 남깁니다.
3. 실패한 시행은 기록을 읽고 "에이전트 실수 / 과제 오류 / 채점기 오류"로 분류합니다.
4. 결과는 날짜·설정·통과율·실패 분류를 표로 남겨 변화 추세를 봅니다.

실행 기록을 어떻게 남길지는 [에이전트 실행 관측과 감사 기록](agent_observability_audit.md)에서 다룹니다.

## 8. 점검표

- [ ] 과제마다 성공 기준이 적혀 있고, 두 사람이 같은 판정을 내릴 수 있는가
- [ ] 과제마다 참고 해답이 있어 풀 수 있는 과제임이 확인됐는가
- [ ] 해야 할 때와 하지 말아야 할 때를 모두 시험하는가
- [ ] 결정론적으로 판정할 수 있는 항목을 코드 채점으로 처리했는가
- [ ] 모델 채점기를 사람 판정 표본과 맞춰 봤는가
- [ ] 시행마다 깨끗한 환경에서 시작하는가
- [ ] 자동 실행에 맡길 일은 pass^k로 판단하는가
- [ ] 실패 기록을 사람이 읽고 분류하는가
- [ ] 회귀 세트가 지침·모델·도구 변경의 관문으로 쓰이는가
- [ ] 포화된 세트에 더 어려운 과제를 보태는 담당이 있는가

## 9. 한계와 미확인

- 7절의 과제 예와 YAML 형식은 이 문서가 만든 것이며 원문에 없습니다. 평가 실행 도구마다 형식이 다릅니다.
- 4절의 계산은 시행이 서로 독립이라는 가정입니다. 실제 값은 반복 시행으로 측정합니다.
- 원문이 든 벤치마크 수치(SWE-bench Verified 1년 사이 약 30%에서 80% 이상)는 원문 주장이며 이 문서가 따로 확인하지 않았습니다.
- τ-bench 논문의 pass^k 정확한 수식은 초록만 확인했고 본문 수식은 확인하지 못했습니다. 4절 정의는 Anthropic 글의 설명을 따랐습니다.
