# Feature Flag 관리

Feature flag(feature toggle, 기능 플래그)는 코드를 다시 배포하지 않고 설정만으로 기능의 동작 경로를 바꾸는 장치입니다. 배포와 출시를 분리해 위험을 줄이지만, 관리하지 않으면 분기와 설정이 쌓여 그 자체가 장애 원인이 됩니다. 이 문서는 플래그 종류, 구성 요소, 운영 규칙, 수명 주기와 제거, 장애 대응을 다룹니다.

## 1. 개요

| 항목      | 값                                                                                                                                                |
|-----------|---------------------------------------------------------------------------------------------------------------------------------------------------|
| 목적      | 배포(deploy)와 출시(release)를 분리해 노출 범위와 시점을 설정으로 조절                                                                            |
| 대표 용도 | 미완성 기능 숨김, 점진 출시, A/B 실험, 장애 시 기능 끄기(kill switch), 요금제별 기능                                                              |
| 비용      | 코드 분기 증가, 테스트 조합 증가, 설정 오류 위험, 플래그 서비스 의존                                                                              |
| 출처      | Martin Fowler 사이트 "Feature Toggles" (Pete Hodgson), OpenFeature 명세                                                                           |
| 연관 문서 | [Progressive Delivery](./progressive_delivery.md), [Change Management](./change_management.md), [Tech Debt 관리](../cost/tech_debt_management.md) |

배포 전략(rolling·canary)은 "어느 서버가 새 코드를 실행하는가"를 정하고, feature flag는 "새 코드 안에서 어느 사용자가 새 기능을 보는가"를 정합니다. 두 방식은 서로 대체하지 않고 함께 씁니다. 예를 들어 새 버전을 canary로 배포해 코드 자체의 안정성을 확인한 뒤, 플래그로 기능을 1% 사용자부터 켭니다.

## 2. 플래그 분류

Fowler 사이트의 글은 플래그를 수명(longevity)과 동적 정도(dynamism)에 따라 네 가지로 나눕니다.

| 종류          | 목적                                              | 수명                                           | 결정 단위                      | 주 담당       |
|---------------|---------------------------------------------------|------------------------------------------------|--------------------------------|---------------|
| Release       | 미완성·미출시 코드를 숨긴 채 main에 병합하고 배포 | 짧음 (보통 1~2주, 길어도 출시 직후 제거)       | 릴리스·환경 단위로 거의 고정   | 개발팀        |
| Experiment    | A/B·다변량 실험에서 사용자를 집단에 일관되게 배정 | 통계적으로 유의한 결과가 나올 때까지 (시간~주) | 요청마다 (사용자별)            | 제품·데이터팀 |
| Ops           | 운영 중 기능을 끄거나 낮은 품질로 전환            | 대부분 짧음, 일부 kill switch는 오래 유지      | 운영자가 즉시 변경 가능해야 함 | 운영·SRE      |
| Permissioning | 요금제·권한·내부 사용자에게만 기능 제공           | 김 (수년)                                      | 요청마다 (사용자별)            | 제품팀        |

### 분류가 중요한 이유

| 차이      | Release                        | Ops                                            | Permissioning                |
|-----------|--------------------------------|------------------------------------------------|------------------------------|
| 설정 위치 | 소스 저장소의 정적 설정도 충분 | 재배포 없이 바뀌어야 하므로 런타임 설정 저장소 | 사용자·계약 데이터와 연동    |
| 제거 계획 | 생성 시 제거 일정 필수         | kill switch만 예외로 문서화                    | 제품 정책의 일부로 장기 유지 |
| 변경 승인 | 개발팀                         | 장애 대응 중 즉시 변경 권한 필요               | 제품·영업 정책               |

종류를 정하지 않고 플래그를 만들면 Release 플래그가 몇 년씩 남거나, Ops 플래그가 재배포해야만 바뀌는 곳에 저장되는 문제가 생깁니다. 플래그를 만들 때 종류를 메타데이터로 남깁니다.

## 3. 구성 요소

### Fowler의 세 가지 개념

| 개념                 | 설명                                       | 예                                     |
|----------------------|--------------------------------------------|----------------------------------------|
| Toggle Point         | 코드에서 두 경로 중 하나를 고르는 지점     | `if flags.is_enabled("new-checkout"):` |
| Toggle Router        | Toggle Point의 결정을 실제로 계산하는 부분 | 사용자 ID·국가·비율 규칙 평가          |
| Toggle Configuration | Router가 읽는 설정                         | on/off, 대상 집단, 비율                |

Toggle Point마다 조건식을 직접 쓰지 말고 이름 붙은 함수 뒤에 결정을 숨기라고 권합니다. 그래야 판단 규칙이 바뀌어도 모든 분기를 고칠 필요가 없습니다.

### OpenFeature 용어

OpenFeature는 특정 벤더에 묶이지 않는 feature flag 평가 API 명세로, CNCF incubating 프로젝트입니다(openfeature.dev, 확인일 2026-11-16). 애플리케이션은 OpenFeature API만 호출하고, 실제 플래그 저장소는 provider를 바꿔 끼웁니다.

| 용어                   | 의미                                                                              |
|------------------------|-----------------------------------------------------------------------------------|
| Evaluation API         | 애플리케이션이 플래그 값을 묻는 데 쓰는 API                                       |
| Provider               | 특정 플래그 관리 시스템에서 값을 가져오는 구현체                                  |
| Client                 | 플래그 평가 함수를 제공하는 가벼운 객체. 하나의 provider와 연결                   |
| Evaluation Context     | 평가에 쓰는 정보(사용자 ID, 환경, 호스트 등). 규칙이 대상별로 다른 값을 내는 근거 |
| Hook                   | 평가 전후에 끼워 넣는 처리 (로그, 지표, 검증)                                     |
| Flag Management System | 플래그 값과 규칙의 원본. SaaS, 사내 구축, 오픈소스 모두 해당                      |
| Variant                | 값 자체 대신 쓰는 의미 있는 식별자 (예: `on`, `off`, `blue`)                      |

```text
+-------------+     +----------------+     +------------+     +----------------+
| application | --> | OpenFeature    | --> | provider   | --> | flag mgmt      |
| code        |     | client + hooks |     | (adapter)  |     | system         |
+-------------+     +----------------+     +------------+     +----------------+
       ^                    |
       +---- value or default on error
```

평가가 실패하면(provider 연결 끊김, 플래그 없음, 타입 불일치) 호출자가 넘긴 기본값으로 돌아가는 것이 명세의 기본 동작입니다. 따라서 기본값을 "안전한 쪽"으로 고르는 것이 설계의 핵심입니다(5절).

## 4. 평가와 타기팅

| 방식              | 설명                             | 주의                                                         |
|-------------------|----------------------------------|--------------------------------------------------------------|
| 전역 on/off       | 모든 요청에 같은 값              | 가장 단순. Ops kill switch에 적합                            |
| 대상 목록         | 특정 사용자·조직·내부 직원만     | 목록이 커지면 규칙 대신 속성(attribute) 기반으로             |
| 속성 규칙         | 국가, 앱 버전, 요금제 등 조건    | Evaluation Context에 속성이 빠지면 기본 규칙으로 떨어짐      |
| 비율 (fractional) | targeting key의 해시로 N%만 선택 | 같은 사용자는 같은 결과를 받도록 안정적인 키(사용자 ID) 사용 |

### 비율 출시의 일관성

OpenFeature는 fractional evaluation을 "targeting key 같은 문맥 속성을 기준으로, 설정한 비율에 따라 의사 난수로 값을 정하는 것"으로 설명합니다. 무작위가 아니라 키 해시 기반이어야 같은 사용자가 요청마다 새 화면과 이전 화면을 오가는 일이 없습니다.

```python
import hashlib

def in_rollout(flag_key: str, user_id: str, percent: int) -> bool:
    """Return True if user_id falls into the first `percent` buckets (0-99)."""
    digest = hashlib.sha256(f"{flag_key}:{user_id}".encode()).hexdigest()
    bucket = int(digest[:8], 16) % 100
    return bucket < percent
```

플래그 키를 해시 입력에 섞으면 플래그마다 서로 다른 사용자 집단이 선택됩니다. 섞지 않으면 모든 실험에서 같은 사용자가 항상 먼저 새 기능을 받게 되어 결과가 치우칩니다. 비율을 5% → 20%로 올릴 때 기존 5% 사용자는 그대로 포함됩니다.

## 5. 운영 규칙

### 플래그 메타데이터

플래그를 만들 때 다음 항목을 함께 기록합니다. 플래그 관리 도구의 설명 필드나 저장소의 설정 파일 주석을 씁니다.

| 항목        | 예                                      | 이유                                                    |
|-------------|-----------------------------------------|---------------------------------------------------------|
| 이름        | `checkout-new-payment-flow`             | 영역-기능 형식, 의미가 드러나게. `test1` 같은 이름 금지 |
| 종류        | release / experiment / ops / permission | 수명과 변경 권한이 종류에 따라 다름                     |
| 담당자      | 팀 이름                                 | 담당자가 퇴사·이동해도 추적 가능하게 개인보다 팀        |
| 만료 예정일 | 2026-12-31                              | Release·Experiment는 필수                               |
| 기본값      | `false`                                 | 평가 실패 시 동작                                       |
| 관련 티켓   | 이슈 번호                               | 제거 작업 추적                                          |

### 기본값 고르기

| 플래그 성격                        | 안전한 기본값   | 이유                                                  |
|------------------------------------|-----------------|-------------------------------------------------------|
| 새 기능 출시                       | off (기존 동작) | 플래그 서비스 장애 시 검증된 경로로 동작              |
| Kill switch (기능 끄기)            | on (기능 유지)  | 플래그 서비스 장애가 곧바로 기능 중단으로 번지지 않게 |
| 보안 통제 (예: 새 권한 검사)       | 통제 유지 쪽    | 장애 시 통제가 풀리지 않게                            |
| 비용이 큰 기능 (예: 고해상도 처리) | 낮은 비용 쪽    | 장애와 부하가 겹칠 때 부담을 줄임                     |

### 변경 관리

- 운영 환경 플래그 변경은 배포와 같은 변경으로 취급하고 누가, 언제, 무엇을 바꿨는지 감사 기록(audit log)을 남깁니다.
- 큰 영향이 있는 플래그(전체 사용자 대상, 결제·인증 경로)는 비율을 단계적으로 올리고 [Progressive Delivery](./progressive_delivery.md)의 판정 기준을 적용합니다.
- 인시던트 타임라인에 플래그 변경 기록이 보이도록 변경 이벤트를 모니터링 도구(대시보드 annotation 등)에 보냅니다.
- Ops 플래그는 장애 대응자가 승인 대기 없이 바꿀 수 있어야 합니다. 권한은 미리 부여하고 사후 검토합니다.

## 6. 수명 주기와 제거

```text
create --> develop (off) --> internal on --> 1% --> 10% --> 50% --> 100%
                                                                     |
                                     remove code path + delete flag <-+
```

Fowler 사이트의 글은 플래그를 "보유 비용(carrying cost)이 있는 재고"로 보고 개수를 적게 유지하라고 권합니다. 100%로 켠 뒤 오래 방치된 플래그는 다음 문제를 만듭니다.

| 문제          | 설명                                                                          |
|---------------|-------------------------------------------------------------------------------|
| 죽은 코드     | 끄면 실행될 이전 경로가 아무도 시험하지 않은 채 남음                          |
| 잘못된 되돌림 | 누군가 오래된 플래그를 끄면 수개월 전 동작으로 돌아가 장애                    |
| 인지 부하     | 코드 읽는 사람이 어느 경로가 실제 경로인지 추적해야 함                        |
| 이름 재사용   | 지운 플래그 이름을 다른 용도로 다시 쓰면 오래된 클라이언트가 엉뚱한 값을 받음 |

### 제거를 강제하는 방법

| 방법              | 설명                                                                          |
|-------------------|-------------------------------------------------------------------------------|
| 생성 시 제거 티켓 | Release 플래그를 만들 때 제거 작업을 같은 백로그에 함께 등록                  |
| 만료일            | 만료일이 지나면 경고. 일부 팀은 만료가 지난 플래그가 있으면 테스트를 실패시킴 |
| 개수 상한         | 팀별 동시 활성 플래그 수에 상한을 두어 새로 만들려면 하나를 지우게 함         |
| 정기 점검         | 월 1회 "100% on 또는 0% 상태로 30일 이상 지난 플래그" 목록 검토               |

### 제거 순서

1. 플래그가 모든 환경에서 같은 값(대개 100% on)으로 안정적인지 확인합니다.
2. 코드에서 Toggle Point와 사용하지 않는 경로를 지우고 배포합니다.
3. 새 코드가 모든 서버·클라이언트에 퍼진 뒤 플래그 관리 시스템에서 플래그를 지웁니다.

🟡 순서를 바꿔 플래그를 먼저 지우면, 아직 이전 코드를 실행 중인 서버나 모바일 앱이 평가 실패로 기본값(대개 off)을 받아 기능이 꺼질 수 있습니다. 모바일 앱처럼 이전 버전이 오래 남는 클라이언트는 사용 버전 분포를 확인한 뒤 지웁니다.

## 7. 테스트

플래그 N개의 모든 조합은 2의 N제곱이므로 전부 시험할 수 없습니다. Fowler 사이트의 글은 운영에서 실제로 켜질 조합과 그 대체(fallback) 조합만 시험하라고 권합니다.

| 시험 대상        | 방법                                                    |
|------------------|---------------------------------------------------------|
| 운영 예정 조합   | 다음 배포에서 켜질 플래그 상태로 통합 시험              |
| 모두 off         | 기존 동작이 유지되는지 (플래그 서비스 장애 상황과 같음) |
| 대상 플래그만 on | 새 기능 단독 동작                                       |
| 평가 실패        | provider를 끊었을 때 기본값으로 정상 동작하는지         |
| 비율 일관성      | 같은 사용자 ID가 반복 평가에서 같은 결과를 받는지       |

단위 시험에서는 OpenFeature의 in-memory provider나 시험용 고정 provider처럼 결과를 지정할 수 있는 provider를 넣어 플래그 값을 고정합니다. 시험 코드에서 실제 플래그 서비스를 호출하지 않습니다.

## 8. 장애 대응

### Kill switch로 장애 줄이기

새 기능이 장애를 일으키면 재배포보다 플래그 끄기가 빠릅니다. 이를 위해 다음을 미리 준비합니다.

- [ ] 위험이 큰 신규 기능마다 끌 수 있는 플래그가 있는가
- [ ] 런북에 플래그 이름과 끄는 방법(콘솔 경로·CLI 명령)이 적혀 있는가
- [ ] 끈 상태(기존 경로)가 최근에 시험되었는가
- [ ] 값 변경이 서버에 반영되는 시간(polling 주기·스트리밍 지연)을 알고 있는가

### 플래그 서비스 자체의 장애

| 위험                                         | 대응                                                                  |
|----------------------------------------------|-----------------------------------------------------------------------|
| 플래그 서비스 응답 지연이 요청 지연으로 번짐 | 요청 경로에서 원격 호출하지 않고, 로컬 캐시·SDK 내부 저장소에서 평가  |
| 시작 시 플래그를 못 받아 기동 실패           | 마지막으로 받은 설정을 디스크에 저장하고 그것으로 기동, 없으면 기본값 |
| 잘못된 설정이 전체에 즉시 퍼짐               | 설정 변경도 단계적으로(환경별·비율별) 적용, 변경 검토 절차 적용       |
| 플래그 서비스 장애 중 Ops 플래그를 못 바꿈   | 핵심 kill switch는 설정 파일·환경 변수 등 대체 경로를 따로 둠         |

[⬆ 목차로 돌아가기](#목차)

## 9. 트러블슈팅

| 증상                                          | 가능한 원인                                    | 확인·조치                                                   |
|-----------------------------------------------|------------------------------------------------|-------------------------------------------------------------|
| 같은 사용자가 새 화면과 이전 화면을 번갈아 봄 | 비율 평가에 무작위 값 사용, targeting key 누락 | 사용자 ID 기반 해시 사용, Evaluation Context에 키 전달 확인 |
| 플래그를 켰는데 일부 서버만 반영              | SDK polling 주기, 캐시 TTL, 연결 끊긴 인스턴스 | SDK 상태 지표·로그 확인, 반영 시간 문서화                   |
| 플래그 서비스 장애 때 기능이 꺼짐             | 기본값이 off인 kill switch                     | 5절 기본값 표에 따라 기본값 재검토                          |
| 모든 실험에서 같은 사용자가 먼저 선택됨       | 해시 입력에 플래그 키를 섞지 않음              | `flag_key:user_id` 형식으로 해시                            |
| 오래된 플래그를 끄자 장애                     | 이전 경로가 오래 시험되지 않음                 | 100% on 플래그는 코드에서 제거, 정기 점검                   |
| 인시던트 원인을 찾는 데 오래 걸림             | 플래그 변경이 타임라인에 안 보임               | 플래그 변경을 대시보드 annotation·변경 이력에 기록          |
| 시험 결과가 실행 때마다 다름                  | 시험이 실제 플래그 서비스를 호출               | 시험용 provider로 값 고정                                   |
