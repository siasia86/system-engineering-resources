# On-Call Design

효과적인 온콜 로테이션을 설계하고 엔지니어의 번아웃을 방지하면서 서비스 안정성을 유지하는 운영 프레임워크입니다. Google SRE Book Ch.11을 기반으로 합니다.

## 1. 개요

| 항목 | 값                                                      |
|------|---------------------------------------------------------|
| 목적 | 장애 발생 시 빠른 대응 보장 + 엔지니어 건강 유지        |
| 출처 | Google SRE Book Ch.11 "Being On-Call"                   |
| 핵심 | 25% 규칙, 균형 잡힌 로테이션, 명확한 에스컬레이션       |
| 전제 | 모니터링 + 알림 + 런북이 갖춰진 상태에서 시작           |
| 연관 | Incident Management (장애 대응), Postmortem (사후 학습) |

### Google 25% 규칙 (SRE Book Ch.11 원문)

> "of the remainder, no more than 25% can be spent on-call, leaving up to another 25% on other types of operational, non-project work"

| 업무 구성      | 비율     |
|----------------|----------|
| 프로젝트 작업  | 50%+     |
| 온콜 duty      | 최대 25% |
| 기타 운영 작업 | 최대 25% |

## 2. 로테이션 설계

### 로테이션 패턴

| 패턴              | 주기           | 적합 팀 규모 | 장점            |
|-------------------|----------------|--------------|-----------------|
| Weekly            | 1주 교대       | 6명+         | 단순, 예측 가능 |
| Follow-the-sun    | 시간대별 교대  | 글로벌 팀    | 야간 호출 없음  |
| Split (day/night) | 주간/야간 분리 | 4명+         | 야간 부담 분산  |
| Buddy system      | 2인 1조        | 소규모 팀    | 신입 멘토링     |

### 최소 인원 산정

| 패턴       | 최소 인원    | 산정 근거                            |
|------------|--------------|--------------------------------------|
| Weekly     | 6명          | 6주 주기 → 연 8.7주 = 약 17% on-call |
| Bi-weekly  | 4명          | 주의: 25% 초과 가능, 보완 필요       |
| Follow-sun | 3 리전 × 2명 | 리전당 최소 2명 (백업 필수)          |

### 일정 관리 규칙

- 최소 2주 전 일정 공개
- 온콜 교환(swap)은 자유롭되 시스템에 반영 필수
- 휴가 기간 온콜 면제 (대체자 지정 필수)
- 연속 온콜 2주 초과 금지

## 3. 보상 체계

### 보상 유형

| 유형        | 내용                        | 적용 시점           |
|-------------|-----------------------------|---------------------|
| 대기 수당   | 온콜 기간 고정 보상         | 온콜 시작~종료      |
| 호출 수당   | 실제 호출 시 추가 보상      | 알림 수신 + 대응 시 |
| 대체 휴무   | 야간/주말 대응 후 보상 휴무 | 대응 다음 영업일    |
| 시간외 수당 | 정규 시간 외 작업 시간      | 대응 시간 기준      |

### 보상 없으면 발생하는 문제

- 온콜 기피 → 특정인 집중 → 번아웃
- "내 시간이 아닌데" 느낌 → 대응 지연
- 채용/리텐션 악화

## 4. 런북

### 런북 구조

```markdown
# Runbook: [Alert Name]

## Severity
SEV-N

## Symptoms
- [관찰 가능한 증상]

## Investigation Steps
1. [확인 명령어/대시보드]
2. [로그 확인 위치]
3. [의존성 확인]

## Remediation
1. [수동 복구 절차]
2. [자동 복구 트리거]

## Escalation
- [에스컬레이션 조건]
- [담당자/채널]

## Related
- [관련 런북 링크]
- [아키텍처 문서]
```

### 런북 품질 기준

| 기준       | 좋은 예                    | 나쁜 예              |
|------------|----------------------------|----------------------|
| Actionable | "kubectl rollout undo ..." | "이전 버전으로 복구" |
| Up-to-date | 마지막 검증일 명시         | 2년 전 작성, 미갱신  |
| Accessible | 알림에 런북 링크 포함      | 위키 어딘가에 존재   |
| Tested     | Game Day에서 검증됨        | 작성만 하고 미사용   |

## 5. 에스컬레이션

### 에스컬레이션 매트릭스

| 시간 경과 | 대상                | 조건               |
|-----------|---------------------|--------------------|
| 0분       | Primary on-call     | 알림 수신          |
| 5분       | Secondary on-call   | Primary 무응답     |
| 15분      | 팀 리드             | SEV-2 이상 미해결  |
| 30분      | Engineering Manager | SEV-1 미해결       |
| 60분      | VP/Director         | 비즈니스 영향 지속 |

### 에스컬레이션 트리거

| 조건                  | 행동                   |
|-----------------------|------------------------|
| 5분 내 ACK 없음       | Secondary 자동 호출    |
| 런북으로 해결 불가    | 도메인 전문가 호출     |
| 고객 영향 확인        | 커뮤니케이션 리드 참여 |
| 복구 예상 시간 > 30분 | IC 지정 + 상위 보고    |

## 6. 핸드오프

### 핸드오프 체크리스트

| 항목           | 내용                               |
|----------------|------------------------------------|
| 진행 중 이슈   | 미해결 알림, 진행 중 작업 인수인계 |
| 최근 변경사항  | 배포, 설정 변경, 인프라 작업       |
| 주의 사항      | 예정된 작업, 알려진 불안정 요소    |
| 도구 접근 확인 | VPN, 대시보드, 호출 도구 정상      |

### 핸드오프 방법

| 방법        | 적합 상황            | 소요 시간 |
|-------------|----------------------|-----------|
| 동기 미팅   | 이슈 많을 때         | 15~30분   |
| 비동기 문서 | 평온한 기간          | 5분       |
| 혼합        | 기본 문서 + 질의응답 | 10분      |

## 7. 번아웃 방지

### 번아웃 지표

| 지표                       | 위험 임계값                 |
|----------------------------|-----------------------------|
| 주당 페이지 수             | > 2회/shift (SRE Book 기준) |
| 야간 호출 빈도             | > 1회/주                    |
| 연속 온콜 주수             | > 2주                       |
| 온콜 중 프로젝트 작업 비율 | < 50% (25% 규칙 위반)       |

### 예방 조치

| 조치              | 설명                                  |
|-------------------|---------------------------------------|
| Toil 자동화       | 반복 수동 작업을 자동화하여 호출 감소 |
| 알림 튜닝         | Noise 제거, 중복 알림 통합            |
| 인원 충원         | 25% 규칙 위반 시 팀 확장 요청         |
| On-call 품질 리뷰 | 월간 호출 건수/유형 분석              |
| 보상 휴무 보장    | 야간 대응 후 다음날 오전 휴무         |

## 9. 트러블슈팅

| 증상                    | 원인                   | 해결                              |
|-------------------------|------------------------|-----------------------------------|
| 온콜이 항상 같은 사람   | 로테이션 설계 미흡     | 공정한 스케줄링 + swap 시스템     |
| 알림 폭풍 (alert storm) | 임계값 과민, 중복 알림 | 알림 튜닝, dedup, grouping        |
| 호출 후 아무것도 못 함  | 런북 부재/부실         | 알림별 런북 필수화, Game Day 검증 |
| 핸드오프 시 정보 유실   | 비동기 전달, 문서 미비 | 표준 핸드오프 템플릿 + 동기 미팅  |
| 온콜 기피로 퇴사 증가   | 보상 부재, 과부하      | 보상 체계 도입, 인원 충원, 자동화 |
