# Toil 관리와 줄이기
<!-- reference: _reference/sre_operations_official_notes.md -->

Toil은 서비스를 운영하면서 생기는 수작업 중 반복되고 자동화할 수 있으며 지나고 나면 남는 가치가 없는 일을 가리키는 SRE 용어입니다. 이 문서는 Google SRE Book Ch.5와 SRE Workbook Ch.6을 바탕으로 toil을 가려내고, 측정하고, 우선순위를 정해 줄이는 방법을 다룹니다.

## 1. 개요

| 항목      | 값                                                                                                                                               |
|-----------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| 정의      | 운영 서비스에 묶인 일 중 수작업·반복·자동화 가능·전술적·지속 가치 없음·서비스 성장에 비례하는 일                                                 |
| 목표치    | Google SRE는 각 SRE 시간 중 toil을 50% 아래로 유지하는 것을 목표로 둠                                                                            |
| 출처      | Google SRE Book Ch.5 "Eliminating Toil", SRE Workbook Ch.6 "Eliminating Toil"                                                                    |
| 연관 문서 | [On-Call 설계](./oncall_design.md), [SLO & Error Budget](./slo_error_budget.md), [Platform Engineering](../organization/platform_engineering.md) |

SRE Book은 toil이 "그냥 하기 싫은 일(work I don't like to do)"과 같지 않다고 강조합니다. 지루해도 오래 남는 가치를 만드는 일은 toil이 아닙니다. 반대로 흥미로워 보여도 매번 같은 손작업으로 같은 상태를 되돌리는 일은 toil입니다.

50% 목표는 나머지 절반 이상을 앞으로의 toil을 줄이거나 서비스 기능을 늘리는 엔지니어링 작업에 쓰기 위한 것입니다. SRE Book은 toil을 그대로 두면 "모든 사람의 시간을 100%까지 채우는 쪽으로 커지는 경향이 있다"고 경고합니다.

## 2. Toil 판별

SRE Book은 아래 특성을 많이 가질수록 toil에 가깝다고 설명합니다. 하나만 해당해도 toil이라고 단정하지 않고, 정도의 문제로 봅니다.

| 특성                               | 설명                                                                   | 판별 질문                               |
|------------------------------------|------------------------------------------------------------------------|-----------------------------------------|
| 수작업 (Manual)                    | 사람이 직접 손으로 진행. 스크립트라도 사람이 매번 실행하면 해당        | 사람이 개입하지 않으면 일어나지 않는가? |
| 반복 (Repetitive)                  | 같은 일이 되풀이됨. 처음 겪는 문제 해결은 toil이 아님                  | 지난달에도 같은 일을 했는가?            |
| 자동화 가능 (Automatable)          | 기계가 같은 품질로 할 수 있거나 설계 변경으로 필요 자체를 없앨 수 있음 | 사람의 판단이 실제로 필요한가?          |
| 전술적 (Tactical)                  | 계획이 아니라 끼어들기(interrupt)로 발생하는 대응                      | 알림·티켓이 와야 시작하는가?            |
| 지속 가치 없음 (No enduring value) | 끝난 뒤 서비스 상태가 전과 같음                                        | 하고 나서 서비스가 나아졌는가?          |
| 성장 비례 O(n)                     | 서비스 크기·트래픽·사용자 수에 비례해 늘어남                           | 서버가 2배면 이 일도 2배인가?           |

### 예시 판정

| 작업                                                | 판정       | 이유                               |
|-----------------------------------------------------|------------|------------------------------------|
| 디스크 사용률 경보가 올 때마다 로그 수동 삭제       | Toil       | 수작업·반복·전술적, 서버 수에 비례 |
| 로그 보존 정책(logrotate, 수명 주기 규칙) 설계·적용 | 엔지니어링 | 한 번 하면 같은 경보가 사라짐      |
| 신규 입사자 계정을 티켓마다 수동 생성               | Toil       | 반복·자동화 가능, 인원에 비례      |
| 처음 보는 장애의 원인 분석                          | Toil 아님  | 새로운 문제, 판단 필요             |
| 같은 원인의 장애를 같은 절차로 매주 복구            | Toil       | 원인을 고치지 않은 반복 대응       |
| 인증서 갱신을 달력 알림 보고 수동 수행              | Toil       | 자동 갱신으로 대체 가능            |

## 3. Toil이 아닌 일

| 구분                    | 예                                  | 관리 방법                                                     |
|-------------------------|-------------------------------------|---------------------------------------------------------------|
| 간접 업무 (Overhead)    | 회의, 인사 행정, 목표 설정, 교육    | 서비스 운영과 직접 관련이 없으므로 toil과 따로 집계           |
| 지루하지만 가치 있는 일 | 레거시 설정 정리, 문서화, 권한 정리 | 끝나면 상태가 나아지므로 엔지니어링으로 봄                    |
| 새 문제 대응            | 처음 겪는 장애 분석                 | 포스트모텀으로 재발 방지 작업을 만들면 다음부터 toil이 줄어듦 |

Toil과 overhead를 섞어 집계하면 "toil이 70%"처럼 실제보다 크게 보이거나, 반대로 회의 시간 때문에 toil 감소 효과가 보이지 않습니다. 두 값을 나누어 기록합니다.

## 4. Toil 유형

SRE Workbook이 정리한 분류입니다. 팀의 업무 기록을 이 분류로 나누어 보면 어디부터 손댈지 보입니다.

| 유형                                  | 예                                         | 흔한 해결 방향                                                                      |
|---------------------------------------|--------------------------------------------|-------------------------------------------------------------------------------------|
| 업무 절차 (Business processes)        | 권한 요청, 계정·자원 발급 티켓             | 셀프서비스 화면·API, 승인 규칙 자동화                                               |
| 운영 끼어들기 (Production interrupts) | 디스크 비우기, 메모리 누수 프로세스 재시작 | 원인 수정, 자동 복구, 경보 정리                                                     |
| 릴리스 돌보기 (Release shepherding)   | 수동 롤백, 긴급 패치, 수동 설정 변경       | 배포 파이프라인 자동화, [Progressive Delivery](../delivery/progressive_delivery.md) |
| 이전 작업 (Migrations)                | 기술 교체에 따른 반복 변경                 | 일괄 변경 도구, 단계별 자동화                                                       |
| 비용·용량 작업                        | 구매, 출시 준비, 자원 재배치               | 용량 모델 자동화, [Capacity Planning](../delivery/capacity_planning.md)             |
| 불투명한 구조의 문제 해결             | 깨지기 쉬운 분산 시스템의 반복 디버깅      | 관측성 보강, 구조 단순화                                                            |

Workbook은 티켓으로 오는 업무 절차 toil이 팀원에게 고르게 퍼져 있어서 눈에 잘 띄지 않는다고 지적합니다. 개인 체감이 아니라 티켓 수·소요 시간을 합산해야 드러납니다.

## 5. 측정

Workbook은 측정을 세 단계로 설명합니다.

1. 실제로 일하는 사람과 함께 toil을 찾습니다.
2. 객관적이고 일관된 단위(분·시간·티켓 수·패치 수)를 정합니다. 맥락 전환(context switch) 비용도 셉니다.
3. 줄이기 전·중·후로 계속 측정합니다. 측정 도구 자체가 새 toil이 되지 않게 기존 티켓·온콜 기록에서 뽑습니다.

### 측정 기록 예시

| 항목             | 값                                  |
|------------------|-------------------------------------|
| 작업명           | 디스크 경보 대응 (로그 수동 정리)   |
| 유형             | 운영 끼어들기                       |
| 월 발생 횟수     | 18회                                |
| 1회 소요         | 25분 (맥락 전환 10분 포함)          |
| 월 합계          | 450분 = 7.5시간                     |
| 성장 추세        | 서버 증설과 함께 증가               |
| 자동화 예상 비용 | 16시간 (보존 정책 + 경보 기준 정리) |
| 회수 기간        | 약 2.1개월                          |

### 데이터 출처

| 출처        | 뽑을 값                                              |
|-------------|------------------------------------------------------|
| 티켓 시스템 | 유형별 건수, 처리 시간, 재오픈 비율                  |
| 온콜 기록   | 호출 수, 야간 호출 수, 같은 경보 반복 횟수           |
| 배포 기록   | 수동 개입이 필요한 배포 비율, 수동 롤백 횟수         |
| 설문        | 분기별 "이번 분기 toil 비율 체감" (정량 기록 보완용) |

## 6. 우선순위 결정

Workbook은 "고치는 비용"과 "절약되는 시간"으로 후보를 줄 세우되, 계산상 손해처럼 보여도 사기·사람 실수로 인한 장애 감소·맥락 전환 감소 같은 간접 이익이 있으면 할 가치가 있다고 설명합니다.

### 점수표 예시

| 후보             | 월 소요(시간) | 자동화 비용(시간) | 회수 기간(개월) | 위험 감소             | 우선순위 |
|------------------|---------------|-------------------|-----------------|-----------------------|----------|
| 디스크 경보 대응 | 7.5           | 16                | 2.1             | 중 (야간 호출 감소)   | 1        |
| 계정 발급 티켓   | 6             | 40                | 6.7             | 중 (권한 오설정 감소) | 2        |
| 인증서 수동 갱신 | 0.5           | 8                 | 16              | 높음 (만료 장애 방지) | 2        |
| 월간 수동 보고서 | 3             | 30                | 10              | 낮음                  | 4        |

인증서 갱신은 시간 절약만 보면 회수 기간이 길지만, 놓치면 전면 장애가 나므로 위험 감소 때문에 우선순위가 올라갑니다. 이처럼 시간과 위험을 함께 봅니다.

### 판단 순서

1. 이 일을 아예 하지 않아도 되는가? (거절·폐기)
2. 설계를 바꿔 필요 자체를 없앨 수 있는가? (원인 제거)
3. 요청자가 직접 하게 할 수 있는가? (셀프서비스)
4. 위 셋이 안 되면 자동화합니다.
5. 자동화 비용이 지나치게 크면 부분 자동화나 절차 개선으로 줄이고, 남은 toil은 받아들입니다.

Workbook은 원인에서 toil을 없애는 방법을 우선 해결책으로 보면서도, 모든 toil을 없앨 수는 없고 전 과정 자동화가 늘 이득은 아니라고 함께 말합니다.

## 7. 줄이는 전략

Workbook의 toil 관리 전략을 운영 관점으로 묶었습니다.

| 전략                           | 내용                                                                         | 적용 예                                                         |
|--------------------------------|------------------------------------------------------------------------------|-----------------------------------------------------------------|
| 거절하기                       | toil이 큰 요청은 먼저 하지 않는 방안을 검토. 미룬 일을 모아 보면 패턴이 보임 | 반복 데이터 추출 요청을 모아 조회 화면 하나로 대체              |
| SLO로 미루기                   | error budget을 위협하지 않는 운영 작업은 뒤로 미룸                           | 예산 여유가 있으면 비긴급 경보는 업무 시간에 처리               |
| 사람이 처리하는 인터페이스부터 | 처음엔 요청 양식을 표준화하고 사람이 처리, 이후 뒤쪽을 자동화                | 정형화된 티켓 양식 → 승인 후 스크립트 자동 실행                 |
| 셀프서비스                     | 요청자가 직접 처리하는 화면·API 제공                                         | DNS 레코드·권한 요청 셀프서비스                                 |
| 관리자와 동료의 지원           | toil 감소를 위한 시간을 공식 일정으로 확보                                   | 분기마다 toil 감소 과제를 계획에 포함                           |
| 기능으로 홍보                  | toil 감소를 비용 절감·신뢰성 향상 같은 기능으로 설명                         | "배포 시간 40분 → 5분" 같은 결과 공유                           |
| 작게 시작                      | 가장 자주 하는 한 가지부터 자동화하고 넓힘                                   | 재시작 스크립트 → 자동 복구 → 원인 수정                         |
| 균일하게 만들기                | 서버·설정을 표준화하면 자동화 대상이 줄어듦                                  | 같은 이미지·같은 설정 관리 도구 사용                            |
| 자동화 위험 평가               | 자동화가 잘못 동작할 때의 영향을 미리 평가                                   | 8절 안전장치 적용                                               |
| 대응 자동화                    | 경보에 대한 정해진 대응을 자동 실행                                          | 디스크 경보 시 오래된 임시 파일 자동 정리                       |
| 공개 도구 활용                 | 직접 만들기 전에 오픈소스·기존 도구 확인                                     | 인증서 자동 갱신 도구, 설정 관리 도구                           |
| 피드백 반영                    | 사용자·운영자 의견으로 자동화를 계속 개선                                    | 자동화 실패 사례를 회고에 포함                                  |
| 레거시 처리                    | 피하기, 감싸기(encapsulation), 교체, 폐기 중 선택                            | [Legacy Modernization](../organization/legacy_modernization.md) |

### 온콜과의 연결

온콜 호출의 상당 부분은 운영 끼어들기 toil입니다. 같은 경보가 반복되면 [On-Call 설계](./oncall_design.md)의 런북에 대응 절차를 적는 데서 멈추지 말고, 그 절차를 자동화하거나 원인을 없애는 과제로 바꿉니다. 포스트모텀의 Action Item에 "같은 수동 대응이 다시 필요 없게 하기"를 포함하는 것도 같은 목적입니다.

## 8. 자동화 안전장치

Workbook 사례에서 나온 교훈은 자동화가 방어 장치를 갖추고, 안전하지 않은 상황에서는 사람에게 넘겨야 한다는 것입니다.

| 장치            | 설명                                   | 예                                       |
|-----------------|----------------------------------------|------------------------------------------|
| 범위 제한       | 한 번에 처리하는 대상 수·비율에 상한   | 재시작은 한 번에 클러스터의 10% 이하     |
| 속도 제한       | 일정 시간 안의 실행 횟수 제한          | 같은 서버 자동 재시작은 1시간에 2회까지  |
| 사전 조건 확인  | 실행 전 상태가 예상과 같은지 확인      | 정상 서버 수가 기준 이하이면 중단        |
| dry-run         | 실제 변경 없이 대상과 동작 출력        | 삭제 대상 파일 목록만 먼저 출력          |
| 사람에게 넘기기 | 예외 상황이면 멈추고 호출              | 예상보다 대상이 많으면 중단 후 온콜 호출 |
| 기록            | 모든 자동 동작을 로그·이벤트로 남김    | 대시보드 annotation, 변경 이력           |
| 담당자          | 자동화에도 소유 팀을 지정하고 유지보수 | 자동화가 다른 팀에 새 toil을 만들지 점검 |

```bash
#!/usr/bin/env bash
# Delete temp files older than N days under one directory, with safety limits.
set -euo pipefail

TARGET_DIR="/var/tmp/app"
MAX_AGE_DAYS=7
MAX_FILES=5000
DRY_RUN="${DRY_RUN:-1}"

count=$(find "$TARGET_DIR" -xdev -type f -mtime +"$MAX_AGE_DAYS" | wc -l)
if [ "$count" -gt "$MAX_FILES" ]; then
    echo "abort: $count files exceed limit $MAX_FILES, escalate to on-call" >&2
    exit 2
fi

if [ "$DRY_RUN" = "1" ]; then
    find "$TARGET_DIR" -xdev -type f -mtime +"$MAX_AGE_DAYS" -print
else
    find "$TARGET_DIR" -xdev -type f -mtime +"$MAX_AGE_DAYS" -delete
fi
```

🟡 위 스크립트는 `DRY_RUN=0`일 때 파일을 실제로 지웁니다. `TARGET_DIR`가 의도한 경로인지, 상한(`MAX_FILES`)이 서비스 규모에 맞는지 dry-run 결과로 먼저 확인한 뒤 적용합니다.

Workbook 사례는 반대 방향의 교훈도 줍니다. 한 팀은 원인 분석에 수년을 쓴 뒤에야 단순한 "빼고 재부팅(drain and reboot)" 정책으로 문제를 해결할 수 있다는 것을 알았습니다. 위험이 낮은 일이라면 일부 경우를 다루지 못하는 자동화도 쓸 만하므로, 오랜 분석으로 시작을 미루지 않습니다.
