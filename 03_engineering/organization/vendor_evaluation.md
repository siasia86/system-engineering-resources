## 1. 개요

| 항목 | 값                                                   |
|------|------------------------------------------------------|
| 목적 | 감정/관성 아닌 데이터 기반 도구 선정                 |
| 범위 | SaaS, OSS, 클라우드 서비스, 상용 소프트웨어          |
| 핵심 | 요구사항 정의 → PoC → TCO → 의사결정 → 계약 → 검증   |
| 위험 | Lock-in, Hidden cost, 과대 평가(PoC bias)            |
| 연관 | Tech Debt (잘못된 선정 = 장기 부채), ADR (결정 기록) |

## 2. 평가 기준

### 필수 평가 항목

| 카테고리      | 평가 항목                                   | 가중치 예시 |
|---------------|---------------------------------------------|-------------|
| Functionality | 요구 기능 충족률, API 완성도                | 30%         |
| Reliability   | SLA, 장애 이력, 가용 리전                   | 20%         |
| Security      | 인증/인가, 암호화, 컴플라이언스 (SOC2, ISO) | 15%         |
| Performance   | Latency, Throughput, 확장성                 | 15%         |
| Cost          | TCO 3년 기준, 가격 모델 투명성              | 10%         |
| Ecosystem     | 통합성, 커뮤니티, 문서 품질                 | 5%          |
| Exit Strategy | 데이터 이관성, 표준 포맷, API 호환          | 5%          |

### Must-have vs Nice-to-have

| 구분         | 정의                            | 처리                |
|--------------|---------------------------------|---------------------|
| Must-have    | 없으면 도입 불가                | 불충족 시 즉시 탈락 |
| Nice-to-have | 있으면 좋지만 대안 가능         | 점수 가산           |
| Deal-breaker | 있으면 도입 불가 (보안 위험 등) | 해당 시 즉시 탈락   |

## 3. PoC 설계

### PoC 원칙

| 원칙                | 설명                                           |
|---------------------|------------------------------------------------|
| 실제 워크로드       | 데모 데이터 아닌 프로덕션 유사 환경에서 테스트 |
| 제한된 기간         | 2~4주 (길어지면 매몰 비용 발생)                |
| 성공 기준 사전 정의 | PoC 시작 전 합격 기준 명문화                   |
| 복수 후보           | 최소 2개 후보 동시 PoC (비교 가능)             |

### PoC 체크리스트

| 단계   | 활동                                      |
|--------|-------------------------------------------|
| Before | 요구사항 목록 + 성공 기준 + 평가 매트릭스 |
| During | 기능 검증 + 성능 측정 + 운영 편의성 확인  |
| After  | 결과 문서화 + 점수 산정 + ADR 작성        |

### PoC 편향 방지

| 편향           | 방지 방법                              |
|----------------|----------------------------------------|
| 챔피언 편향    | 복수 평가자, 블라인드 점수             |
| 매몰 비용      | 기간 엄수, 사전 중단 기준 설정         |
| 벤더 지원 편향 | PoC 중 벤더 지원 수준 = 도입 후와 다름 |
| 기능 과잉 평가 | Must-have 기준으로만 합격 판정         |

## 4. TCO 산정

### TCO 구성 요소

| 항목                 | 포함 내용                               |
|----------------------|-----------------------------------------|
| License/Subscription | 월/연 구독료, 사용자/용량 기반          |
| Infrastructure       | 호스팅, 네트워크, 스토리지              |
| Integration          | 기존 시스템 연동 개발 비용              |
| Migration            | 데이터 이관, 학습, 전환 기간            |
| Operation            | 관리 인력, 모니터링, 업그레이드         |
| Training             | 팀 교육, 문서화                         |
| Exit Cost            | 향후 이탈 시 비용 (데이터 추출, 재개발) |

### TCO 계산 기간

| 기간 | 적합 상황                     |
|------|-------------------------------|
| 1년  | 빠른 검증 필요, 불확실성 높음 |
| 3년  | 일반적 비교 기준 (권장)       |
| 5년  | 대규모 인프라, 장기 계약      |

## 5. Lock-in 평가

### Lock-in 유형

| 유형             | 예시                        | 위험도 |
|------------------|-----------------------------|--------|
| Data Lock-in     | 독점 포맷, 내보내기 불가    | 높음   |
| API Lock-in      | 비표준 API, SDK 의존        | 중간   |
| Platform Lock-in | 특정 클라우드 전용 서비스   | 중간   |
| Contract Lock-in | 장기 계약, 높은 해지 비용   | 중간   |
| Skill Lock-in    | 희귀 기술 스택, 채용 어려움 | 낮음   |

### Lock-in 완화 전략

| 전략              | 방법                                  |
|-------------------|---------------------------------------|
| 표준 포맷 사용    | JSON, CSV, Parquet, OCI               |
| Abstraction layer | Terraform, Crossplane (IaC 추상화)    |
| Multi-vendor 전략 | 핵심 기능은 2nd source 확보           |
| 계약 조건 협상    | 데이터 내보내기 조항, 해지 조건 명시  |
| 정기 이탈 연습    | 연 1회 데이터 추출 + 대안 환경 테스트 |

## 6. 의사결정 매트릭스

### Weighted Scoring 예시

| 기준          | 가중치 | 도구 A (점수) | 도구 B (점수) | 도구 C (점수) |
|---------------|--------|---------------|---------------|---------------|
| Functionality | 30%    | 8 (2.4)       | 9 (2.7)       | 7 (2.1)       |
| Reliability   | 20%    | 9 (1.8)       | 7 (1.4)       | 8 (1.6)       |
| Security      | 15%    | 8 (1.2)       | 9 (1.35)      | 8 (1.2)       |
| Performance   | 15%    | 7 (1.05)      | 8 (1.2)       | 9 (1.35)      |
| Cost          | 10%    | 6 (0.6)       | 8 (0.8)       | 7 (0.7)       |
| Ecosystem     | 5%     | 9 (0.45)      | 6 (0.3)       | 7 (0.35)      |
| Exit Strategy | 5%     | 7 (0.35)      | 5 (0.25)      | 8 (0.4)       |
| **Total**     | 100%   | **7.85**      | **8.00**      | **7.70**      |

## 7. 계약 검토

### 주요 검토 항목

| 항목              | 확인 사항                           |
|-------------------|-------------------------------------|
| SLA 보장          | 가용성 %, 위반 시 크레딧, 측정 방법 |
| 데이터 소유권     | 계약 종료 후 데이터 반환 조건       |
| 가격 인상 조항    | 연간 인상 상한, 사전 통보 기간      |
| 해지 조건         | 해지 위약금, 데이터 보존 기간       |
| 보안/컴플라이언스 | SOC2, ISO 27001, GDPR, 감사 권한    |
| 지원 수준         | 응답 시간, 전담 TAM, 긴급 지원 채널 |

## 8. 도입 후 검증

### 30/60/90일 검증

| 시점 | 검증 항목                                   |
|------|---------------------------------------------|
| 30일 | 기본 기능 동작, 통합 완료, 팀 온보딩        |
| 60일 | 성능 기준 충족, 운영 안정성, 비용 예측 일치 |
| 90일 | 전체 요구사항 충족, Go/No-go 최종 판정      |

### 실패 시 롤백 계획

- 도입 전 기존 도구/서비스 즉시 제거하지 않음
- 90일 검증 완료 전까지 이전 시스템 유지
- 롤백 절차 + 데이터 복원 방법 사전 문서화

## 9. 트러블슈팅

| 증상                      | 원인                   | 해결                                  |
|---------------------------|------------------------|---------------------------------------|
| PoC 결과와 실제 운영 괴리 | 벤더 과도한 PoC 지원   | PoC 중 지원 수준 제한, 자체 운영 검증 |
| TCO 초과                  | Hidden cost 미발견     | Exit cost + Integration cost 포함     |
| 도입 후 사용률 저조       | 팀 니즈 미반영         | 사용자 인터뷰 기반 요구사항 재정의    |
| Lock-in 후 가격 인상      | 계약 조건 미확인       | 인상 상한 조항, 멀티벤더 전략         |
| 의사결정 지연             | 기준 불명확, 합의 부재 | Weighted scoring + ADR 작성           |

> 벤더 평가 프레임워크는 Gartner의 Magic Quadrant 방법론과 NIST SP 800-53(보안 통제)을 참고하여 구성했습니다.
> — https://www.gartner.com/en/research/methodologies/magic-quadrants-research
> — https://csrc.nist.gov/publications/detail/sp/800-53/rev-5/final

> TCO(Total Cost of Ownership) 평가 시 라이선스 비용만이 아닌 운영, 교육, 마이그레이션, 종속성 비용을 포함해야 합니다.
> — AWS Well-Architected Framework, Cost Optimization Pillar: https://docs.aws.amazon.com/wellarchitected/latest/cost-optimization-pillar/

> 보안 평가 시 SOC 2 Type II 보고서와 ISO 27001 인증을 기본 요구사항으로 설정합니다.
> — https://www.aicpa-cima.com/topic/audit-assurance/audit-and-assurance-greater-than-soc-2

> Vendor Lock-in 평가: 데이터 이식성(export 가능 여부), API 표준 준수(OpenAPI 등), 계약 조건(exit clause)을 확인합니다.
> — NIST SP 500-292: Cloud Computing Reference Architecture (https://www.nist.gov/publications/nist-cloud-computing-reference-architecture)
